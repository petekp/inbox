# Differences on purpose: how each host runs in Herdr

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |
| --- | --- | --- | --- | --- | --- |
| Herdr sidebar (`herdr-sidebar`) | Inside a pane of Herdr's terminal multiplexer, each saved change reports the pane tokens with `herdr pane report-metadata`. Inside a Herdr app terminal, it sets the same values as `inbox.` labels on the terminal with one `hc label` call, with `inbox.session` naming the session, and tries `hc` on `PATH`, then `~/.local/bin/hc`. The session's end clears them. When a report fails, the next change sends it again. A timer also retries it after each wait in `HERDR_RETRY_MS`, and stops once Herdr takes a report. Herdr's app does not draw the labels in its sidebar yet. | Same as terminal when the app has `HERDR_PANE_ID` or `HC_TERMINAL_ID`. An app started outside Herdr has neither. | A Codex CLI in Herdr reports from its hooks and from the update a hook starts. Each report runs under the session's Herdr lock and reads the newest saved state, so reports from these processes go out in the order they run. A pane report carries the state's `writtenAt` as `--seq`, and Herdr drops one whose `--seq` is not above the last one it took. Each change a hook or an update makes sets `writtenAt` under the session's lock, always above the one before it, even when nothing else changed. A report that fails is not saved, so the next hook or update sends it again. No timer retries it. A record or close the agent makes during a turn reaches the sidebar at the next hook. Codex finds no stops, and its tokens and labels stay after the session ends. | Codex runs hooks with the CLI's environment, but its MCP server gets only the variables `.mcp.json` lists, and in the Codex app one server serves every chat. Codex has no hook for a session's end. A hook or update process exits when its work ends, so it cannot hold a retry timer. `hc label` takes no sequence number, so only the lock orders reports from separate processes. | `hooks/herdr.ts:herdrTokens`, `hooks/herdr.ts:herdrTarget`, `hooks/herdr.ts:herdrReporter`, `hooks/mod-herdr.ts:publishToHerdr`, `codex/src/host.ts:herdrOnWrite`, `omp/src/host-sessions.ts:reportCounts` |
| Session published for the Herdr look, and its presses (`herdr-look`) | In a Herdr app terminal, each saved change publishes the session to `<app home>/inbox/sessions/<session id>.json`, where the app home is `HERDR_APP_HOME` or `~/.config/herdr-app`. It writes a temporary file and moves it over the old one, in the same turn as the label report and before it. Over 1 MiB it leaves out the closed items the view does not show and sets `trimmed: true`. The session's end removes the file. The mod applies the presses the look writes to `<app home>/inbox/presses/<session id>/`. It reads that folder at start, when the terminal's `inbox.press` label changes, which it follows with `hc events`, and every 10 seconds. A press with `result` records that outcome and does not open or copy again. After each press, the published file names it in `lastPress`, with `stale` when its row had already changed. The folder also takes a look file, which reports a look at the Status that ended. The host counts it as `lookReported` counts it, in time order with the presses, and names it in no `lastPress`. The Herdr look writes none yet. | Same as terminal when the app has `HC_TERMINAL_ID`, except that omp watches the shown session's press folder with `fs.watch` instead of following the label. | Each hook, each update and the MCP server publish under the session's Herdr lock, from the newest saved state, with the state's `writtenAt`. The MCP server watches the whole presses folder and applies the presses of each session whose published file names Codex and this terminal. The file stays after the session ends. | Codex's MCP server cannot tell which session it serves until a tool call names one. Codex has no hook for a session's end. omp and Codex run in long-lived processes that can watch a folder, and the mod cannot. | `hooks/herdr-app.ts:publishSession`, `hooks/herdr-app.ts:pressDrainer`, `hooks/herdr.ts:herdrEnvelope`, `hooks/herdr-app.ts:applyHerdrFile`, `hooks/status-children.ts:lookReported`, `hooks/mod-herdr.ts:publishToHerdr`, `hooks/mod-herdr.ts:listenForHerdrPresses`, `codex/src/host.ts:herdrOnWrite`, `codex/src/server-herdr.ts:followCodexPresses`, `omp/src/host-sessions.ts:reportCounts`, `omp/src/host-presses.ts:ompPresses` |
| Opening the Herdr look (`herdr-open`) | In a Herdr app terminal, `/inbox` and the band's Open inbox press open the Herdr look in a pane to the right of the terminal, and the inbox pane stays closed. The mod finds the terminal's pane in `herdr-app ls` and runs `herdr-app do pane.split` with `direction: right` and `mod: inbox`. It tries `herdr-app` on `PATH`, then `~/.local/bin/herdr-app`. After a split it sets the terminal's `inbox.panel` label to the new pane. The next open, from this host or another in the terminal, runs `pane.focus` on that pane: exit 0 focuses it, `no such pane` splits again, and any other failure says the inbox is already open. Two opens at once share one split. When the app home has no `mods/inbox/main.js`, no `herdr-app` starts, `ls` lists no pane for the terminal, or the split fails, the mod opens the inbox pane. A split that prints no pane or times out may still have opened one, and the line says so. `/inbox` says why in its reply line, and the band press writes why to the debug log. The mod reads whether the app home has the inbox mod as it publishes, so a press without it opens the inbox pane at once. A band press whose split fails opens the pane after the `herdr-app` calls, so below 144 columns, once the person has closed the pane, the engine can leave it unplaced. `/inbox` with any argument, and any open while a demo is on, stays in the inbox pane. A `herdr-app` that hangs holds an open for up to three 5 s calls. Outside an app terminal nothing new runs. | Same as terminal when the app has `HC_TERMINAL_ID`. An app started outside Herdr has none. | None. | The Codex CLI has no action that opens the inbox: a Codex plugin adds skills, MCP servers and hooks but no slash command, and the Inbox tab shows only in the Codex app. A `$inbox` skill that has the model call an MCP tool could open the look, but only after a model turn, so the press could not show what it did at once. It stays an option. `herdr-app ls` lists terminals and not mod panes, so a host finds the panel only through the `inbox.panel` label or the pane it remembers. The band has no line for a note. | `hooks/herdr-open.ts:herdrPanelOpener`, `hooks/mod-herdr.ts:openInHerdr`, `hooks/register.tsx:openInbox`, `hooks/register.tsx:on('command.run')`, `omp/src/host.ts:createInbox` |
| Installing and updating the Herdr mod (`herdr-install`) | Once at turn-on in a Herdr app terminal, the mod compares the build time on the second line of its own `herdr/mod/inbox/main.js` with the one in `<app home>/mods/inbox/main.js`, and replaces an older inbox build. That line also says how many characters follow it, so an installed copy cut off mid-write counts as older, and a bundled copy cut off is not installed. It writes the new files to a temporary folder under `<app home>/inbox/` and moves them over the old ones, `main.js` last, so Herdr reloads the mod in place. A missing mod is installed only after a yes saved in `<app home>/inbox/herdr-mod.json`, which every host reads. After the install the answer reads `installed`, so a mod the person removes stays removed. A `mods/inbox` that is a link, whose `main.js` or `mod.json` is not a plain file, or that holds no inbox build, is the person's own and is never written, whatever build time it holds. An installed build stamped later than the clock counts as older. An answer file in a newer format counts as answered: no host asks, installs or writes over it, and `/inbox herdr` says a newer build saved it. A build of the inbox from a development checkout carries a newer time, so it replaces the installed one until a build with newer code starts. Two hosts with different builds that start at the same moment can both pass the check, and the older one's move can land last. No lock prevents this, since a lock left by a host that stopped would need its own cleanup. The newer host's next start replaces it again: a Claude Code turn-on, an omp start or a Codex handler load. The same start removes each published session file, with its press folder, that no live terminal's `inbox.session` label names, that was written over a day ago, and that another terminal published. It reads the labels with one `terminal.list` call through `hc connect`, and removes nothing unless the list holds its own terminal and every entry has a `labels` object. It also removes each temporary file or folder an install, update or answer left in `<app home>/inbox/` over a day before, as when its host stopped mid-write, and finds its age in its name. Each outcome and failure goes to the debug log. A failed install or update also shows as a warning banner under the tab bar, with the failure text, until the next turn-on. When the mod is missing and no answer is saved, a banner under the tab bar asks "Install the inbox's Herdr mod?" on its own line in `pal.key`, the blue the terminal draws keys in, with its tint mixed from that blue. Under it, in the muted color, it says what the mod does and names the folder. Install and Don't install sit on a line below. The terminal's Button takes only a plain label, so Install is not drawn as the recommended answer. Either press hides the buttons at once. Install shows "Installing the inbox mod in Herdr…", then "✓ Installed the inbox mod in Herdr." Don't install shows "Saving the answer…", then "Run /inbox herdr to install it later." Each result clears after `SETTLED_MS`, and a failed press shows the warning banner. Each open session reads the answer file every `PRESS_POLL_MS` and drops the question once another session answers. `/inbox herdr` shows the question again, even after a no. The band does not count the question: it counts what waits on the person for the agent's work to go on, and this is an offer from the inbox about itself, so a count in every session would nag. | Same as terminal when the app has `HC_TERMINAL_ID`. The question's tint is one rgba halfway between the terminal's light and dark key blues, since the desktop palette has one tint for both of the app's themes. omp does it at its first `session_start`, from the copy in `omp/dist/herdr-mod/`, and its panel shows the same failure banner. omp asks the question in a row at the top of the Asks tab, boxed like the stop row, with its first line in the `key` tone and Install underlined and marked "(recommended)", as omp marks a recommended answer. `/inbox herdr` there shows it again and opens the panel on the Asks tab, where the row is. | The MCP server does it each time its handler loads, from the copy in `codex/plugin/dist/herdr-mod/`, and a failure then goes only to `herdr.log`. The Codex app's Inbox tab asks the same question in any terminal when the Herdr app's settings folder exists, the mod is missing and no answer is saved. A settings folder that is a link counts. Each view reads the answer file first, and reads nothing more once an answer is saved. Its banner uses `var(--key)`, and Install is filled as the recommended answer. Don't install shows "Run /inbox herdr in Claude Code or omp to install it later." A failed press from the tab shows the warning banner. | The Codex CLI shows no inbox where the question or a failure could show: a Codex plugin adds no slash command, and the Inbox tab shows only in the Codex app. So only the app's tab asks, and Codex has no `/inbox herdr`. omp's panel takes keys only, so the question is a row the person can move to. The Herdr look never asks, since it is the mod being offered. Codex and omp install only their own folders, so `herdr/build.ts` writes a copy of the mod into each. A reinstall loads the handler again with the newer copy beside it, so Codex updates then. | `hooks/herdr-install.ts:keepHerdrModCurrent`, `hooks/herdr-install.ts:answerHerdrMod`, `hooks/herdr-sweep.ts:sweepPublished`, `hooks/herdr-sweep.ts:labelledSessions`, `hooks/herdr-sweep.ts:sweepModTemporaries`, `hooks/herdr-ask.ts:herdrAskBanner`, `hooks/herdr-ask.ts:answerHerdrAsk`, `hooks/herdr-ask.ts:herdrAskInApp`, `hooks/mod-herdr.ts:pressHerdrAsk`, `hooks/pane-frame.tsx`, `omp/src/host-herdr-ask.ts:ompHerdrAsk`, `omp/src/panel-entries.ts`, `omp/src/panel.ts`, `codex/src/server-herdr.ts:codexHerdrAsk`, `codex/src/tab-herdr-ask.tsx`, `hooks/herdr-start.ts:startInHerdrApp`, `hooks/mod-herdr.ts:startInHerdr`, `codex/src/server-herdr.ts:startCodexInHerdrApp`, `omp/src/host-presses.ts:startOmpInHerdrApp`, `herdr/build.ts` |
