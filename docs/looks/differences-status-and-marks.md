# Differences on purpose: the Status page and marks

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |

| Status head | The title, bold, in the column of the rows' marks, with the description muted on the line under it. A head with no description yet shows the title alone. The omp panel draws the same, with the description dim. | Same as terminal, in the row frame. | The title is 15 px semibold over 13 px rows, at the marks' left edge, with the description muted at 13 px under it. | The terminal has one text size, and desktop Text has no size prop, so those looks set the title apart by weight alone. | `hooks/pane-status-lines.tsx:statusHead`, `codex/src/tab-css/status-page.css:.status-head`, `omp/src/panel-entries.ts:pageEntries` |
| What a look counts as seen (`seen-on-screen`) | A subject counts as seen when its row's first line was in the pane's window at any point after the subject last changed, even for a moment during a scroll. Claude Code tells a pane its scroll offset and height but not where each row sits, so each function that draws a part of the Status returns the terminal lines that part takes with its element, and the rows' first lines come from stacking those parts. Text Claude Code wraps itself counts only when one cell less of width would wrap it the same way. A row below anything it cannot count exactly, such as an open goal field, counts as seen, and so does every row while a banner or the demo notice sits above the tabs' page, or the tabs wrap. The omp panel counts the rows whose first line is in its window, from `drawPanel`. A named fold's row counts as showing every subject in its `subjectIds`, in every look. | The same rule, from estimated lines. Each function that draws a part of the Status returns the least and the most lines that part may take, in the pane's scroll rows of one text line. A row counts as seen when its first line is surely whole in the window: with the most lines above it, the line still ends by the window's bottom, and with the least, it starts at or under the window's top. A row whose first line is surely in the lines the windows covered while the person scrolled counts as seen from when they started covering. For that, each window must overlap the one before by one line plus the page top's range, and no row may have moved between the draws. Text counts at least one line, and at most the lines `desktopLines` estimates one cell narrower than its column. Padding, margins and gaps count half a line per cell, a native button 23 pt, and the tabs the height of their Client. Other work's counts take at most the lines they wrap to when each count moves down whole. The page's top counts a row either way, because the pane reports its scroll in whole rows and may round its height up. A row with no known place, such as one below an open goal field or while a banner sits above the tabs' page, stays unseen until a look places it. So desktop can leave a row that was on screen unseen, and never counts one that was not. | The tab notes each row whose top is inside its window, by the subjects in its `data-subjects` attribute, after each draw and on each scroll, and sends them with its next `inbox_view` request. The server keeps them in `lookRows` until the look ends, so a look that ends because the pane closed still counts them. | No pane hook learns where an element sits or how tall it is, so each look counts its own lines. The terminal wraps text in whole cells, so it counts them exactly. Desktop wraps text in a proportional font whose widths the mod only estimates from above, so it bounds each row's first line instead. The terminal counts a row with no known place as seen, since it loses a row's place whenever a line of text ends within a cell of its column's edge. Desktop loses a place only below the few parts it does not bound, so it leaves those rows unseen. | `hooks/status-children.ts:lookEnded`, `hooks/pane-status-shown.ts:noteStatusDrawn`, `hooks/pane-status-tops.ts:stacked`, `hooks/pane-status-tops.ts:desktopTextLines`, `omp/src/panel.ts:drawPanel`, `codex/src/tab.tsx:noteStatusInView`, `codex/src/core.ts:lookOnView` |
| Running marks (`pending-answer-mark`) | A row's result mark runs while what the row sent is on its way, as an answer, a Done or a Fix, and while the agent works on a Talk press, beside "Explaining…". It is blank while an answer or a Fix waits out its Undo window, since nothing has left yet. On the Status, a working subject's mark moves while this session's turn runs or a child under it still moves, unless an open item holds it up. When neither runs, it draws ◐, which stays still in every look. A child's mark moves while it runs. A delegate that waits shows ◆ and a finished one ✓, neither moving. The mark cycles through ● ◉ ◎ ◉, one frame each `RUNNING_FRAME_MS`. One timer redraws the pane while it shows a running mark. The omp panel draws the same glyphs, from a timer that redraws only the panel. | The mark is an Svg dot, the size of the ● glyph, that fades and returns once each `RUNNING_PULSE_MS`. A pane redraw starts an Svg's animation again, so each dot begins at the clock's point in the pulse, and every dot moves together. | The mark fades and returns once each `RUNNING_PULSE_MS`, in CSS. Every mark's animation starts at the page's time origin, so all of them move together. With reduced motion, the mark stays still. | Terminal text has no opacity, so it changes the glyph. A pane redraw loop stops clicks on desktop, and an Svg animates without redraws. A still ● read as a frozen running mark, so a working subject with nothing running draws its own mark. | `hooks/timing.ts:runningMark`, `hooks/help.ts:IDLE_MARK`, `hooks/running-mark-timer.ts:animateRunningMarks`, `hooks/desktop-svg.ts:runningSvg`, `hooks/pane-row-lines.tsx:markGlyph`, `codex/src/tab-status.tsx:StatusLine`, `codex/src/tab-parts.tsx:ResultMarkView`, `omp/src/panel-page.ts:drawPageRow`, `omp/src/panel-draw.ts:markText`, `omp/src/controller.ts:createPanel` |
| Result marks and the mark column | An Asks or Finds row has no mark column: its title starts after the tree's arm. Its result mark, with a space, starts its result: the settled label on the line under the title, a Closed line's outcome, or a handed-off row's feedback. A blank mark keeps its two cells. A dismissed PR's block has no mark column either. Its title starts at an open PR title's edge, and its ✕ starts "✕ Dismissed" on the line under it. | The row's mark column stays, and the result mark is drawn in it, with the Svg dot while it runs. | Same as desktop, in the row's first grid track. | Only the terminal draws a tree, so only there did the column sit between the tree and the text. On desktop and in Codex the column is also the indent under the group title and the Status's mark track, so dropping it would put rows left of their group title. Desktop's row Client draws text only, so a running Svg cannot sit in its result text. | `hooks/pane-row-lines.tsx:columnsFor`, `hooks/pane-row-parts.tsx:resultLine`, `hooks/pane-prs.tsx:settledPrBlock`, `hooks/pane-row-lines.tsx:gutterMark`, `codex/src/tab-parts.tsx:resultHandle`, `codex/src/tab-css/groups.css:.group-mark` |
| The cancelled and waiting marks | ⊘ in place of ✗, from `textMark`, and the font's ◌. A cancelled check's ⊘ is the font's too. The omp panel draws the same. | ✗, ◌ and a cancelled check's ⊘ are Svg shapes from `mutedMarkShape`, in the mark's color, wherever a row or the Help legend draws them. ✗ is the ballot X. ◌ is a ring of eight short dashes as wide as ○, so its Svg takes two cells and centres the ring where ○ sits. ⊘ is a ring as wide as ○ crossed by a slash, in two cells. A dismissed row's ✕ stays text. | ✗, ◌ and ⊘ are inline svgs of the same shapes, in the mark's color, wherever a row or the Help legend draws them. The ring sits where the tab's font draws ○. A dismissed row's ✕ stays text. | The system font draws ✗ the same as ✕, so a cancelled row would look dismissed. It draws ◌ with specks for dots, so a waiting subject's mark nearly vanishes. In the Codex tab, the font's ◌ is 13 px across at 2x beside a 22 px ○, with about a ninth of ○'s ink. The system font draws ⊘ thin and about 60% as wide as ○. The desktop pane's Text cannot choose a font, and its Svg cannot load the app's font. A drawn shape looks the same whatever fonts the system has. macOS Terminal's default font, SF Mono, draws ✗ as ×. It has no ✕, so Terminal falls back to Menlo, which draws ✕ as the same ×. A text look can draw only a font's glyphs, so the terminal and omp draw ⊘, which Menlo draws as a slashed circle. Desktop and Codex draw the ballot X that ✗ names. A monospace font draws ◌ as wide as ○. | `hooks/marks.ts:textMark`, `hooks/timing.ts:resultGlyph`, `omp/src/panel-draw.ts:paintMark`, `hooks/marks.ts:mutedMarkShape`, `hooks/marks.ts:cancelledMarkShape`, `hooks/marks.ts:waitingMarkShape`, `hooks/marks.ts:cancelledCheckShape`, `hooks/desktop-svg.ts:mutedMarkSvg`, `hooks/pane-row-lines.tsx:markGlyph`, `hooks/pane-status.tsx:statusMark`, `hooks/pane-help.tsx:legendMark`, `codex/src/tab-parts.tsx:MarkGlyph`, `codex/src/tab-parts.tsx:CIRCLE_MID`, `codex/src/tab-status.tsx:StatusLine` |
| Tree lines on the Status | The Asks tree's glyphs, in the subject's mark column: `│` runs down from under the subject's mark, each row under it starts with `├─`, and the last with `└─`. A wrapped row keeps `│` beside each line while rows follow it. The omp panel draws the same glyphs. | Hairlines, each a 1 pt filled Box in the divider color, in the same places. Each row draws its part in its mark column, and each part reaches over the frame's padding and border to meet the next row's. | 1 px CSS lines in the same places, drawn by each row's `::before` and `::after`. | Desktop lines differ in height, so stacked glyphs break into separate bars, and a Box has no per-side border. A web page draws lines with CSS. | `hooks/pane-status-lines.tsx:statusTree`, `codex/src/tab-css/status-page.css:.has-children`, `omp/src/panel-page.ts:withTree` |
| The rule after the goal | The goal and the list after it draw as one section, and a run of `─` in the divider color, from the text column to the end of the row, takes the last of the blank lines that would sit between them. So the docked pane draws a blank line and the rule, and the inline pane only the rule, and the page is no taller than with two sections. The omp panel draws a blank line, then the same run in its dim color. While the page sets no rule, the terminal and omp keep their blank lines. | The hairline between two sections is the rule. While the page sets no rule after a goal, that hairline keeps its space and draws no line. | The line between two sections (`section + section::before`) is the rule. While the page sets no rule after a goal, the list after it takes `.unruled` and draws no line. | Desktop and Codex already draw a line between every two sections, so a second rule there would double it. The terminal separates sections with blank lines only. Desktop text uses a proportional font, where a run of `─` sized in cells wraps onto a second line. A web page draws lines with CSS. | `hooks/pane-status.tsx:terminalGoalEndRule`, `hooks/pane-row-parts.tsx:sections`, `codex/src/tab-css/status-page.css:.unruled`, `omp/src/panel-page.ts:pageRule`, `omp/src/panel-goal.ts:drawGoalPart` |
| The Status call's subject rule | The Status call reads `STATUS_SYSTEM`, which has no rule for splitting a plan into subjects. The omp panel's call reads the same. | Same as terminal. | The call reads `PARTS_STATUS_SYSTEM`. Each part of the plan that the person would name on its own gets its own subject, queued until it starts. Work that the session's own subagents or background tasks do on a subject keeps it working. | The rule helps Codex and hurts Sonnet. In the `single-task` replay, 3 runs per model, it cut Codex's failed rule-steps for `open-pieces-kept` from 26 to 16 of 30, and for `changes-move` from 14 to 6. On Sonnet, the proposed goal's milestones copied the subjects' names, and `milestones-true` failed 27 of 30, against 17 without the rule. Proposing the goal in a separate call before the Status call left it at 23. | `hostStatusSystem` in `hooks/status-prompt.ts`, `splitsPlanIntoSubjects` on each `Host` |
