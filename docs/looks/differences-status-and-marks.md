| Status head | The title, bold, as the heading of the list after the goal, in the place of "Other work": at the mark column, where the Goal heading starts, with a rule to the right edge, and the description muted on the line under it. A head with no description yet shows the title alone. With no goal, its rule follows the goal's empty section. The omp panel draws the same, with the description dim. | Same as terminal, in the row frame. | The title is semibold at the mark column over the rule, in the text color, with the description muted under it. | The terminal has one text size, and desktop Text has no size prop, so those looks set the title apart by weight alone. | `hooks/pane-status-part.tsx:statusPartLine`, `codex/src/tab-css/status-page.css:.part-title`, `omp/src/panel-page.ts:partHeading` |
| What a look counts as seen (`seen-on-screen`) | A subject counts as seen when its row's first line was in the pane's window at any point after the subject last changed, even for a moment during a scroll. Claude Code tells a pane its scroll offset and height but not where each row sits, so each function that draws a part of the Status returns the terminal lines that part takes with its element, and the rows' first lines come from stacking those parts. Text Claude Code wraps itself counts only when one cell less of width would wrap it the same way. A row below anything it cannot count exactly, such as an open goal field, counts as seen, and so does every row while a banner or the demo notice sits above the tabs' page, or the tabs wrap. The omp panel counts the rows whose first line is in its window, from `drawPanel`. A named fold's row counts as showing every subject in its `subjectIds`, in every look. | The same rule, from estimated lines. Each function that draws a part of the Status returns the least and the most lines that part may take, in the pane's scroll rows of one text line. A row counts as seen when its first line is surely whole in the window: with the most lines above it, the line still ends by the window's bottom, and with the least, it starts at or under the window's top. A row whose first line is surely in the lines the windows covered while the person scrolled counts as seen from when they started covering. For that, each window must overlap the one before by one line plus the page top's range, and no row may have moved between the draws. Text counts at least one line, and at most the lines `desktopLines` estimates one cell narrower than its column. Padding, margins and gaps count half a line per cell, a native button 23 pt, and the tabs the height of their Client. Other work's counts take at most the lines they wrap to when each count moves down whole. The page's top counts a row either way, because the pane reports its scroll in whole rows and may round its height up. A row with no known place, such as one below an open goal field or while a banner sits above the tabs' page, stays unseen until a look places it. So desktop can leave a row that was on screen unseen, and never counts one that was not. | The tab notes each row whose top is inside its window, by the subjects in its `data-subjects` attribute, after each draw and on each scroll, and sends them with its next `inbox_view` request. The server keeps them in `lookRows` until the look ends, so a look that ends because the pane closed still counts them. The Herdr look counts a row only when its first line is in view with the list scrolled to either end. [Its table](differences-herdr-status.md) says why. | No pane hook learns where an element sits or how tall it is, so each look counts its own lines. The terminal wraps text in whole cells, so it counts them exactly. Desktop wraps text in a proportional font whose widths the mod only estimates from above, so it bounds each row's first line instead. The terminal counts a row with no known place as seen, since it loses a row's place whenever a line of text ends within a cell of its column's edge. Desktop loses a place only below the few parts it does not bound, so it leaves those rows unseen. | `hooks/status-children.ts:lookEnded`, `hooks/pane-status-shown.ts:noteStatusDrawn`, `hooks/pane-status-tops.ts:stacked`, `hooks/pane-status-tops.ts:desktopTextLines`, `omp/src/panel.ts:drawPanel`, `codex/src/tab.tsx:noteStatusInView`, `codex/src/core.ts:lookOnView`, `hooks/status-children.ts:lookReported` |
| Running marks (`pending-answer-mark`) | A row's result mark runs while what the row sent is on its way, as an answer, a Done or a Fix, and while the agent works on a Talk press, beside "Explaining…". It is blank while an answer or a Fix waits out its Undo window, since nothing has left yet. On the Status, a working subject's mark moves while this session's turn runs or a child under it still moves, unless an open item holds it up. When neither runs, it draws ◐, which stays still in every look. A child's mark moves while it runs. A delegate that waits shows ◆ and a finished one ✓, neither moving. The mark cycles through ● ◉ ◎ ◉, one frame each `RUNNING_FRAME_MS`. The mod's one timer for the shared controller's wakes redraws the terminal for each frame, and only once the last frame has drawn. A frame redraws only the terminal, so desktop beside it is not redrawn. The omp panel draws the same glyphs, from a timer that redraws only the panel. | The mark is an Svg dot, the size of the ● glyph, that fades and returns once each `RUNNING_PULSE_MS`. A pane redraw starts an Svg's animation again, so each dot begins at the clock's point in the pulse, and every dot moves together. | The mark fades and returns once each `RUNNING_PULSE_MS`, in CSS. Every mark's animation starts at the page's time origin, so all of them move together. With reduced motion, the mark stays still. | Terminal text has no opacity, so it changes the glyph. A pane redraw loop stops clicks on desktop, and an Svg animates without redraws. A still ● read as a frozen running mark, so a working subject with nothing running draws its own mark. | `hooks/timing.ts:runningMark`, `hooks/help.ts:IDLE_MARK`, `hooks/mod-ui-loop.ts:wakeUi`, `hooks/ui-controller-clock.ts:nextWakeAt`, `hooks/desktop-svg.ts:runningSvg`, `hooks/pane-row-lines.tsx:markGlyph`, `codex/src/tab-status-line.tsx:StatusLine`, `codex/src/tab-parts.tsx:ResultMarkView`, `omp/src/panel-page.ts:drawPageRow`, `omp/src/panel-draw.ts:markText`, `omp/src/controller.ts:createPanel` |
| Result marks and the mark column | An Asks or Finds row has no mark column: its title starts after the tree's arm. Its result mark, with a space, starts its result: the settled label on the line under the title, a Closed line's outcome, or a handed-off row's feedback. A blank mark keeps its two cells. The omp panel draws the same. A dismissed PR's block has no mark column either. Its title starts at an open PR title's edge, and its ✕ starts "✕ Dismissed" on the line under it. | The row's mark column stays, and the result mark is drawn in it, with the Svg dot while it runs. | Same as desktop, in the row's first grid track. | Only the terminal and omp draw a group's rows on a tree, so only there did the column sit between the tree and the text. On desktop and in Codex the column is also the Status's mark track, so dropping it would put rows left of the Status's marks. A group title with no mark starts at the mark column its own rows use, in the Herdr panel, Codex and desktop, where the title is at the edge of the marks' hung column. On desktop that edge is the frame's inset, one cell right of where a hung mark's glyph starts. A PR's title, its group titles and its Other PRs caption keep the text column on desktop and in Codex, since a settled PR there draws its mark in the first column with its title in the second, and a title at the edge would jump when the PR settles. The Herdr panel puts them at the edge. The terminal and omp draw no lead for a title with no mark, so they already match. Desktop's row Client draws text only, so a running Svg cannot sit in its result text. | `hooks/pane-row-lines.tsx:columnsFor`, `hooks/pane-row-parts.tsx:resultLine`, `hooks/pane-prs.tsx:settledPrBlock`, `hooks/pane-row-lines.tsx:gutterMark`, `codex/src/tab-parts.tsx:resultHandle`, `codex/src/tab-css/groups.css:.group-mark` |
| The cancelled and waiting marks | ⊘ in place of ✗, from `textMark`, and the font's ◌. A cancelled check's ⊘ is the font's too. The omp panel draws the same. | ✗, ◌ and a cancelled check's ⊘ are Svg shapes from `mutedMarkShape`, in the mark's color, wherever a row or the Help legend draws them. ✗ is the ballot X. ◌ is a ring of eight short dashes as wide as ○, so its Svg takes two cells and centres the ring where ○ sits. ⊘ is a ring as wide as ○ crossed by a slash, in two cells. A dismissed row's ✕ stays text. | The system font draws ✗ the same as ✕, so a cancelled row would look dismissed. It draws ◌ with specks for dots, so a waiting subject's mark nearly vanishes. | The goal's path | `│` in the milestones' mark column, from under a milestone's mark to the next milestone's, and `┆` into the next one. | Tree lines on the Status | The Asks tree's glyphs, in the subject's mark column: `│` runs down from under the subject's mark, each row under it starts with `├─`, and the last with `└─`. A wrapped row keeps `│` beside each line while rows follow it. A milestone draws the same down to its rows. Where the path's line runs on past them, a row's `├─` takes the path glyph's place on its first line, and `│` or `┆` goes on beside its other lines. The omp panel draws the same glyphs, with a milestone's rows a cell further in so a space follows each arm, as after a subject's. | Hairlines, each a 1 pt filled Box in the palette's `line` color, in the same places. Beside the path's line, a milestone's row draws only its arm, starting a hairline right of the path's. That color is translucent and the app refuses `color-mix()`, so no two parts cover the same point. | 1 px CSS lines in the same places, drawn by each row's `::before` and `::after`. | The Status call's subject rule | The Status call reads `STATUS_SYSTEM`, which has no rule for splitting a plan into subjects.
