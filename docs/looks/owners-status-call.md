# Owners: the Status call

Part of [the look map](../looks.md#who-owns-each-rule).

| Rule | Owner | Read by |
| --- | --- | --- |
| Status-failed warning (`status-failed-warning`) | `hooks/session-host.ts:runUpdates`, `hooks/session-status.ts:failedStatus`, `hooks/status-page.ts:statusPage`, `hooks/view.ts:footerStatus` | Every host. A Status call that gives no answer, or answers twice with no operation, saves `overviewFailure`: its time, its cause, and the start of a refused answer. The Status tab's status line then reads "The inbox couldn't update this page from one of the agent's replies. What changed in that reply may be missing. It reads the conversation again after the next reply." in place of the update-failed warning, until a catch-up Status call, which reads the whole conversation, writes. `needsCatchUp` makes the next reply's update a catch-up while the failure stands. The line stays while that call runs. |
| Status refresh during a long turn (`status-mid-turn-refresh`) | `hooks/session-status.ts:claimedStatusRefresh`, `hooks/status-records.ts:refreshStatus`, `hooks/status-prompt.ts:statusMidTurnPrompt` | Every host. The main agent's next tool call after `STATUS_REFRESH_MS` has passed since the turn started and since the last Status call claims a Status call, in the same write that notes the activity, so two calls in a row claim it once. The mod and omp note a call's activity when the call ends, and only for a call that ran (`ran-call-activity`), so a call claims the Status call when it ends. The call reads what the person sent and the turn's activity so far, with no reply, and runs after the session's earlier Status calls. A subagent's tool calls claim none, since the call reads only the main agent's activity. An idle session makes no call. The mod claims in `hooks/register.tsx:noteActivity` and omp in `omp/src/host-activity.ts:noteQuietly`, and each runs the call in its own process. Codex claims in its `PreToolUse` hook, after it takes back the lines of the turn's earlier calls that did not run, and starts a detached update process in its `status-refresh` mode (`codex/src/update-main.ts`), since a hook process ends before a model call would. |
| Status call records (`status-call-records`) | `hooks/status-records.ts:StatusRecord`, `hooks/status-records.ts:writeStatusRecord`, `hooks/status-records.ts:askAndWriteStatus` | Every host, on a next build only. A release build passes no `records` and keeps none. Each Status call, after a reply, during a long turn or after a catch-up, gets a record once its answer is written. The record is one JSON line in a file of its own, named by the call's start time and kind. It holds the session and time, the exact system text and prompt, and what the prompt was built from as data: the Status the call read with its children, the open asks, the task list, and the exchange, which also says the kind. `hooks/status-records.ts:statusCallPrompt` builds the prompt from that data, so a record can be replayed against a changed prompt. It also holds each answer or error with the model asked for and how long it took, whether the answer parsed, and the saved Status just before and after. The write runs in the background, and a failed write is dropped. A session keeps its newest `RECORDS_PER_SESSION` records, and its records are dropped `RECORDS_KEPT_MS` after its last call. The mod keeps them in `<Claude Code config folder>/plugins/data/inbox/overview-calls/<session>/`. It removes files with `rm` and `rmdir`, since the engine has no call that removes a file. Codex keeps them in its plugin data folder, as `~/.codex/plugins/data/inbox-inbox/overview-calls/<session>/`, and omp in `~/.omp/agent/inbox/overview-calls/<session>/`. omp names the model that answered when its reply's `upstreamModel` says, as a router's or a signed thinking block's model. The mod's engine and `codex exec` never say. `scripts/status-call.sh` prints a record, and with `--run` sends its prompt once more. |
