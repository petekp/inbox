# Differences on purpose: how each host runs

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |
| --- | --- | --- | --- | --- | --- |
| Hot reload | Mod handlers reload. | Same as terminal. | The handler reloads. The tab stages a candidate before replacing its root, style and script. Failed startup keeps the working page; successful replacement waits for active presses. The loader needs Codex restarted. | Each instance owns its timers, listeners and animations. Staging preserves the working UI and host state until the candidate can take over. | `codex/src/server-main.ts:load`, `codex/src/server-handler.ts:createHandler`, `codex/src/tab-swap.ts:swapPage`, `codex/src/tab-host.ts:dispose` |
| Storage | An engine atom holds the drawn conversation's session. The engine store keeps each conversation's saved session. | Same as terminal. | One JSON file per session, under a lock. | Codex has no engine store. Its hooks run as separate short-lived processes beside the server. | `hooks/register.tsx:changeSession`, `codex/src/state.ts:withLock` |
| Band, stop and dialog rows (`band-and-stop-rows`) | Yes. | Yes. | No. | Codex has no line above its prompt. | `hooks/view.ts:LISTED_TABS` |
| PR data | The mod runs gh through the engine, on a timer while the person is around, and when a reply ends once `isPrFetchDue` says so. A Refresh PRs press or a fix press fetches after any fetch that is running. | Same as terminal. | The server runs gh through `deps.exec` in the session's folder, and refetches on a view when `isPrFetchDue` says so: the last fetch is over 2 minutes old, or over 15 seconds old and the agent replied since. A Refresh PRs press or a fix press fetches after any fetch that is running. It tries `gh`, then the Homebrew folders. | The ChatGPT app may start the Codex server without Homebrew on its PATH. A Claude Code session, in the terminal or the Claude app, gets the login shell's PATH. | `hooks/register.tsx:fetchPrsNow`, `hooks/session-host.ts:fetchPrs`, `hooks/session-host.ts:prFetchTracker`, `hooks/gh.ts:ghFinder` |
| Hooks need trust (`hooks-need-trust`) | None. Claude Code runs the mod's hooks without asking for trust. | Same as terminal. | While Codex does not run the inbox's hooks, every chat's Inbox tab shows an error banner under the tab bar, on every tab, saying why and naming the hook icon and Allow all, then Settings' Hooks page for when the icon is missing: "Codex is not running the inbox's hooks…" when Codex never trusted them, and "Codex stopped the inbox's hooks when the inbox updated…" when it trusted them before an update changed the plugin. The Asks tab's empty state then leaves its own hook text out. Otherwise, a chat that has heard from no hook reads "The inbox starts with your next message." The server asks `codex app-server` for `hooks/list` in the background, once per chat folder. It asks again every 5 seconds while Codex is not running the hooks, so the line leaves soon after the person trusts them, and 30 seconds after a failed answer. A trusted answer stands until a turn runs whose prompt and Stop the inbox did not hear, or until the server's handler reloads, as every plugin update makes it do. A missing, trusted or failed answer shows no line. Turns that ended while the hooks were off are caught up at the chat's next hook (see "Catch-up and a behind ledger"). | Codex binds each approval to every file in the plugin, so every update asks again, and until then the hooks fail. omp has no such approval either (see its table). | `codex/src/hook-trust.ts:trustOfHooks`, `codex/src/server-trust.ts:hooksTrustNow`, `codex/src/tab-chrome.tsx:TabBar`, `codex/src/history.ts:withMissedTurns` |
| Where the agent reads the guidance | In the description of the `close` tool, through `tool.describe`. | Same as terminal. | In the `SessionStart` hook's added context. | The guard Claude Code loads on Team and Enterprise sign-ins skips a user mod's `prompt.compose` hook and passes `tool.describe`. Claude Code sends a pinned tool's first 4096 characters, and `record`'s own description leaves too little room, so `close` carries it. The Codex and omp agents read the shared tool descriptions too, so the guidance is not in `hooks/tools.ts`. omp adds it to its system prompt. | `hooks/register.tsx:on('tool.describe')`, `hooks/model-text.ts:guidedCloseDescription`, `codex/src/hook.ts`, `omp/src/host.ts:on('before_agent_start')` |
| Carried state at a conversation's first prompt | The Status's head, as "Working on: title: description", and where each open subject stands, in the first prompt's added context from `prompt.submit`. The `inbox:` text beside that prompt lists the open items and the closed ones. | Same as terminal. | `startContext` gives the head and the open subjects, the open items, the findings and the closed ones in the `SessionStart` context. omp adds only the guidance to the system prompt, in `before_agent_start`, and no state. | The guard skips a user mod's `prompt.context` hook and passes `prompt.submit`. The mod's `inbox:` text already lists the items, so repeating them would duplicate them. Codex and omp have no `inbox:` text before their first prompt. | `hooks/register.tsx:on('prompt.submit')`, `hooks/model-text.ts:statusCarryText`, `hooks/session.ts:startContext` |
| Reload after /clear, /resume and /branch | `classic.SessionStart` reloads at once. Where the guard skips it, the first prompt after the switch reloads, and the pane shows the old state until then. | Same as terminal. | A new session id loads when its hook runs. | The guard skips `classic.*`. `session.start` and `session.attach` do not fire on these switches, and the first prompt is the first event that carries the new id. | `hooks/register.tsx:on('prompt.submit')`, `hooks/register.tsx:on('classic.SessionStart')` |
| Rows that need a hook the guard skips | Where the guard loads, the permission row comes from `tool.check` instead of `classic.PermissionRequest`. The hook returns `next(e)` as it received it, and a `$.tool.check` query of the same call gives the verdict. An `ask` opens the row only if the call has not run after `PERMISSION_FALLBACK_DELAY_MS`, which is 1.5 s, and the row clears when the call ends. In manual mode the row appears 1.5 s after the dialog. The row also clears, and is never drawn, once the call's `ToolUse` row reports `isRunning`, or once its entry in a collapsed `ToolGroup` does, matched by `tool_use_id`. The query asks no PreToolUse hook, so an ask that only a PreToolUse hook makes draws no row. Checked live on Claude Code 2.1.312, with no guard, a stand-in model server, and a stand-in mod ahead of the inbox that answers `classic.PermissionRequest` without calling `next`. Manual mode showed the row 1.5 s after the check and cleared it on answer. An allowed 5 s `sleep`, a call a deny rule refused, an `AskUserQuestion` call and a subagent's dialog drew none. On 2.1.308, a 10 s Bash call that the auto-mode classifier approved drew none, and a `ToolUse` row's `isRunning` stayed false during a dialog and turned true when the tool started. Not checked live: the `ToolGroup` path (the types give `calls[].isRunning`, and a mocked render covers it), a classifier slower than the delay, auto mode on 2.1.312, and the desktop app. A `$.tool.check` query has no `tool_use_id`, so it never opens a row. Where `classic.PermissionRequest` runs, it is the only source. The stop row and a reply a Stop hook sent back to the agent still arrive, through events the guard passes. Where `classic.StopFailure` runs, it sets the stop row with Claude Code's error code. Where the guard skips it, `turn.complete` with reason `error` sets it from the error text the transcript ends on, so the kind comes from the text and the code reads `unknown` where the text names none. A reply sent back is the answer of a `turn.step` that ended with no tool call and was followed by another step in the same turn. | Same as terminal. | No guard in Codex. | The guard skips a user mod's `classic.*` hooks. `turn.step` and `turn.complete` pass. `tool.check` passes and carries the `ask` verdict, but it also fires when the auto-mode classifier then approves the call, so it does not show that a dialog opened. The plugin directory accepts a permission hook only when it returns `next(e)` itself or a fixed `deny` or `ask`, so the hook does not read the verdict `next` resolves to. | `hooks/register.tsx:on('classic.PermissionRequest')`, `hooks/register.tsx:on('tool.check')`, `hooks/register.tsx:waitForPermission`, `hooks/register.tsx:on('ui.render')` for `ToolUse` and `ToolGroup`, `hooks/view.ts:PERMISSION_FALLBACK_DELAY_MS`, `hooks/register.tsx:on('classic.StopFailure')`, `hooks/register.tsx:on('turn.step')`, `hooks/register.tsx:setStopFromLastReply`, `hooks/claude.ts:stopOfMessage` |
| Herdr sidebar (`herdr-sidebar`) | Inside a Herdr pane, each saved change reports the pane tokens, and the session's end clears them. | Same as terminal when the app has `HERDR_PANE_ID`. An app started outside Herdr does not. | A Codex CLI in a Herdr pane reports from its hooks and from the update a hook starts. Each report carries its write time as `--seq`, and Herdr drops a report whose `--seq` is not above the last one it took. A record or close the agent makes during a turn reaches the sidebar at the next hook. Codex finds no stops, and its tokens stay after the session ends. | Codex runs hooks with the CLI's environment, but its MCP server gets only the variables `.mcp.json` lists, and in the Codex app one server serves every chat. Codex has no hook for a session's end. | `hooks/herdr.ts:herdrTokens`, `hooks/register.tsx:publishStatus`, `codex/src/host.ts:herdrOnWrite`, `omp/src/host-sessions.ts:reportCounts` |
