# Differences on purpose: how each host runs

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |

| Desktop Codex connection (`codex-desktop-companion`) | Not applicable. | Not applicable. | An explicit chat allowlist exposes existing state and supported actions through a private local socket. | It uses Codex's saved chat files and running MCP host. Other hosts publish through Herdr; no second updater is introduced. | `codex/src/companion-listener.ts`, `codex/src/server-companion.ts` |
| Hot reload | Mod handlers reload. | Same as terminal. | The handler reloads. The tab stages a candidate before replacing its root, style and script. | Storage | An engine atom holds the drawn conversation's session. The engine store keeps each conversation's saved session, with at most `SAVED_PR_VIEWS_MAX` (75,000) characters of its PR views. The drawn session keeps every view. | Same as terminal. | One JSON file per session, under a lock, with every PR view. Its viewer leases go in a second file beside it, where the mod keeps them in memory. Its command log goes in a third file beside it, under its own lock. The mod keeps the log in the inbox's state folder. | Codex has no engine store. Its hooks run as separate short-lived processes beside the server, and each prunes the session with the leases. A session that loads reads the PRs it lacks from GitHub again. | `hooks/mod/mod-session-write.ts:changeSession`, `hooks/mod/mod-saves.ts:forStore`, `codex/src/lock.ts:withLock`, `codex/src/viewers.ts:codexViewerStore`, `core/runtime/command-store.ts:fileCommandStore` |
| Session registry pid (`session-registry`) | The entry's pid is the Claude Code process that runs the conversation, and the entry goes when the conversation ends. | Same as terminal. | Under the Codex app, every chat's entry carries the app server's pid, so a closed chat's entry reads as running until the app quits. | Tool fields after an update | Each conversation keeps the fields of its `record`, `close` and `order_prs` tools, saved with its session. | Band, stop and dialog rows (`band-and-stop-rows`) | Yes. The band shows from the session's start. | Yes. The band shows once the session's engine runs. A new session starts its engine at the first message, so the band shows then, before the reply. | No. | Codex has no line above its prompt. The desktop app runs no engine for a new session until its first message is sent, so nothing draws above that session's prompt before then. Seen on 2026-11-22 with engine 2.1.330. | `core/view/band.ts:bandCounts`, `core/view/band.ts:bandIdleText` |
| Go to inbox after the app hides the pane | The band reads "Go to inbox" from the time the engine draws the pane until it closes. Escape and the pane's close mark close it and raise `ui.close`. A press opens the pane with the keys. | The band keeps reading "Go to inbox" after the app's View > Hide Side Panel (⌘.) hides the pane. The app draws a pane it shows again well within 300 ms, and the press then only opens it, so the pane keeps its tab and scroll position. | PR data | The mod runs gh through the engine, on a timer while the person is around, and when a reply ends once `isPrFetchDue` says so. A Refresh PRs press or a fix press fetches after any fetch that is running. | Same as terminal. | The server runs gh through `deps.exec` in the session's folder, and refetches on a view when `isPrFetchDue` says so: the last fetch is over 2 minutes old, or over 15 seconds old and the agent replied since. A `record` or `order_prs` call that puts a PR on the tab fetches at once, as in the mod. A PR a reply or a command links waits for the next view, since the hook process saves it and the server hears no turn end. A Refresh PRs press or a fix press fetches after any fetch that is running. It tries `gh`, then the Homebrew folders. | The ChatGPT app may start the Codex server without Homebrew on its PATH. A Claude Code session, in the terminal or the Claude app, gets the login shell's PATH. | `hooks/mod/mod-prs.ts:fetchPrsNow`, `core/runtime/host-prs.ts:fetchPrs`, `core/runtime/host-prs.ts:prFetchTracker`, `core/domain/gh.ts:ghFinder` |
| Hooks need trust (`hooks-need-trust`) | None. Claude Code runs the mod's hooks without asking for trust. | Same as terminal. | While Codex does not run the inbox's hooks, every chat's Inbox tab shows an error banner under the tab bar, on every tab, saying why and naming the hook icon and Allow all, then Settings' Hooks page for when the icon is missing: "Codex is not running the inbox's hooks…" when Codex never trusted them, and "Codex stopped the inbox's hooks when the inbox updated…" when it trusted them before an update changed the plugin. The Asks tab's empty state then leaves its own hook text out. Otherwise, a chat that has heard from no hook reads "The inbox starts with your next message." The server asks `codex app-server` for `hooks/list` in the background, once per chat folder. It asks again every 5 seconds while Codex is not running the hooks, so the line leaves soon after the person trusts them, and 30 seconds after a failed answer. A trusted answer stands until a turn runs whose prompt and Stop the inbox did not hear, or until the server's handler reloads, as every plugin update makes it do. A missing, trusted or failed answer shows no line. Turns that ended while the hooks were off are caught up at the chat's next hook (see "Catch-up and a behind ledger"). | Codex binds each approval to every file in the plugin, so every update asks again, and until then the hooks fail. omp has no such approval either (see its table). | `codex/src/hook-trust.ts:trustOfHooks`, `codex/src/server-trust.ts:hooksTrustNow`, `codex/src/tab-chrome.tsx:TabBar`, `codex/src/history.ts:withMissedTurns` |
| Where the agent reads the guidance | In the description of the `close` tool, through `tool.describe`. | Same as terminal. | In the `SessionStart` hook's added context. | The guard Claude Code loads on Team and Enterprise sign-ins skips a user mod's `prompt.compose` hook and passes `tool.describe`. | Rows that need a hook the guard skips | Where the guard loads, the permission row comes from `tool.check` instead of `classic.PermissionRequest`. The hook returns `next(e)` as it received it, and a `$.tool.check` query of the same call gives the verdict. An `ask` opens the row only if the call has not been allowed after `PERMISSION_FALLBACK_DELAY_MS`, which is 1.5 s. In manual mode the row appears 1.5 s after the dialog. The row clears, and is never drawn, once `tool.run` fires for the call, matched by `tool_use_id`. The engine raises `tool.run` only for an allowed call, after whoever settled the ask, so it also clears a row `classic.PermissionRequest` opened. A refused call clears its row when the call ends. A `ToolUse` row's `isRunning` cannot stand in for `tool.run`: in the desktop app it is true while the dialog is open. The query asks no PreToolUse hook, so an ask that only a PreToolUse hook makes draws no row. These checks ran while the row still cleared on a `ToolUse` row's `isRunning`, not on `tool.run`. Checked live on Claude Code 2.1.312, with no guard, a stand-in model server, and a stand-in mod ahead of the inbox that answers `classic.PermissionRequest` without calling `next`. Manual mode showed the row 1.5 s after the check and cleared it on answer. An allowed 5 s `sleep`, a call a deny rule refused, an `AskUserQuestion` call and a subagent's dialog drew none. On 2.1.308, a 10 s Bash call that the auto-mode classifier approved drew none, and a `ToolUse` row's `isRunning` stayed false during a dialog and turned true when the tool started. In the desktop app, app 6.28899.6 with engine 2.1.330 and no guard, a real dialog in Manual mode showed the row while it was open and cleared it when allowed. On Claude Code 2.1.330 with the guard loaded on a Team sign-in, a probe mod in the user tier received `tool.run` in `claude -p` for a call a rule allowed, and for a call the auto-mode classifier allowed 0.5 s after `tool.check` answered `ask`. Not checked live: a classifier slower than the delay (which would show the row, and list it in the Asks tab, with no dialog on screen until the call runs), auto mode on 2.1.312, and the desktop app with the guard seated. A `$.tool.check` query has no `tool_use_id`, so it never opens a row. Where `classic.PermissionRequest` runs, it is the only source. The stop row and the text of each step still arrive, through events the guard passes. Where `classic.StopFailure` runs, it sets the stop row with Claude Code's error code. Where the guard skips it, `turn.complete` with reason `error` sets it from the error text the transcript ends on, so the kind comes from the text and the code reads `unknown` where the text names none. The turn's reply is the answer of each `turn.step`, in order, so it holds a reply a Stop hook sent back. | Same as terminal. | No guard in Codex. | The guard skips a user mod's `classic.*` hooks. `turn.step` and `turn.complete` pass. `tool.check` passes and carries the `ask` verdict, but it also fires when the auto-mode classifier then approves the call, so it does not show that a dialog opened. The plugin directory accepts a permission hook only when it returns `next(e)` itself or a fixed `deny` or `ask`, so the hook does not read the verdict `next` resolves to. | `hooks/register.tsx:on('classic.PermissionRequest')`, `hooks/register.tsx:on('tool.check')`, `hooks/mod/mod-dialogs.ts:waitForPermission`, `hooks/register.tsx:on('tool.run')`, `hooks/mod/mod-dialogs.ts:callAllowed`, `core/view/timing.ts:PERMISSION_FALLBACK_DELAY_MS`, `hooks/register.tsx:on('classic.StopFailure')`, `hooks/register.tsx:on('turn.step')`, `hooks/mod/mod-turns.ts:setStopFromLastReply`, `hooks/mod/claude.ts:stopOfMessage` |
