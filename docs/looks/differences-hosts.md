# Differences on purpose: how each host runs

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |
| --- | --- | --- | --- | --- | --- |
| Desktop Codex connection (`codex-desktop-companion`) | Not applicable. | Not applicable. | An explicit chat allowlist exposes existing state and supported actions through a private local socket. | It uses Codex's saved chat files and running MCP host. Other hosts publish through Herdr; no second updater is introduced. | `codex/src/companion-listener.ts`, `codex/src/server-companion.ts` |
| Hot reload | Mod handlers reload. | Same as terminal. | The handler reloads. The tab stages a candidate before replacing its root, style and script. Failed startup keeps the working page; successful replacement waits for active presses. The loader needs Codex restarted. | Each instance owns its timers, listeners and animations. Staging preserves the working UI and host state until the candidate can take over. | `codex/src/server-main.ts:load`, `codex/src/server-handler.ts:createHandler`, `codex/src/tab-swap.ts:swapPage`, `codex/src/tab-host.ts:dispose` |
| Storage | An engine atom holds the drawn conversation's session. The engine store keeps each conversation's saved session, with at most `SAVED_PR_VIEWS_MAX` (75,000) characters of its PR views. The drawn session keeps every view. | Same as terminal. | One JSON file per session, under a lock, with every PR view. Its viewer leases go in a second file beside it, where the mod keeps them in memory. Its command log goes in a third file beside it, under its own lock. The mod keeps the log in the inbox's state folder. | Codex has no engine store. Its hooks run as separate short-lived processes beside the server, and each prunes the session with the leases. Every Claude Code session's saves share one engine store, which Claude Code caps at 4 MiB of JSON, so each saved session keeps its PR views within a share of it. A session that loads reads the PRs it lacks from GitHub again. | `hooks/mod/mod-session-write.ts:changeSession`, `hooks/mod/mod-saves.ts:forStore`, `codex/src/lock.ts:withLock`, `codex/src/viewers.ts:codexViewerStore`, `core/runtime/command-store.ts:fileCommandStore` |
| Session registry pid (`session-registry`) | The entry's pid is the Claude Code process that runs the conversation, and the entry goes when the conversation ends. | Same as terminal. | Under the Codex app, every chat's entry carries the app server's pid, so a closed chat's entry reads as running until the app quits. A Codex CLI session gets its own process, so its entry reads as ended once the CLI exits. | Codex runs each chat's hooks and its tab server under the app server, and tells no hook when a chat closes. No process belongs to one chat in the app. | `codex/src/registry.ts:registryOnWrite`, `codex/src/cli.ts:ancestorCodex`, `core/runtime/session-registry.ts:writeRegistryEntry` |
| Model call failure record | `callFailures` keeps the last ledger and Status call failures, with `process: null` and the engine's `error` (such as `api-error 529: overloaded`). | Same as terminal. | `process` holds the failed `codex exec` exit code, signal, error code, timeout and stderr error/warning lines (omitting lines that can hold prompts or replies). | Codex spawns a process per model call; the mod and omp call in-process. | `core/runtime/call-record.ts:withCall`, `codex/src/update.ts:codexAsk` |
| Tool fields after an update | Each conversation keeps the fields of its `record`, `close` and `order_prs` tools, saved with its session. A conversation the inbox saw start gets this build's: one with no turns when the inbox loads it, or one `/clear` opens. A fork takes its parent's. Any other conversation with no saved fields gets 0.3.0's. | Same as terminal. | The server keeps the fields of the build that last answered `tools/list` since Codex opened, or 0.3.0's when none did. | Claude Code sends a resumed conversation's first tool schemas again, so each conversation can hold a different build's tools. One Codex server process answers `tools/list` for every chat. A tool answer asks only for fields the agent's tool has, and asks for less when the inbox cannot tell. | `hooks/mod/mod-sessions.ts:withLoadedToolFields`, `core/domain/tool-schemas.ts:sessionToolFields`, `codex/src/server-tools.ts:listedToolFields`, `core/domain/question-checks.ts:missingText` |
| Band, stop and dialog rows (`band-and-stop-rows`) | Yes. The band shows from the session's start. | Yes. The band shows once the session's engine runs. A new session starts its engine at the first message, so the band shows then, before the reply. | No. | Codex has no line above its prompt. The desktop app runs no engine for a new session until its first message is sent, so nothing draws above that session's prompt before then. Seen on 2026-11-22 with engine 2.1.330. | `core/view/band.ts:bandCounts`, `core/view/band.ts:bandIdleText` |
| Remote Resume (`remote-resume`) | Yes. | Yes. | No. | Codex lacks stopped-turn state. | `core/runtime/session-presses.ts:pressOn` |
| Go to inbox after the app hides the pane | The band reads "Go to inbox" from the time the engine draws the pane until it closes. Escape and the pane's close mark close it and raise `ui.close`. A press opens the pane with the keys. | The band keeps reading "Go to inbox" after the app's View > Hide Side Panel (⌘.) hides the pane. A press on the desktop band, and `/inbox` when only the desktop app draws the pane, first ask for a redraw. The app draws a pane it shows again well within 300 ms, and the press then only opens it, so the pane keeps its tab and scroll position. When no drawing comes within 300 ms, the press closes the pane and opens it again, which shows it. The controller does not hear that close, so the tab, held rows and reply drafts stay. The pane comes back scrolled to the top, as the app's own Show Side Panel brings it back. After that close, or Escape's, the pane draws a copy of each new `Client` with its own elements: the tab row, closed rows, open row titles, fold lines, links and Status parents. Each `Client` lies over its copy and draws itself there, and its first post drops the copy. So they all come with the pane's first drawing (#785). For about a frame the copy and the `Client` draw the same text in the same place, which looks bolder. A row dismissed while open on the shown tab keeps its title and links `Client`s drawn at zero height while it waits on Undo and comes back, so the open row shows them again with no copy (#801). Switching tabs drops them. A press before the `Client` draws lands on the copy and does nothing. One or two blank frames still come before the pane's first drawing, from the app. After the app's own Show Side Panel, the mod cannot tell its `Client`s are new, and they still come after the rest of the pane. | No band. | Hide Side Panel raises no `ui.close` and no render, `ui.panes` still reads the pane shown and focused, and `ui.open` returns `isPlaced: true` but leaves it hidden. Only a close then an open shows it again. Seen on 2026-11-22 with a probe mod in the Claude app. While the pane is hidden, a redraw draws nothing and a `Client`'s timers stop. Seen on 2026-11-23. A pane shown again gets new `Client`s, which the app drew 20 to 580 ms after the pane's own elements (#765, #785). The app can also show a `Client`'s new props a frame after the pane's own elements change, seen on 2026-11-23. So each `Client` draws from its first render and does not wait for its props. The blank frames come after the mod has returned the pane's drawing. In two runs on 2026-11-23, the mod returned it 81 and 361 ms after the press. The app showed its own panel until 84 and 400 ms, a blank pane at 117 and 426 ms, and the drawing at 165 and 457 ms. | `hooks/mod/mod-pane-open.ts:openInbox`, `hooks/mod/mod-pane-open.ts:showInbox`, `hooks/mod/mod-pane-open.ts:showAgainIfHidden`, `hooks/register.tsx:on('ui.close')`, `hooks/pane/tabs-client.tsx:tabsTree`, `hooks/pane/client-copy.tsx:withCopy`, `hooks/pane/held-clients.tsx:heldClients`, `hooks/pane/pane-row-clients.tsx`, `hooks/mod/mod-pane-events.ts:paneMessaged` |
| PR data | The mod runs gh through the engine, on a timer while the person is around, and when a reply ends once `isPrFetchDue` says so. A Refresh PRs press or a fix press fetches after any fetch that is running. | Same as terminal. | The server runs gh through `deps.exec` in the session's folder, and refetches on a view when `isPrFetchDue` says so: the last fetch is over 2 minutes old, or over 15 seconds old and the agent replied since. A `record` or `order_prs` call that puts a PR on the tab fetches at once, as in the mod. In a Herdr app terminal, the server also watches the saved sessions this terminal publishes. It fetches at once when a save shows a PR on the tab that no fetch has tried, such as a PR the hook linked for a reply or a command (`codex/src/server-pr-links.ts:linkedPrReads`). Elsewhere such a PR waits for the next view of the Codex tab, which then reads it. A Refresh PRs press or a fix press fetches after any fetch that is running. It tries `gh`, then the Homebrew folders. | The ChatGPT app may start the Codex server without Homebrew on its PATH. A Claude Code session, in the terminal or the Claude app, gets the login shell's PATH. | `hooks/mod/mod-prs.ts:fetchPrsNow`, `core/runtime/host-prs.ts:fetchPrs`, `core/runtime/host-prs.ts:prFetchTracker`, `core/domain/gh.ts:ghFinder` |
| Where the agent reads the guidance | In the description of the `close` tool, through `tool.describe`. | Same as terminal. | In the `SessionStart` hook's added context. | The guard Claude Code loads on Team and Enterprise sign-ins skips a user mod's `prompt.compose` hook and passes `tool.describe`. Claude Code sends a pinned tool's first 4096 characters, and `record`'s own description leaves too little room, so `close` carries it. The Codex and omp agents read the shared tool descriptions too, so the guidance is not in `core/runtime/tools.ts`. omp adds it to its system prompt. | `hooks/register.tsx:on('tool.describe')`, `core/domain/model-text.ts:guidedCloseDescription`, `codex/src/hook.ts`, `omp/src/host.ts:on('before_agent_start')` |
| Carried state at a conversation's first prompt | The Status's head, as "Working on: title: description", and where each open subject stands, in the first prompt's added context from `prompt.submit`. The `inbox:` text beside that prompt lists the open items and the closed ones. | Same as terminal. | `startContext` gives the head and the open subjects, the open items, the findings and the closed ones in the `SessionStart` context. omp adds only the guidance to the system prompt, in `before_agent_start`, and no state. | The guard skips a user mod's `prompt.context` hook and passes `prompt.submit`. Codex and omp have no `inbox:` text before their first prompt. | `hooks/register.tsx:on('prompt.submit')`, `core/domain/inbox-text.ts:statusCarryText`, `core/runtime/session-turns.ts:startContext` |
| Reload after /clear, /resume and /branch | `classic.SessionStart` reloads at once. | Code Mode | From Claude Code 2.1.327, Claude Code's experimental Code Mode (`CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`) starts with the inbox loaded. Through 2.1.326 it refused to start. | Not applicable. Code Mode runs only in the interactive terminal. | Not applicable. | The 2.1.327 changelog says: "Changed Code Mode to no longer refuse to start when an installed mod hooks tool calls; an administrator can still keep Code Mode off in managed settings". Through 2.1.326, Claude Code scanned each mod's source for tool-call hooks and refused Code Mode if it found any. The inbox hooks `tool.call` to answer its own `record`, `close` and `order_prs` tools. The 2.1.326 changelog also says: "Fixed mods being unable to use Bash, Read and other tools through `$.tool.call` and `$.tool.check` in Code Mode". Code Mode also refuses to start when `ANTHROPIC_BASE_URL` names an address other than Anthropic's, and when the organization's policy cannot be read, so a check needs a real sign-in. That the desktop app cannot run Code Mode is read from the 2.1.329 binary, not checked live. Checked live on 2026-11-20 in Claude Code 2.1.329 on a Team sign-in. The session ran in tmux with its own `CLAUDE_CONFIG_DIR` and `XDG_STATE_HOME`. The inbox loaded from a working copy, and `HC_TERMINAL_ID` and `HERDR_APP_HOME` were unset. The first start asked once to turn on Code Mode. After that, `/status` read "Code Mode: on (experimental)" and the band drew. A Haiku 5.5 turn called `record`, the `tool.call` hook answered it, and the band showed "Asks 1". `/status` listed only user settings. Code Mode stayed on, so the organization's policy was read without turning it off. Not checked: the `tool.check` permission row, the activity lines from calls that ran, and a session where managed settings turn Code Mode off. Issue #507 records the earlier refusal. | `hooks/register.tsx:on('tool.call')`, `hooks/register.tsx:on('tool.check')`, `hooks/register.tsx:on('classic.PermissionRequest')` |
