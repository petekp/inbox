# Differences on purpose: how each host runs

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |
| --- | --- | --- | --- | --- | --- |
| Hot reload | Mod handlers reload. | Same as terminal. | The handler reloads. The tab stages a candidate before replacing its root, style and script. Failed startup keeps the working page; successful replacement waits for active presses. The loader needs Codex restarted. | Each instance owns its timers, listeners and animations. Staging preserves the working UI and host state until the candidate can take over. | `codex/src/server-main.ts:load`, `codex/src/server-handler.ts:createHandler`, `codex/src/tab-swap.ts:swapPage`, `codex/src/tab-host.ts:dispose` |
| Storage | An engine atom holds the drawn conversation's session. The engine store keeps each conversation's saved session, with at most `SAVED_PR_VIEWS_MAX` (75,000) characters of its PR views. The drawn session keeps every view. | Same as terminal. | One JSON file per session, under a lock, with every PR view. | Codex has no engine store. Its hooks run as separate short-lived processes beside the server. Every Claude Code session's saves share one engine store, which Claude Code caps at 4 MiB of JSON, so each saved session keeps its PR views within a share of it. A session that loads reads the PRs it lacks from GitHub again. | `hooks/register.tsx:changeSession`, `hooks/mod-saves.ts:forStore`, `codex/src/state.ts:withLock` |
| Model call failure record | `callFailures` keeps the last failure of the ledger call and of the Status call, and each failure's `process` is null. An `error` holds the engine's reason, such as `api-error 529: overloaded`. | Same as terminal. | `process` holds the failed `codex exec` call: its exit code, signal, error code, timeout and the error and warning lines of its stderr. The other lines can hold the prompt and the model's reply, so they are left out. | Codex runs each model call as a separate process. The mod and omp call the model in their own process, so they have no process to describe. | `hooks/call-record.ts:withCall`, `codex/src/update.ts:codexAsk` |
| Band, stop and dialog rows (`band-and-stop-rows`) | Yes. | Yes. | No. | Codex has no line above its prompt. | `hooks/band.ts:bandCounts`, `hooks/band.ts:noCountsText` |
| PR data | The mod runs gh through the engine, on a timer while the person is around, and when a reply ends once `isPrFetchDue` says so. A Refresh PRs press or a fix press fetches after any fetch that is running. | Same as terminal. | The server runs gh through `deps.exec` in the session's folder, and refetches on a view when `isPrFetchDue` says so: the last fetch is over 2 minutes old, or over 15 seconds old and the agent replied since. A Refresh PRs press or a fix press fetches after any fetch that is running. It tries `gh`, then the Homebrew folders. | The ChatGPT app may start the Codex server without Homebrew on its PATH. A Claude Code session, in the terminal or the Claude app, gets the login shell's PATH. | `hooks/register.tsx:fetchPrsNow`, `hooks/host-prs.ts:fetchPrs`, `hooks/host-prs.ts:prFetchTracker`, `hooks/gh.ts:ghFinder` |
| Hooks need trust (`hooks-need-trust`) | None. Claude Code runs the mod's hooks without asking for trust. | Same as terminal. | While Codex does not run the inbox's hooks, every chat's Inbox tab shows an error banner under the tab bar, on every tab, saying why and naming the hook icon and Allow all, then Settings' Hooks page for when the icon is missing: "Codex is not running the inbox's hooks…" when Codex never trusted them, and "Codex stopped the inbox's hooks when the inbox updated…" when it trusted them before an update changed the plugin. The Asks tab's empty state then leaves its own hook text out. Otherwise, a chat that has heard from no hook reads "The inbox starts with your next message." The server asks `codex app-server` for `hooks/list` in the background, once per chat folder. It asks again every 5 seconds while Codex is not running the hooks, so the line leaves soon after the person trusts them, and 30 seconds after a failed answer. A trusted answer stands until a turn runs whose prompt and Stop the inbox did not hear, or until the server's handler reloads, as every plugin update makes it do. A missing, trusted or failed answer shows no line. Turns that ended while the hooks were off are caught up at the chat's next hook (see "Catch-up and a behind ledger"). | Codex binds each approval to every file in the plugin, so every update asks again, and until then the hooks fail. omp has no such approval either (see its table). | `codex/src/hook-trust.ts:trustOfHooks`, `codex/src/server-trust.ts:hooksTrustNow`, `codex/src/tab-chrome.tsx:TabBar`, `codex/src/history.ts:withMissedTurns` |
| Where the agent reads the guidance | In the description of the `close` tool, through `tool.describe`. | Same as terminal. | In the `SessionStart` hook's added context. | The guard Claude Code loads on Team and Enterprise sign-ins skips a user mod's `prompt.compose` hook and passes `tool.describe`. Claude Code sends a pinned tool's first 4096 characters, and `record`'s own description leaves too little room, so `close` carries it. The Codex and omp agents read the shared tool descriptions too, so the guidance is not in `hooks/tools.ts`. omp adds it to its system prompt. | `hooks/register.tsx:on('tool.describe')`, `hooks/model-text.ts:guidedCloseDescription`, `codex/src/hook.ts`, `omp/src/host.ts:on('before_agent_start')` |
| Carried state at a conversation's first prompt | The Status's head, as "Working on: title: description", and where each open subject stands, in the first prompt's added context from `prompt.submit`. The `inbox:` text beside that prompt lists the open items and the closed ones. | Same as terminal. | `startContext` gives the head and the open subjects, the open items, the findings and the closed ones in the `SessionStart` context. omp adds only the guidance to the system prompt, in `before_agent_start`, and no state. | The guard skips a user mod's `prompt.context` hook and passes `prompt.submit`. The mod's `inbox:` text already lists the items, so repeating them would duplicate them. Codex and omp have no `inbox:` text before their first prompt. | `hooks/register.tsx:on('prompt.submit')`, `hooks/inbox-text.ts:statusCarryText`, `hooks/session-turns.ts:startContext` |
| Reload after /clear, /resume and /branch | `classic.SessionStart` reloads at once. Where the guard skips it, the first prompt after the switch reloads, and the pane shows the old state until then. | Same as terminal. | A new session id loads when its hook runs. | The guard skips `classic.*`. `session.start` and `session.attach` do not fire on these switches, and the first prompt is the first event that carries the new id. | `hooks/register.tsx:on('prompt.submit')`, `hooks/register.tsx:on('classic.SessionStart')` |
| Rows that need a hook the guard skips | Where the guard loads, the permission row comes from `tool.check` instead of `classic.PermissionRequest`. The hook returns `next(e)` as it received it, and a `$.tool.check` query of the same call gives the verdict. An `ask` opens the row only if the call has not run after `PERMISSION_FALLBACK_DELAY_MS`, which is 1.5 s, and the row clears when the call ends. In manual mode the row appears 1.5 s after the dialog. The row also clears, and is never drawn, once the call's `ToolUse` row reports `isRunning`, or once its entry in a collapsed `ToolGroup` does, matched by `tool_use_id`. The query asks no PreToolUse hook, so an ask that only a PreToolUse hook makes draws no row. Checked live on Claude Code 2.1.312, with no guard, a stand-in model server, and a stand-in mod ahead of the inbox that answers `classic.PermissionRequest` without calling `next`. Manual mode showed the row 1.5 s after the check and cleared it on answer. An allowed 5 s `sleep`, a call a deny rule refused, an `AskUserQuestion` call and a subagent's dialog drew none. On 2.1.308, a 10 s Bash call that the auto-mode classifier approved drew none, and a `ToolUse` row's `isRunning` stayed false during a dialog and turned true when the tool started. Not checked live: the `ToolGroup` path (the types give `calls[].isRunning`, and a mocked render covers it), a classifier slower than the delay, auto mode on 2.1.312, and the desktop app. A `$.tool.check` query has no `tool_use_id`, so it never opens a row. Where `classic.PermissionRequest` runs, it is the only source. The stop row and the text of each step still arrive, through events the guard passes. Where `classic.StopFailure` runs, it sets the stop row with Claude Code's error code. Where the guard skips it, `turn.complete` with reason `error` sets it from the error text the transcript ends on, so the kind comes from the text and the code reads `unknown` where the text names none. The turn's reply is the answer of each `turn.step`, in order, so it holds a reply a Stop hook sent back. | Same as terminal. | No guard in Codex. | The guard skips a user mod's `classic.*` hooks. `turn.step` and `turn.complete` pass. `tool.check` passes and carries the `ask` verdict, but it also fires when the auto-mode classifier then approves the call, so it does not show that a dialog opened. The plugin directory accepts a permission hook only when it returns `next(e)` itself or a fixed `deny` or `ask`, so the hook does not read the verdict `next` resolves to. | `hooks/register.tsx:on('classic.PermissionRequest')`, `hooks/register.tsx:on('tool.check')`, `hooks/register.tsx:waitForPermission`, `hooks/register.tsx:on('ui.render')` for `ToolUse` and `ToolGroup`, `hooks/timing.ts:PERMISSION_FALLBACK_DELAY_MS`, `hooks/register.tsx:on('classic.StopFailure')`, `hooks/register.tsx:on('turn.step')`, `hooks/register.tsx:setStopFromLastReply`, `hooks/claude.ts:stopOfMessage` |
| Herdr sidebar (`herdr-sidebar`) | Inside a pane of Herdr's terminal multiplexer, each saved change reports the pane tokens with `herdr pane report-metadata`. Inside a Herdr app terminal, it sets the same values as `inbox.` labels on the terminal with one `hc label` call, with `inbox.session` naming the session, and tries `hc` on `PATH`, then `~/.local/bin/hc`. The session's end clears them. When a report fails, the next change sends it again. A timer also retries it after each wait in `HERDR_RETRY_MS`, and stops once Herdr takes a report. Herdr's app does not draw the labels in its sidebar yet. | Same as terminal when the app has `HERDR_PANE_ID` or `HC_TERMINAL_ID`. An app started outside Herdr has neither. | A Codex CLI in Herdr reports from its hooks and from the update a hook starts. Each report runs under the session's Herdr lock and reads the newest saved state, so reports from these processes go out in the order they run. A pane report carries the state's `writtenAt` as `--seq`, and Herdr drops one whose `--seq` is not above the last one it took. Each change a hook or an update makes sets `writtenAt` under the session's lock, always above the one before it, even when nothing else changed. A report that fails is not saved, so the next hook or update sends it again. No timer retries it. A record or close the agent makes during a turn reaches the sidebar at the next hook. Codex finds no stops, and its tokens and labels stay after the session ends. | Codex runs hooks with the CLI's environment, but its MCP server gets only the variables `.mcp.json` lists, and in the Codex app one server serves every chat. Codex has no hook for a session's end. A hook or update process exits when its work ends, so it cannot hold a retry timer. `hc label` takes no sequence number, so only the lock orders reports from separate processes. | `hooks/herdr.ts:herdrTokens`, `hooks/herdr.ts:herdrTarget`, `hooks/herdr.ts:herdrReporter`, `hooks/mod-herdr.ts:publishToHerdr`, `codex/src/host.ts:herdrOnWrite`, `omp/src/host-sessions.ts:reportCounts` |
| Session published for the Herdr look, and its presses (`herdr-look`) | In a Herdr app terminal, each saved change publishes the session to `<app home>/inbox/sessions/<session id>.json`, where the app home is `HERDR_APP_HOME` or `~/.config/herdr-app`. It writes a temporary file and moves it over the old one, in the same turn as the label report and before it. Over 1 MiB it leaves out the closed items the view does not show and sets `trimmed: true`. The session's end removes the file. The mod applies the presses the look writes to `<app home>/inbox/presses/<session id>/`. It reads that folder at start, when the terminal's `inbox.press` label changes, which it follows with `hc events`, and every 10 seconds. A press with `result` records that outcome and does not open or copy again. After each press, the published file names it in `lastPress`, with `stale` when its row had already changed. | Same as terminal when the app has `HC_TERMINAL_ID`, except that omp watches the shown session's press folder with `fs.watch` instead of following the label. | Each hook, each update and the MCP server publish under the session's Herdr lock, from the newest saved state, with the state's `writtenAt`. The MCP server watches the whole presses folder and applies the presses of each session whose published file names Codex and this terminal. The file stays after the session ends. | Codex's MCP server cannot tell which session it serves until a tool call names one. Codex has no hook for a session's end. omp and Codex run in long-lived processes that can watch a folder, and the mod cannot. | `hooks/herdr-app.ts:publishSession`, `hooks/herdr-app.ts:pressDrainer`, `hooks/herdr.ts:herdrEnvelope`, `hooks/herdr-app.ts:applyLookPress`, `hooks/mod-herdr.ts:publishToHerdr`, `hooks/mod-herdr.ts:listenForHerdrPresses`, `codex/src/host.ts:herdrOnWrite`, `codex/src/server-herdr.ts:followCodexPresses`, `omp/src/host-sessions.ts:reportCounts`, `omp/src/host-presses.ts:ompPresses` |
| Opening the Herdr look (`herdr-open`) | In a Herdr app terminal, `/inbox` and the band's Open inbox press open the Herdr look in a pane to the right of the terminal, and the inbox pane stays closed. The mod finds the terminal's pane in `herdr-app ls` and runs `herdr-app do pane.split` with `direction: right` and `mod: inbox`. It tries `herdr-app` on `PATH`, then `~/.local/bin/herdr-app`. After a split it sets the terminal's `inbox.panel` label to the new pane. The next open, from this host or another in the terminal, runs `pane.focus` on that pane: exit 0 focuses it, `no such pane` splits again, and any other failure says the inbox is already open. Two opens at once share one split. When the app home has no `mods/inbox/main.js`, no `herdr-app` starts, `ls` lists no pane for the terminal, or the split fails, the mod opens the inbox pane. A split that prints no pane or times out may still have opened one, and the line says so. `/inbox` says why in its reply line, and the band press writes why to the debug log. The mod reads whether the app home has the inbox mod as it publishes, so a press without it opens the inbox pane at once. A band press whose split fails opens the pane after the `herdr-app` calls, so below 144 columns, once the person has closed the pane, the engine can leave it unplaced. `/inbox` with any argument, and any open while a demo is on, stays in the inbox pane. A `herdr-app` that hangs holds an open for up to three 5 s calls. Outside an app terminal nothing new runs. | Same as terminal when the app has `HC_TERMINAL_ID`. An app started outside Herdr has none. | None. | The Codex CLI has no action that opens the inbox: a Codex plugin adds skills, MCP servers and hooks but no slash command, and the Inbox tab shows only in the Codex app. A `$inbox` skill that has the model call an MCP tool could open the look, but only after a model turn, so the press could not show what it did at once. It stays an option. `herdr-app ls` lists terminals and not mod panes, so a host finds the panel only through the `inbox.panel` label or the pane it remembers. The band has no line for a note. | `hooks/herdr-open.ts:herdrPanelOpener`, `hooks/mod-herdr.ts:openInHerdr`, `hooks/register.tsx:openInbox`, `hooks/register.tsx:on('command.run')`, `omp/src/host.ts:createInbox` |
| Installing and updating the Herdr mod (`herdr-install`) | Once at turn-on in a Herdr app terminal, the mod compares the build time on the second line of its own `herdr/mod/inbox/main.js` with the one in `<app home>/mods/inbox/main.js`, and replaces an older inbox build. It writes the new files to a temporary folder under `<app home>/inbox/` and moves them over the old ones, `main.js` last, so Herdr reloads the mod in place. A missing mod is installed only after a yes saved in `<app home>/inbox/herdr-mod.json`, which every host reads. After the install the answer reads `installed`, so a mod the person removes stays removed. A `mods/inbox` that is a link, or that holds no inbox build, is the person's own and is never written. The same start removes each published session file, with its press folder, that no live terminal's `inbox.session` label names and that was written over a day ago. It reads the labels with one `terminal.list` call through `hc connect`. Each outcome and failure goes to the debug log. The install question has no form yet. | Same as terminal when the app has `HC_TERMINAL_ID`. omp does it at its first `session_start`, from the copy in `omp/dist/herdr-mod/`. | The MCP server does it each time its handler loads, from the copy in `codex/plugin/dist/herdr-mod/`, and it never asks. | The Codex CLI shows no inbox where the question could show: a Codex plugin adds no slash command, and the Inbox tab shows only in the Codex app. Codex and omp install only their own folders, so `herdr/build.ts` writes a copy of the mod into each. A reinstall loads the handler again with the newer copy beside it, so Codex updates then. | `hooks/herdr-install.ts:keepHerdrModCurrent`, `hooks/herdr-install.ts:answerHerdrMod`, `hooks/herdr-sweep.ts:sweepPublished`, `hooks/herdr-sweep.ts:labelledSessions`, `hooks/herdr-start.ts:startInHerdrApp`, `hooks/mod-herdr.ts:startInHerdr`, `codex/src/server-herdr.ts:startCodexInHerdrApp`, `omp/src/host-presses.ts:startOmpInHerdrApp`, `herdr/build.ts` |
