# Owners: the Status page

Part of [the look map](../looks.md#who-owns-each-rule).

| Rule | Owner | Read by |
| --- | --- | --- |
| The order of Status rows: the rows that changed since the last look above the Seen line, and on each side of it ◆, ● and ◐, ◌, ○, then ✓ and ✗ together, each group newest change first | `hooks/status-page.ts:STATUS_PLACES`, `hooks/status-page.ts:statusPage` | All four looks draw `StatusPage.rows` in order. |
| The "N more" fold: which open subjects the Status draws, and which fold into one row | `hooks/status-page.ts:statusPage` draws at most `hooks/status-limits.ts:OPEN_SUBJECTS` open subjects, the number the Status call is told to keep. It folds the rest into "○ N more", taking the rows it would draw last: queued ones first, then those that wait on others, then working ones. Three kinds of subject never fold, so more can show: one an open ask holds up, one that changed since the last look, and one with a child row under it. A page the person has never looked at folds nothing. The fold's mark is always ○. | All four looks draw the `fold` row's mark, tone and text, as they draw "✓ N done". |
| Status row lines and tree: how many lines each text on a row wraps to before a look cuts it with an ellipsis, which rows hang under a subject, and which is last | `hooks/status-page.ts:STATUS_TEXT_LINES` is the line limit. `hooks/status-page.ts:statusPage` sets `branch` on child and more rows, and `hasChildren` on subject rows. A child row with no `branch` is linked to no subject the list shows, and sits at the top. | All four looks. Each wraps in its own units, and cuts with `hooks/text.ts:cutForEllipsis`, except Codex: the terminal through `hooks/terminal-text.ts:terminalSpanLines`, desktop through `hooks/terminal-text.ts:desktopSpanLines`, Codex with `-webkit-line-clamp`, and omp through `omp/src/panel-page.ts:pageLine`. Each draws the tree line its own way: see "Tree lines on the Status" in Differences on purpose. |
| Where an Status row stands, its stall word, and its merged line | `hooks/status-page.ts:statusPage` sets `stall` on subject and child rows, as text and a tone. A subject that an open ask holds up reads "waiting" in the needs-you tone. A subject that waits on someone else shows no word. `hooks/status-page.ts:childStall` writes a child's stall word from the state `hooks/children.ts:delegatesSettled` takes from Herdr: "waiting" in the needs-you tone for a blocked delegate, and "finished" in the done tone. Other children show none, and no row shows a time. A stall word's tone is always needs-you or done. `hooks/status-page.ts:mergedLine` writes "merged in:" and the names of the subjects dropped into a subject, cut to one line at a phrase by `hooks/text.ts:cutAtPhrase`. | All four looks. Each draws a row's name, then `STALL_GAP` and the stall word in its tone. A wrap never splits the name's last word, the gap and the stall word, so the word always shares a line with the name. When the row runs past its lines, `hooks/status-page.ts:nameBeforeStall` cuts the name at a word, and the stall word stays whole. A subject then draws where it stands, muted, then the merged line, then the was line. Each look passes `mergedLine` its own width test. Codex measures the merged line in a canvas, and counts the name line's lines as the browser lays them out. |
| Rules between Status rows: which rows a rule sets apart | `hooks/status-page.ts:statusPage` sets `StatusRow.isRuledAbove`. A subject and the rows under it are one item, and no rule sits beside the Seen line. | All four looks. Each draws the rule its own way: see "Rules between Status rows" in Differences on purpose. |
| The Seen line's dashes, and the space above it and, unless it ends the list, below it | `hooks/status-page.ts:LOOK_DASH`, `hooks/layout.ts:LOOK_GAP_PT`. `hooks/status-page.ts:statusPage` sets `StatusRow.isLast`. | All four looks. Each draws them its own way: see "The Seen line" in Differences on purpose. |
| Running marks: which Status rows run, which result marks run, and how fast a mark moves | `hooks/status-page.ts:statusPage` sets `StatusRow.isRunning` on subject and child rows, and a child row's `mark` and `tone`: ◆ in the needs-you tone for a delegate that waits, and ✓ in the done tone for one that finished. `ResultMark.isRunning` says a row's result mark runs. `hooks/timing.ts:hasRunningMark`, `hooks/arrivals.ts:isRowTabRunning` and `hooks/pr-rows.ts:isPrTabRunning` say whether a tab draws one, and `hooks/session-view.ts:showsRunningMark` picks the one for the shown tab. `PrRowMark.isRunning` says a PR thread's mark runs. `hooks/timing.ts:runningMark`, `hooks/timing.ts:RUNNING_FRAME_MS`, `hooks/timing.ts:RUNNING_PULSE_MS` | All four looks read `isRunning`. The terminal and omp start their timer from `showsRunningMark`: `hasRunningMark` on the Status, `isRowTabRunning` on the Asks and Finds tabs, `isPrTabRunning` on the PRs tab, and always while Help shows, since the legend's first mark runs. They draw `runningMark` each `RUNNING_FRAME_MS`. Desktop and Codex fade the mark once each `RUNNING_PULSE_MS`. A Talk press, such as Explaining…, reads its label and runs no mark. |
| Asks that hold up a subject on the Status | `hooks/status-ops.ts:applyOps` saves `Status.askSubjects` from the Status call's LINK lines that name an open item. `hooks/status-page.ts:statusPage` draws ◆ in the `needsYou` tone on an open subject while an open item links to it, in place of its status's mark. That subject never folds into "N more", and its mark does not run. | All four looks draw the row's `mark` and `tone`. |
| Buttons on an Status row: View question or View task, on a subject an open ask holds up. It opens Asks with the oldest of those asks selected, takes its label from that ask's kind, and sends nothing. j and k move between the rows that have buttons, and only the selected row's keys work. | `hooks/action-plan.ts:statusKeyPlan`, `hooks/action-plan.ts:statusKeyRows`, `hooks/action-plan.ts:statusSelected`. `hooks/action-plan.ts:VIEW_ASK_LABELS`. `hooks/status-page.ts:statusPage` sets the subject row's `ask`. | All four looks draw the plan's buttons under the row's text, in the plan's order. The terminal draws them as a key row, marks the selected row the way a row tab does, and shows the key only on that row's button. Desktop draws native Buttons. Codex draws `.key` buttons that take clicks (see `status-view-ask` in Differences on purpose). omp draws the selected row's button focused, so Enter or its key presses it, and scrolls the page to the row j or k selects. omp holds the opened ask's buttons for `PRESS_GUARD_MS`, as the terminal and Codex do, so a second Enter does not press its recommended option. Each look runs the press itself: `hooks/register.tsx:showAsk`, `codex/src/tab-status.tsx:showAsk` and `omp/src/panel-keys.ts:pageKey`. |
| The "Holds up" line on an Asks row | `hooks/view.ts:inboxView` sets `RowView.holdsUpLine`, "Holds up" and the subject's name, on an open item that the Status call linked to an open subject. `hooks/help.ts:HELD_MARK` is the ◆ it starts with, the held subject's mark on the Status. | All four looks draw it on a next build only, since only a next build draws the Status. It is muted, under the title, in the collapsed and the selected row, after ◆ in the needs-you tone. The row Client draws the ◆ from its `noteMark`. The terminal draws it in `hooks/register.tsx:unselectedLine` and as the row's subtitle. Desktop draws it as the row Client's `note` (`hooks/row-client.tsx`) and as the subtitle. Codex draws it as `.holds-up` in `codex/src/tab-list.tsx`, and omp under the title line in `omp/src/panel-draw.ts:drawLine`. |
| Status-failed warning (`status-failed-warning`) | `hooks/session-host.ts:runUpdates`, `hooks/session-status.ts:failedStatus`, `hooks/status-page.ts:statusPage`, `hooks/view.ts:footerStatus` | Every host. A Status call that gives no answer, or answers with prose twice, saves `overviewFailure`: its time, its cause, and the start of a refused answer. The Status tab's status line then reads "Last Status update failed. Changes from that reply may be missing." in place of the update-failed warning, until a later Status call writes. The line stays while that call runs. |
| Status refresh during a long turn (`status-mid-turn-refresh`) | `hooks/session-status.ts:claimedStatusRefresh`, `hooks/status-records.ts:refreshStatus`, `hooks/status-prompt.ts:statusMidTurnPrompt` | Every host. The main agent's next tool call after `STATUS_REFRESH_MS` has passed since the turn started and since the last Status call claims a Status call, in the same write that notes the activity, so two calls in a row claim it once. The mod and omp note a call's activity when the call ends, and only for a call that ran (`ran-call-activity`), so a call claims the Status call when it ends. The call reads what the person sent and the turn's activity so far, with no reply, and runs after the session's earlier Status calls. A subagent's tool calls claim none, since the call reads only the main agent's activity. An idle session makes no call. The mod claims in `hooks/register.tsx:noteActivity` and omp in `omp/src/host-activity.ts:noteQuietly`, and each runs the call in its own process. Codex claims in its `PreToolUse` hook and starts a detached update process in its `status-refresh` mode (`codex/src/update-main.ts`), since a hook process ends before a model call would. |
| Status call records (`status-call-records`) | `hooks/status-records.ts:StatusRecord`, `hooks/status-records.ts:writeStatusRecord`, `hooks/status-records.ts:askAndWriteStatus` | Every host, on a next build only. A release build passes no `records` and keeps none. Each Status call, after a reply, during a long turn or after a catch-up, gets a record once its answer is written. The record is one JSON line in a file of its own, named by the call's start time and kind. It holds the session and time, the exact system text and prompt, and what the prompt was built from as data: the Status the call read with its children, the open asks, the task list, and the exchange, which also says the kind. `hooks/status-records.ts:statusCallPrompt` builds the prompt from that data, so a record can be replayed against a changed prompt. It also holds each answer or error with the model asked for and how long it took, whether the answer parsed, and the saved Status just before and after. The write runs in the background, and a failed write is dropped. A session keeps its newest `RECORDS_PER_SESSION` records, and its records are dropped `RECORDS_KEPT_MS` after its last call. The mod keeps them in `<Claude Code config folder>/plugins/data/inbox/overview-calls/<session>/`. It removes files with `rm` and `rmdir`, since the engine has no call that removes a file. Codex keeps them in its plugin data folder, as `~/.codex/plugins/data/inbox-inbox/overview-calls/<session>/`, and omp in `~/.omp/agent/inbox/overview-calls/<session>/`. omp names the model that answered when its reply's `upstreamModel` says, as a router's or a signed thinking block's model. The mod's engine and `codex exec` never say. `scripts/status-call.sh` prints a record, and with `--run` sends its prompt once more. |
