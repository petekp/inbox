# Differences on purpose: keys, clicks and replies

Part of [the look map](../looks.md#differences-on-purpose).

| Topic | Terminal | Desktop | Codex | Why | Where |
| --- | --- | --- | --- | --- | --- |
| Keys | Button hotkeys work. The key letter is drawn before the label. | Clicks only. Button hotkeys do nothing, and no letter is drawn. | A page `keydown` handler takes the letters. No key text is drawn. | The desktop pane takes no key input. A browser page can, but keys are an extra there. | `hooks/pane-row-keys.tsx:keyedButton`, `codex/src/tab-parts.tsx:KeyButton` |
| Help (`help-page`) | A "Help" button at the footer's left opens it, and reads "✕ Close help" while it shows, with the ✕ the pane draws on its own close button. It has no key letter: the engine binds only a digit or a lowercase letter, so `?` is refused, and no free letter reads as help. | The same native Button, without `dimColor`, and the same key in both states, so the pane keeps its focus. Help lists only the marks. | A "Help" button at the footer's left, and the `?` key, open it. `?`, Escape and the button close it. | The desktop pane takes no keys. A browser page takes `?`. A desktop Client draws over an absolute Box, so no look draws Help as an overlay. | `hooks/pane-help.tsx:helpView`, `codex/src/tab-chrome.tsx:HelpPage` |
| Hit areas | Character cells. | A Button takes a click only over its label. A Client region takes clicks over a whole shape. | Normal page hit areas. | The engine draws desktop Buttons label-sized. | `hooks/row-client.tsx:RowProps`, `hooks/tabs-client.tsx:TabsProps` |
| Reply while its send is out | The draft is deleted once the press is saved, and put back when the press is not confirmed. Reply pressed before the send settles opens an empty field. | Same as terminal. | The draft stays through the press, and is deleted once the press is confirmed and the draft is unedited. | A mod send can wait through a whole turn before its prompt enters. A draft kept that long would draw a closed row the reply answered as held again once the person leaves the tab, as if the person were still writing. | `hooks/register.tsx:runPress`, `codex/src/tab-rows.tsx:sendReply`, `hooks/press-reducer.ts:isPressConfirmed` |
| How a press sends, opens and copies | Sends with the engine's prompt submit. Opens and copies in process. | Same as terminal. | Sends with `codex queue` from the server. Opens in the server. The tab copies. | Codex's server cannot reach the page's clipboard. | `hooks/press-effects.ts:EffectHost`, `hooks/host-press.ts:startPress`, `codex/src/server-host.ts:hostFor` |
| Primary buttons | None. A plain terminal Button ignores `variant`. The recommended option ends "(recommended)". | The recommended option, Done, Fix or Do it. On the PRs tab, Address, Fix, or a PR's first move. | Same as desktop. | `docs/plans/inbox-ui.md` says the desktop pane makes the recommended option, or else Done, Fix or Do it, the primary button. | `hooks/pane-row-keys.tsx:keyedButton`, `codex/src/tab-parts.tsx:KeyButton` |
| Recommended answer label | "Pinch (recommended)". A long label wraps. | "Pinch (recommended)" where the button fits it, and "Pinch" where the button would cut it. The filled primary style still marks the answer. | "Pinch (recommended)". A long label wraps. | A desktop native Button is one line and cuts a label wider than its row with an ellipsis. `actionLabel` takes each look's own fit test. Desktop passes one, and so does omp (see its table). | `hooks/rows.ts:actionLabel`, `hooks/pane-row-keys.tsx:fittedDesktopLabel` |
| Reply control | A labeled action with its key. | A plain native Button, before the Client region that draws the other follow-ups. | A normal button. | A click on a desktop Client gives that Client the keys until Escape, so a field opened from it never gets the typing. A native Button's press leaves the keys in the pane, where the mod moves them to the field. The other follow-ups stay in the Client, which keeps their hit areas and spacing. Reply keeps normal emphasis and its place first among the follow-ups. | `hooks/pane-row-keys.tsx:keyRow`, `hooks/links-client.tsx:LinksProps`, `codex/src/row-actions.tsx:ActionButton` |
| Reply focus | The reply field, and the Status goal field, receive typing. When the prompt holds text, typing stays in the prompt, and "Click the field to type" shows under the field until a click on it moves typing there. | Reply, a proposal's Edit and the goal's button, then labeled Change goal, open their fields with the keys on the first click, also when the composer holds text, which stays in the composer. "Click the field to type" shows only when the pane cannot take the keys. Checked in the Claude app 4.4212.0 with engine 2.1.309. | The reply field receives typing after Reply. Built-page and native MCP-panel checks pass. | The engine refuses to give a pane the keys while the prompt holds text, and a click on a pane Button leaves them where they were. In the Claude app, a native Button's press gives the pane the keys, and a click on a Client gives them to that Client. So each button that opens a field is a native Button there, and after the drawing that drops the pressed Button, the mod moves the focus to the field. Codex and omp cannot open a field without the keys: a click on Reply puts the Codex tab's page in focus, and the omp panel takes every key while it is open. | `hooks/register.tsx:focusField`, `hooks/register.tsx:startTyping`, `hooks/pane-row-keys.tsx:keyRow`, `hooks/rows.ts:ROW_COPY`, `hooks/pane-status-goal.tsx:fieldInput`, `codex/src/tab.tsx:draw` |
| Leaving a reply field | Escape closes the field and keeps its draft. The pane stays and the prompt gets the keys. A second Escape closes the pane only at an idle, empty prompt. During a turn, over prompt text, a dialog or a prompt mode, the engine keeps that Escape, and during a turn it interrupts the turn. A click outside the pane also closes the field and keeps its draft. | Escape closes the field and keeps its draft, and the pane stays. A second Escape leaves the pane open, because the app does not close the pane on Escape. A click in the composer also closes the field and keeps its draft. Checked in the Claude app 3.6556.1. Expanding or collapsing the pane also closes an open field and keeps its draft, in the Claude app 4.4212.0. | Escape closes the field and keeps its draft. A click elsewhere leaves the field open. | The engine closes a pane opened with `closeOnEscape` on Escape, with the same `ui.close` its close mark sends. So while a field is open the mod opens the pane without `closeOnEscape`, and closes the field when the pane loses the keys. A click outside the pane also takes the keys, and the mod cannot tell it from Escape. In the Claude app, expanding or collapsing the pane takes the keys too. The engine raises no expand event, and the drawing without the keys comes about 60 to 90 ms before the one at the new width, so the mod cannot tell an expand from a click in the composer. | `hooks/register.tsx:openPane`, `hooks/register.tsx:matchPaneEscape`, `hooks/register.tsx:on('ui.render')` for `Pane`, `codex/src/tab.tsx` keydown handler |
| View's key on the Status (`status-view-ask`) | `v` presses the selected row's View, and j and k move the selection. | Clicks only, as for every desktop Button. | Clicks only. | Pete's choice: the Codex Status has no row selection and is used by clicking, so View has no key there. | `codex/src/tab-status.tsx:StatusLine` |
| The goal's keys on the Status (`status-goal`) | `s`, `e` and `x` press the selected proposal's buttons, and `s`, `e` or `g` the goal's. j and k move the selection. | Clicks only, as for every desktop Button. | Clicks only. | The same reason as View's key: the Codex Status has no row selection and is used by clicking. | `codex/src/tab-status.tsx:statusKey` |
| The goal field while its press is out | The field closes at once, and the new goal shows in the same draw. | Same as terminal. | The field stays open, its buttons dimmed, until the server confirms the goal. A failed press shows why under it. | The mod runs the goal press in its own process before the next draw. The Codex tab sends it to its server, so closing the field first would show the old goal until the answer comes. omp closes the field at once, as the terminal does. | `hooks/pane-status.tsx`, `codex/src/tab-status.tsx:GoalField` |
| The goal field's buttons | Set goal is the field's own submit. Cancel draws on a row under the field; in a proposal, under its milestones. | Same as terminal. | Set goal and Cancel sit on the field's line, and wrap under it in a narrow tab. | A Codex text field carries its buttons on its own line, as the reply field does. | `hooks/pane-status-goal.tsx:fieldKeys`, `codex/src/tab-status.tsx:GoalField` |
| The goal's Edit in "Goal · Edit" (`status-goal`) | Muted text after "Goal ·", its key letter drawn before it while the goal is selected. The selection color covers the goal's label and text. | A plain, dim native Button after "Goal ·", so that line is a button's height, taller than a text line. | A text button in the label's muted color, which takes the text color on hover. | A desktop Button is always native and taller than a line of text, and a Client cannot draw Edit as text, since a click on a Client keeps the keys from the field Edit opens. omp draws Edit as a dim button cell after "Goal ·", inverted while it is focused. | `hooks/pane-row-keys.tsx:textKey`, `codex/src/tab-status.tsx:GoalAbove`, `omp/src/panel-goal.ts:drawGoalPart` |
| Quiet buttons, such as Set a goal | Drawn like any button: a plain terminal Button has no quieter style. | Drawn like any native Button. | A ghost button. | The emphasis is the shared plan's; each look draws it with what its host has. omp draws a quiet button dim until it is focused. | `hooks/status-keys.ts:goalKeyPlan` |
| Long button labels | The host's Button draws a label on one line and cuts it with an ellipsis when it does not fit. | Same as terminal, inside the pill. | The label wraps inside the button, which becomes a rounded rectangle. | Terminal and desktop Buttons are drawn by the host on one line. The Codex tab can wrap, so the whole answer stays readable. | `hooks/pane-row-keys.tsx:keyedButton`, `codex/src/row-actions.tsx:ActionButton` |
| Failed press result on an open row | Its own line above the buttons, in the error color, such as "Could not open load.md: it no longer exists" or "Not sent: …". A finished result that did not fail, such as "✓ Copied npm login", follows the title. | Same as terminal. | Follows the title, in the error color, like every finished result. The text wraps, so a long error shows in full. | A failure says what went wrong, so the terminal and desktop looks set it apart from the title. The Codex tab draws every finished result in one span after the title, and that span wraps. | `hooks/feedback.ts:isAfterTitle`, `hooks/pane-row-lines.tsx:feedbackLabel`, `codex/src/tab-list.tsx:ListRow` |
| Text selection | The terminal selects any text. | The host decides. | Tabs, headings, marks, ages, buttons, status lines and the footer cannot be selected and show the arrow cursor. Item and PR text, the Status tab's lines, errors and the reply field can be selected. | A web page lets a person select its controls and labels as text. The terminal and desktop looks have no per-element selection control: the desktop pane has no CSS. | `codex/src/tab-css/base.css` |
| `/inbox` at startup | Registers before the first prompt. | The first `/inbox demo` opens the sample pane without an agent turn. The host can still show a stale unknown-command warning. | No command. The Inbox tab opens at any time. | Registration runs during `session.start`; a command waits for Inbox initialization. The remaining warning belongs to the desktop host. | `hooks/register.tsx:registerInboxCommand`, `hooks/register.tsx:ensureOn` |
| `/inbox` during a turn | Runs at once. | Waits until the turn ends. | No command. The Inbox tab opens at any time. | The command is registered `immediate`. The desktop app sends a typed command through Claude Code's prompt queue, which holds it until the turn ends whatever `immediate` says, as checked in Claude Code 2.1.296. | `hooks/register.tsx:registerInboxCommand` |
| Pressed button while its press is out (`dim-pressed-button`) | The Button and its key letter draw with `dimColor`, in gray. Its key and a click do nothing. | `dimColor` fades the Button's label about two thirds of the way toward its fill, and the fill stays. A click still shows the native press highlight, and the shared press path ignores the press. A follow-up link's text draws with `dimColor` and no hover highlight. | The button fades to 40% opacity and is `disabled`, so a click does nothing and its width stays. Its key does nothing. It dims from the moment of the press, before the server answers. | The desktop app's Button has no disabled state, and `dimColor` changes only its label's color. The tab waits on the server for each press, so it dims the pressed button itself until the answer arrives. | `hooks/pane-row-keys.tsx:keyedButton`, `hooks/links-client.tsx`, `codex/src/row-actions.tsx:ActionButton`, `codex/src/tab-rows.tsx:act` |
