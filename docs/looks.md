# Looks

Status: current. Read this before you change the UI or a business rule.

The inbox has four looks: `terminal`, `desktop`, `codex` and `omp`. A look is one way the inbox is drawn, and `GLOSSARY.md` defines it with host, shared module, adapter and difference on purpose. The rule is that shared modules decide and adapters draw. If a rule decides what a row says, which action leads, when a tab counts as empty or what text appears, it lives in a shared module. An adapter decides only how its look draws that. The plan for finishing this split is `docs/plans/three-looks.md`.

## Files

Shared modules are in `hooks/`. Every host consumes them, directly or through a build. They import only shared modules and shared types. `scripts/check-structure.mjs` checks those boundaries, including type imports. Codex and omp type checking need no generated Claude engine types.

A `deliveryId` identifies one local press. Each host keeps a sent-prompt record
before an arrival can change its rows. Arrival events provide message text but
no matching delivery ID, so they consume the oldest matching record. A press whose host holds its delivery until the message runs, as the mod does in the terminal and the desktop app, reads “Queued” from the moment it is sent. Codex and omp deliver at once, so their press reads unconfirmed until the delivery is saved. Queued feedback appears only after the message has waited one second. Until then the press shows its plain label and no ✓.
Unconfirmed feedback has no delay and is for a delivery in doubt: a delivery that failed to report, a message another plugin changed, or a restart that lost it. A newer
identical press reads “Not confirmed” until a later arrival can confirm
its record. Open rows, settled rows and Closed folds preserve that status
without a success mark.

The mod keeps sent-prompt records in its live plugin state across reloads.
A saved session brought back into a new process starts with none. Its pending
messages may never arrive, and their rows already read unconfirmed. A kept
record would take the arrival of the same text sent again.
Older state can lack the history needed to distinguish identical messages;
those message texts remain unconfirmed in that session. Within one process,
unmatched records are retained because discarding one could make its late
arrival acknowledge a newer press. Exact reconciliation and bounded retention need host queue identity or
queue status that the current arrival APIs do not provide.

## Adding a host

A host is a program that runs the inbox's agent: it reacts to events, keeps state, runs the inbox model and the presses. It supplies a `SessionHost`, calls the shared session functions on its events, and draws a look. `omp/` is the example, and `docs/plans/omp-look.md` records how it was built.

### What a host supplies

`SessionHost` in `hooks/session-host.ts` is everything a host provides to run one session. Each shared function takes only the members it uses.

| Member | What the host does |
| --- | --- |
| `now` | The clock. |
| `read`, `update` | Read the session, and change it under a lock. An external effect, such as a delivery, runs outside the change. |
| `exclusive` | Runs the per-reply update unless another run holds the session. |
| `catchUp` | Optional, on the update host. Has the inbox model read the whole conversation and returns its ledger answer and the Overview call to make, the conversation it reads and the `ask` that sends it, which `runUpdates` runs once the catch-up has applied, or says the conversation is unreadable. Without it, a host only runs the pending exchanges. The mod forks the conversation, and Codex and omp pass their conversation text to `askOverConversation`. |
| `ask` | Calls the inbox model with a prompt and the system text for it, and returns null when it fails. It tells its optional `report` the model it asked for, the model that answered when the host knows, and why a call gave no answer. `runUpdates` calls it twice for a reply, one after the other: the ledger call with `systemText` and `buildPrompt`, whose update applies at once, then the Overview call with `OVERVIEW_SYSTEM` and `overviewPrompt`, whose answer `hooks/session.ts:appliedOverview` writes to the ledger. |
| `inOrder` | Required on the update host. Runs an Overview call after the earlier ones for the session have finished, so each reads the Overview the one before wrote. The mod and omp chain them in process. Codex chains calls in process, then takes a `.results` file lock, which waits up to 8 minutes. The lock does not queue across processes, so Overview calls waiting in two update processes can run in either order. That needs a second update process to start while the first still waits on its Overview calls. No ledger call and no lock waits on it. |
| `background` | Optional, on the update host. Keeps Overview calls running after `runUpdates` returns, so the next ledger update starts at once. The mod and omp pass it. Codex omits it, so its detached update process stays until the calls end. |
| `records` | Optional, on the update host. Where a next build keeps its Overview call records: the host, the folder, the session, and the file calls that write, list and remove them. A release build passes none. |
| `deliver` | Sends a message to the agent as if the person typed it. |
| `isDeliveryHeldUntilRun` | Optional. True when `deliver` returns only once the message runs, which can be a whole turn later. Until then the press reads Queued. The mod sets it. |
| `prepare` | Throws when `deliver` could not start, before a sent record is saved. |
| `perform` | Opens a link or path, or copies text. Returns why it could not, or null. |
| `refreshPrs` | Fetches the session's PRs, and resolves once that fetch ends. `startPress` calls it for a press's `refresh-prs` effect, and before a fix press sends. |
| `gh` | Finds gh, drops the one it kept, runs gh for the session, and reports when none starts. |
| `settleWindowMs`, `newId` | The settle window before Done tells the agent, and delivery ids. |
| `answerMessage` | Optional. Builds the message an answer press sends when the agent reads answers in its own form. Codex sets it for a question linked to an open dialog. |
| `comparePage` | The absolute path of the host's copy of the comparison page template, which the Compare message names. |

A host reports a running turn by calling `hooks/session.ts:turnStarted` and `turnEnded`, which set `presence.isTurnRunning`. A running turn holds a Done message back and moves a working subject's mark on the Overview.

The host's state type extends `Session` from `hooks/session.ts`. It adds its own fields, and upgrades a state saved by an earlier build, as `omp/src/state.ts:upgraded` does.

### What a host calls on each event

| Event | Shared function |
| --- | --- |
| Session start or resume | `hooks/session.ts:startContext` gives the guidance and carried items. `hooks/session.ts:cleared` empties a session after a clear. A session with turns the inbox never recorded (`hooks/session.ts:isUnseen`) is marked `behind`, and its first update catches up. |
| A prompt reaches the agent | `hooks/session.ts:notePrompt` records it, matches a press's message, and returns the notes to add beside the prompt. |
| The person sends a message they typed | `hooks/session.ts:messageTyped` saves its time, and the rows that settled before it fold. A host never calls it for a message a press sent. |
| The agent uses a tool | `hooks/model-text.ts:toolActivity` and `hooks/session.ts:noteActivity` add a line of turn activity. |
| The agent calls `record` or `close` | `hooks/session.ts:recorded`, with the answer from `hooks/tools.ts`: the text the agent reads, and the person's line, which the host draws under the call. |
| A turn ends | `hooks/session.ts:endTurn` queues the exchange. Then `hooks/session-host.ts:runUpdates` runs the inbox model on it, or catches up when `needsCatchUp` says the ledger may have missed a turn, and `hooks/session-host.ts:wakeForDone` tells the agent about rows closed with Done. |
| The person presses a button | `hooks/session-host.ts:press` applies it, saves a sent record before delivery, delivers, and runs local effects. |
| The PRs tab opens | `hooks/session-host.ts:fetchPrs` fetches through the host's gh. |
| A look draws | `hooks/session.ts:sessionView` builds the view. |

The Claude Code mod's are `mcp__inbox__record` and `mcp__inbox__close`, since an MCP server's name prefixes its tools.

### Where else to register a host

1. `Look` in `hooks/view.ts` gains the new value. Name the places that branch on it, as `isTerminalLike` does for the terminal's handles.
2. `scripts/check-structure.mjs` checks the host's imports. omp's rule is that its files import only shared modules, and that one file imports the agent's packages.
3. `scripts/check.sh` runs the host's bundle check, type check and tests.
4. `evals/agent.ts` gains the agent, with a stand-in for the inbox that uses the real tool descriptions, as `evals/omp-probe.ts` does for omp. `scripts/eval.sh` passes it through.
5. The tests run `tests/session-script.ts` against the host's `SessionHost`, as `omp/tests/session.spec.ts` does. The script drives a prompt, a `record` call, a turn end, the inbox model's answer, a press that sends, its arrival, Done and Undo. It calls the shared functions directly, so the host's event wiring needs its own tests.
6. `ClientId` in `hooks/clients.ts` gains the host. Classify every `FeatureId` for it as `full`, `different` or `unsupported`, check each against the host's code, and give each `different` or `unsupported` entry a reason that is a real host limit or a product decision. Add the host to `DIFFERENCE_TABLES` in `scripts/check-structure.mjs`, with a table in "Differences on purpose" that has a row for each of those features.
7. The docs rows: this file's Files table, owners table, Differences on purpose and "After you change X"; `GLOSSARY.md`; `AGENTS.md`; the README's install steps; and `docs/release.md` for the version field and the build.

| `codex/src/server-main.ts` | The loader | Quit and reopen Codex. A change to `codex/src/server-handler.ts` or anything it imports reloads without a restart. |

## Checks

`scripts/check-structure.mjs` checks the parity record in `hooks/clients.ts` against "Differences on purpose", as described there. It also parses imports and resolves their targets. It follows local import chains, including type bridges. Shared modules retain their shared-only restriction through those chains, and Codex cannot reach nonshared hooks through another local module. It includes build-shared tones and type imports. Shared modules and Codex reject computed targets. The only exception is a direct `import(url)` in the top-level `codex/src/server-main.ts:load` function. Nested functions do not inherit that exception. That function selects installed or dev handler URLs for hot reload.

The script also checks that omp's files import only shared modules, and that only `omp/src/host.ts` imports omp's packages. It checks plan status lines, file references and links. Its owner-symbol check only verifies that a word occurs in the referenced file. It does not establish a definition or semantic freshness.

`codex/tests/structure.spec.ts` checks the command against disposable fixtures. Mounted row-action tests check Codex controls and outcomes. The mod demo test checks terminal and desktop titles and actions, with settled rows and PRs outside that test. Full-page behavior, native painting, clipboard, focus and measured motion still need their own checks.

`omp/tests/session.spec.ts` runs the shared session script from `tests/session-script.ts` against omp's `SessionHost`. `omp/tests/panel.spec.ts` checks that the panel draws buttons in the shared plan order, in place of the demo test in `tests/hooks.test.ts`.

`./scripts/check.sh` runs formatting, plugin validation, structure, the type checks, the test suites, and that the Codex bundles and `omp/dist/host.js` match their sources. Run it after every change. Model evaluations run separately when model-facing text changes.
