# Evals the release can trust: Status checks set aside

Part of [Evals the release can trust](eval-trust.md), split from [eval-trust-follow-ups-replays.md](eval-trust-follow-ups-replays.md). Each item is a Status check that blocks nothing today: a rule's or a step's `until`, or a fact that also accepts a status through `alsoRight`. Each says what it waits on and what the check catches once it blocks again.

Status: building. Remove an item when the change it waits on lands, and take its `until` or `alsoRight` out in the same change.

- **An `until` also hides a fault at later steps.** Targets count only fresh failures. A fault that first shows at an `until` step and stays on the page fails no later target of the same rule. Counting a failure carried from an `until` step as fresh at the next target would catch it. The report lists each `until` target that passed in every run, from `passingUntils` in `evals/status-report.ts`, so an `until` left after its fix lands shows. That line blocks nothing, since one clean batch can be luck.
- **Sonnet links the 2.5 ask to the fix it waits on.** At `coordinator-day` step 4, the ask "Should 2.5 wait for the archive fix, or ship without it?" holds up the 2.5 release, which the page draws only as a milestone. All 3 Sonnet runs and 1 Codex run linked it to the "Vanishing notes" subject, and 2 Codex runs wrote `LINK: i2 | m5`, as the prompt asks (`status-2026-11-15T08-04-46.170Z.json`). The step lists `asks-linked` in `until`. A sentence in the LINK rule saying an ask that holds up a milestone is linked to the milestone, not to the work it waits for, tested on this step, would let the target block again.
- **The folder bug is folded into the set-aside Export button.** At `coordinator-day` step 8, the person reports a Windows default-folder bug. 5 of 6 runs reused the Export button subject for it, as `SET: s3 | queued | Windows default folder bug, after 2.5`, instead of writing NEW. When the folder fix merges, DONE closes the button, and step 11's `marks-true` fails on it (`status-2026-11-15T08-04-46.170Z.json`). The step lists `marks-true` in `until`. A sentence in `STATUS_SYSTEM` saying set-aside work keeps its subject and new work gets NEW, tested on step 8, would let the target block again. A step 8 `open-pieces-kept` target would catch the fold where it happens.
- **The `Now:` line keeps naming a fix after it merges.** At `coordinator-day`'s step 9 in the docs, all 3 Sonnet runs kept a line such as "Fixing archive bug, then shipping 2.5", and 2 Codex runs kept "Fixing disappearing notes, then shipping the update", after the fix's subject closed (`status-2026-11-12T22-16-07.559Z.json`, `status-2026-11-13T06-31-39.003Z.json`). Code clears a kept line only when it holds every word of the closed subject's name, in `namesClosed` in `hooks/status-ops.ts`, and looser word rules clear true lines. Two shared words cleared "Adding offline sync to the notes app" when "Offline sync toggle" closed while the engine still ran, and "Getting search under 100 ms" when "Search under 200 ms" closed. One shared word, the only rule that catches the Codex runs, cleared "Shipping Notes 2.5" when "Vanishing notes" closed. Leaving out the head title's and the goal's words passes those cases but catches 2 of the 5 runs. So the fix is a sentence beside "Never reword a head that still holds" in `STATUS_SYSTEM`. The step's `head-follows` target, whose `pastMatch` takes "vanish", "disappear" and "archiv", catches a line left on the merged fix. In `status-2026-11-15T08-04-46.170Z.json` it failed 4 of 6 runs, so the step lists `head-follows` in `until`.
- **A new goal written in place of a DROP.** In `milestone-dropped`, the person cuts the store review from 2.5. 2 of 3 Codex runs and 1 of 3 Sonnet runs wrote a GOAL such as "Notes 2.5 web beta out" with no `DROP: m2` (`status-2026-11-15T08-04-46.170Z.json`; 8 of 18 in `status-2026-11-15T06-56-10.615Z.json`). Code refuses a GOAL while the goal's work is open, so the store review stays queued. The step lists `milestones-true` in `until`. The person's words arguably reframe the goal as a web beta, so first decide whether a new goal is right there. If it is, the facts should take it; if not, a sentence saying a cut milestone gets DROP, tested on this step, would fix it.
- **The mid-turn wording follow-up: Sonnet still writes the agent's edits mid-turn.** `statusMidTurnPrompt` says how to write a piece that has started with nothing working yet: "PDF export started, not working yet", not "PDF edits begun, untested". The judge passes "started, not working yet" and "incomplete", as property 6 in `docs/plans/status/good-status.md` allows, and fails "edits begun". In `status-2026-11-02T01-28-54.089Z.json`, `mid-turn-activity` failed `where-it-stands` in 5 of 5 Sonnet runs and 0 of 5 Codex runs. Sonnet kept the edits as the subject: "Ranking edits started, not working yet" and "ranking edits started, not verified". The step lists `where-it-stands` in its `until` until a wording fix passes the case. A rule in `STATUS_SYSTEM` itself that calls an edit an activity, as in "edits started" or "edited, untested", tested on this case, would show whether the mid-turn line is too weak where it sits.
- **A Herdr focus in the Status replays.** The `child-labels` rule in `evals/status-rules.ts` still waits on #149, which is built. The replays name their delegates by ids, `vn2` in `coordinator-day.ts` and `sm4` in `coordinator-day-start.ts`, and no replay step reads Herdr, so a delegate never takes its session's focus. A replay event that answers a Herdr check with each delegate's `inbox-focus`, run through `delegatesSettled`, would let the rule block again and catch a delegate row that keeps its id.

Only [#412](https://github.com/petekp/inbox/pull/412), not merged yet, makes code start a milestone when its work runs. So `ms-live25` there also takes `queued`.
