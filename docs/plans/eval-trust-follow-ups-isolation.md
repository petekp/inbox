# Evals the release can trust: agent suite isolation

Part of [Evals the release can trust](eval-trust.md). These follow-ups cover what an agent in `./scripts/eval.sh --suite agent` can reach beyond the stand-in inbox: its shell, the runner's files and other tools.

Status: building. Each item stays until the change that does it lands.

Each item names what it would catch. Remove an item when the change that does it lands.

- **The Codex agent suite stops when Codex names the runner's home folder.** On 2026-11-07, Codex listed the runner's home folder in `pivot-moots-recorded-task`. `assertCodexUsedOnlyProbe` in `evals/codex-isolation.ts` stops the whole Codex run with exit 3 on such a command, so the cases after it never run, and a guidance change gets no Codex result on them unless they are run alone. The stop guards the runner's skills and config, so it stays. A sandbox that kept the run's shell out of that folder would let such a run be graded instead.
- **Codex's own resource tools can leave a case ungraded.** Codex offers `list_mcp_resources`, `list_mcp_resource_templates` and `read_mcp_resource` whenever a session has an MCP server, and no config turns them off. A run that calls one cannot be graded, and the harness tries it twice more. Codex called them in `side-request-leaves-question-open` and `user-did-it-closes-question` on 2026-11-04 and 2026-11-07, and on ac4026ea. A case where Codex calls one in most runs reports "not run" and the suite exits 2, so a Codex regression in that case passes unseen. A way to grade such a run, or to keep Codex from calling them without changing what it reads, would catch it.
- **No test covers the Codex isolation guard.** `assertCodexUsedOnlyProbe` and `codexResourceCall` in `evals/codex-isolation.ts` decide which Codex events stop the agent suite and which leave a run ungraded. A test would catch a change that lets a call to a server other than the probe through, or that grades a run that called one of Codex's resource tools. `claude plugin test` refuses `node:` imports, and `evals/codex-isolation.ts` imports `node:child_process` and `node:os`, so no test runner in the repo loads it. Moving the two functions into a module with no `node:` imports, which takes the home folder as an argument and gets `IsolationError` from a module without them, would let `claude plugin test` load it. A Bun or `node --test` runner for `evals/` would also work.
- **Codex may run a system `gh` over the case's stub.** Its `zsh -lc` puts `/usr/local/bin` and `/usr/bin` before the case's `bin`. On 2026-11-21, `zsh -lc 'which gh'` with an empty `HOME` and the case's `bin` first found the stub on a Mac whose only `gh` is in `/opt/homebrew/bin`, which comes after the case's `bin`. On a Mac with `gh` in `/usr/local/bin` or `/usr/bin`, Codex runs the real one and the case tests nothing. Stopping a run whose `gh` is not the stub would catch it.
- **An omp run can call the real `herdr` CLI.** omp has a shell, and nothing in the suite stops a command that reaches Herdr, as `assertCodexUsedOnlyProbe` does for a Codex command that names the runner's home folder. In `delegate-question-not-moved-to-another-kind` on 2026-11-20, one omp run of 5 ran `herdr agent list` to message its parent terminal (`agent-2026-11-20T20-56-41.465Z.json`). The call failed only because the temporary `HOME` made Herdr's socket path too long. The run then recorded a finding about it, which failed the case. A `herdr` stub on the case's `PATH`, or a stop on any `herdr` or `hc` command, would catch a run that messages a real Herdr terminal.
- **A Codex run that timed out reads as Codex's own stdin notice.** On 2026-11-24, three agent-suite runs went at once, and 9 Codex runs in `agent-2026-11-24T07-03-59.974Z.json` ended with `codex exited -1: Reading additional input from stdin...`. Code -1 means `exec` in `evals/agent-cli.ts` killed it at `TIMEOUT_MS`, or something else killed it. The omp path in `evals/agent.ts` already says "timed out after 300s or was killed". Saying the same for Codex would keep a timeout from reading as a stdin problem. Seven cases went ungraded and passed 5 of 5 each when rerun alone (`agent-2026-11-24T09-00-56.142Z.json`).
- **An omp run can still add to or replace the harness files.** `ompSandboxProfile` in `evals/agent-cli.ts` refuses an omp run reading, listing, moving or removing `calls.jsonl`, `tools.json` and `state.json` in its case folder. It cannot refuse writes to them, because the probe in `evals/omp-probe.ts` runs in omp's own process and writes those files. A shell command that guesses a name, such as `echo '{}' >> ../calls.jsonl`, could add a call the grader counts. A sandbox on omp's shell commands alone, or a probe that writes where the shell cannot reach, would catch it.
- **`state.json` is readable until the probe removes it.** The probe reads and removes it as omp starts, before the first prompt. If the probe failed to remove it, the agent could read the state it is graded against. A stop when the file still exists at the first prompt would catch it.
- **A reply that names a harness file for its own reasons stops the omp run.** `assertOmpSawNoHarness` matches the bare names `calls.jsonl`, `tools.json` and `state.json` anywhere in a message or tool result. So a case about a project that has its own `tools.json` would stop as a leak. Matching a name together with the case folder's path would catch only real leaks.
- **An omp run can read files outside its case folder.** The sandbox refuses only the harness files. The agent's shell can still read the runner's home folder by its full path, as the Codex stop above guards against. A read deny on that folder, except what omp needs, would catch it.
- **The Codex run was not checked for reads of the harness files.** The omp sandbox does not cover Codex. A Codex run that tries `ls ..` and `cat` on the harness names would show whether Codex's own sandbox refuses them.
