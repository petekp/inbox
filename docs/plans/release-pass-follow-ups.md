# Scripted release pass: follow-ups

Part of [Scripted release pass](release-pass.md).

Status: building. Each item stays until the change that does it lands.

- **An `@inbox` check in omp.** Run omp with a fresh `HOME` and three configs: no `@inbox`, `@inbox` set to a working model, and `@inbox` set to a model omp cannot use. The panel footer must name the Sonnet, the working model, and the Sonnet again. It would catch a change that breaks the fall-through, or a footer that names a model the inbox does not call.
- **An update with the Codex Inbox tab open.** Open the Inbox tab in the ChatGPT app, then install a newer build the way `~/.agents/scripts/inbox-live.sh` does (`codex plugin add inbox@inbox`). Change threads until the Codex log shows "Loading MCP server catalog", and check the tab still works. Then open a new Inbox tab in a thread that has none, and check it shows the new build, using a build that looks different, such as one with Show demo. The first step would catch a tab address that changes between builds: Codex then removes the open tab, which shows "Couldn't display Inbox" until it is closed and opened again. The second would catch a page swap that fails, since a new tab starts on Codex's saved copy of an earlier build and then stays on it. The release pass installs a build once, before any tab is open, so it missed both.
- **A message typed in Codex while a turn runs.** In the ChatGPT app with the Inbox tab open, give the agent a task that runs for a while. While it runs, dismiss a row and wait for its Undo to end. Type a message and press Enter, then press Done on another row before the turn ends. The dismissed row must fold at Enter, and the Done row must stay until you type again. The inbox counts a typed message when Codex runs `UserPromptSubmit` (`codex/src/hook.ts`), and nothing has shown when Codex runs that hook for a message sent during a turn. In Claude Code, the mod's `prompt.submit` runs at Enter even for a queued message, so Codex should match it. The check would catch two failures. If Codex runs the hook only when the waiting message starts, the dismissed row stays until then, and the Done row folds too, though nothing was typed after it. If Codex runs no hook for that message, the dismissed row stays until a tab change. `codex/tests/hook.spec.ts` sends `UserPromptSubmit` itself, and no check in the pass sends a message while a turn runs, so neither catches these.
- **The omp panel test can still time out under heavy load.** "/inbox hides the band while the panel shows…" in `omp/tests/host-panel.spec.ts` timed out after 5 s in one of three `check.sh` runs on 2026-10-24. It has not failed since in about 2,000 runs with up to 64 test processes at once. Most of the test's time goes to waiting for the panel to open, which includes the first `import('@oh-my-pi/pi-tui')` that `openPanelUi` in `omp/src/host.ts` runs. That wait takes about 150 ms on a quiet machine and up to 2.3 s with 64 processes running. The test already waits on each state it reads, so heavier load can use up its 5 s on that wait alone. Load pi-tui before the test starts, or give the test a longer timeout, so that a timeout means the panel did not open.
- **Fixed: the Codex row-actions test failed under load ([#75](https://github.com/petekp/inbox/issues/75)).** The test in `codex/tests/row-actions.spec.ts` stamped Codex's close with `Date.now()`, just after a reply the tab could not confirm. When the close and the reply fell in the same millisecond, the view counted the reply as sent after the close, since `replyAfter` in `hooks/view.ts` compares `last.at >= closedAt`. The row then settled as "Replied" and its reply field went away. The test now stamps the close 1 ms after the reply. In a quiet run the two were about 1 ms apart. Why load raised the failure rate is not known.

  A failure also ran for about 100 s and could grow to gigabytes, because `assert.equal` on two DOM elements makes Node diff their printed forms. The Codex specs now compare elements with `assert.ok(a === b, message)`, so a failure reports at once.
- **Read the plugin directory's scan of `main` after each update.** Nothing local runs the directory's rules for a hooks module. `claude plugin validate --profile directory` says it applies none of them. The directory checks `main` about every 6 hours and scans each new commit. After `main` moves to a release, the release owner reads the scan of that commit in the developer portal. The release is done when the scan reports no block and no hold that the README's "What it runs, sends and changes" section leaves out. A scan that did not finish counts as not read, so the owner reads the next one. This would have caught the two blocks on 0.2.13: `$` passed to functions in another file, merged on 2026-10-19, and a `tool.check` hook that read its verdict, merged on 2026-10-22. They reached `main` with 0.2.13 and went unseen for nine days.
- **A slow gh in each look.** Put a gh on the PATH that sleeps 25 seconds before it runs the real one, and open the PRs tab in each look. Each PR must keep its last view and read "Last refresh failed: gh did not answer within 20 seconds". The first 0.2.14 pass saw the PRs tab say "The inbox could not find gh" on a busy host, where gh was only slow, and #175 fixed it. This step would catch a timeout read as a missing gh again, in any host's run.
- **One question per turn in the Codex dialog step.** Asked for two questions, Codex put both in one two-page dialog. The step then cannot answer one question and close the other with its ✕, and the 0.2.14 pass needed an extra turn to check that a dialog closed unanswered leaves an Asks row. Asking for one question per turn would keep that check in the step.
- **The omp band test fails when run alone.** "the band shows above the editor and redraws with the counts after a change" in `omp/tests/host-panel.spec.ts` failed 12 of 15 times run alone on 2026-10-28, on `f66b4f82` too. Another run of 15 failed once. Each failure is an assertion, not a timeout: after `renders.count` rose, the band still read "Nothing needed", not "Asks". A render the test did not cause can pass its wait before the recorded task reaches the band. Waiting for the band's text instead of the render count would make a failure mean the band did not redraw.
- **The mod's test kit skips a `process.run` fake that throws.** In `claude plugin test`, a fake that throws, as `world()` in `tests/hooks-world.ts` does for a missing gh, is skipped with "test's process.run hook was skipped". The mod's call then rejects with "no implementation for process.run", not with the fake's error. A test whose fake throws a message the mod reads, as #175's first version read "still running after", passes or fails on the kit's message instead. A fake that returns `{ deny: … }` reaches the mod with its own message. Moving the throwing fakes to `deny`, or a kit that fails the call with the thrown error, would catch a mod that reads the wrong error.
- **The mod's test kit cannot see where a desktop drawing moves the focus.** The pane calls `$.ui.focus` after its render hook returns, through that hook's `$`. In `claude plugin test` that call rejects with "no implementation for ui.focus", even when the test registers its own `on('ui.focus')` handler, so a test cannot tell which element a drawing focused. A test for #128 and #71 checked that a click that opens a row and a PR's Dismiss move no focus, and that Reply gives its field the keys. It failed before and after the fix because the test kit has no `ui.focus`, so it was dropped. If the kit passed a render hook's later calls to the test's handlers, that test would catch a focus move coming back. In the Claude app, such a move scrolls the pane to the focused button and can draw a keyboard focus ring on it.
- **The look map's `on('event')` references go unchecked.** `checkLookMap` in `scripts/structure/docs.mjs` checks a `path:symbol` reference only when the symbol is a name. The look map names a hook handler as `hooks/register.tsx:on('tool.describe')`, and such a reference passes even when the file has no handler for that event. A check that the named file calls `on` with that event would catch a reference left behind when a split moves a handler or a change removes one.
- **No omp test covers a `herdr agent wait` while it runs.** `omp/src/host.ts` shows the delegate's row at `tool_execution_start`. At `tool_execution_end`, it takes the row back if no `tool_result` came, since the wait never ran. No test sends either event for a wait. So the tests would still pass if a running wait showed no row, or a blocked wait left its row.
- **Mod tests without a 20 s limit can still time out under heavy load.** On #223, `check.sh` ran at a load average of 28 on 16 cores, and the slowest test in each of six files in `tests/` hit the 5 s default: `hooks-closing`, `hooks-demo`, `hooks-done`, `hooks-prs-links`, `hooks-row-drawing` and `hooks-tasks`. Those six tests now have a 20 s limit. Alone, at a load average of 5 to 7, the five besides row-drawing take 0.35 to 0.93 s, and nothing in them could go without dropping a check. Most of their time goes to two things. The kit loads the mod again for each test, so each test's first `$.session.start` takes 140 to 220 ms, and almost all of it passes before the mod makes its first call. A one-file mod's takes 7 ms. And each clock advance through an Undo window redraws the terminal pane 24 times, at 2 to 5 ms a redraw. Every other mod test keeps the 5 s default. The other tests in these five files take 0.19 to 0.31 s alone, and their first `$.session.start` is 140 to 170 ms of that. On #223 the tasks test took at least 13 times as long as it does alone, so a load like that could time out any of them, and their timeout cannot tell a hang from load. A kit that kept the loaded mod between tests would remove most of that time. On #282, `check.sh` ran at a load average of 21 to 44, and three more tests hit the 5 s default: the terminal tabs test in `hooks-tabs-and-footer`, and both demo button-order tests in `hooks`. Each draws many rows or widths, as the row-drawing test does. Both files passed when run alone. On #347, `check.sh` ran at a load average of 90 to 100 and 79 tests across 32 files hit the 5 s default, all timeouts; rerun alone as a batch at load 12 to 20, 13 to 48 still timed out, on different tests each time, and every file then passed on its own. On #246, `check.sh` ran at a load average of up to 320, and 37 tests across 19 files hit the 5 s default. Run alone at load 140 to 235, 18 of those files passed. The 19th, `hooks-prs-buttons`, timed out on its other test, then passed twice at load 100, in about the time it takes on `next`.
- **Codex PR fetch tests wait 50 ms of real time.** `viewAfterFetch` in `codex/tests/server-fixtures.ts` asks for a view, waits 50 ms, then asks again, on the guess that the fetch the first view started has finished. "a view polls the PRs again after 2 minutes…" in `codex/tests/server-gh.spec.ts` waits the same way. On #246, at a load average near 320, that test counted 2 GraphQL queries where it expects 3. It passed alone at load 265. Waiting for the fetch itself instead of a fixed time would make a failure mean the view did not fetch.
- **No test covers what the mod's model call reports.** `askInboxModel` in `hooks/register.tsx` passes each call's model, the model that answered and its error to `report`, and a next build saves them in its record of each Status call. `tests/session-status-calls.test.ts` checks that record with a stand-in host, and no mod test reads it from the mod's own call. So a change that dropped the mod's `report` call would pass, and its records would lose why a call failed. A mod test that fails a Status call and reads its record would catch that.
- **No pass step opens an `http` link from a row, and no row can hold one.** #203 made each host open `http://` links the way it opens `https://` links (`openTarget` in `hooks/presses.ts`). But `readHelp` in `hooks/reply-parse.ts` keeps a link only when it starts with `https:`, so a task step such as `http://localhost:5173/greet` is dropped before it reaches a row. The `record` tool's answer then says the step was "not a command, a file path or a link". In the 0.3.0 pass, an agent asked to record that step got the task without it. A step that records a task with an `http://localhost` step and presses it would catch a local link that cannot be opened from the inbox. It fails today, so it waits on a choice: accept `http` links as steps, or keep steps `https`-only and have the answer say why the link was left out.
- **A PR whose saved view the mod dropped loses its Merged row.** To keep a saved session's PR views within `SAVED_PR_VIEWS_MAX`, `forStore` in `hooks/mod-saves.ts` drops whole views, and it can drop an open PR's. If that PR merges while its conversation is closed, the fetch on load finds it merged with no earlier view. `withFinishedPrsSettled` in `hooks/pr-tab.ts` then does not settle it, and it leaves the PRs tab with no Merged row. A stub view with empty checks and threads would keep the row, but until the load's fetch lands, the stub's row reads "Ready to merge" even while checks fail. Drawing a PR that no fetch has read since load as "Checking…", in every look, would let the save keep such stubs. A pass step that resumes a conversation over the cap after one of its PRs merged would catch the lost row.
- **No check looks for value import cycles, and `next` has two.** A value import cycle is a loop of modules that import values from each other, with `import type` left out. At load, a module in such a loop can read a binding another has not set yet, and throw. No script in `scripts/` looks for these loops, and the repo has no CI. A check run by hand on #246 found two on `next` at 720bddc3. One runs through `hooks/pr-press.ts`, `hooks/pr-refresh.ts` and `hooks/pr-rows.ts`. The other runs through `omp/src/panel-draw.ts`, `panel-entries.ts`, `panel-goal.ts`, `panel-keys.ts` and `panel-page.ts`. The tests pass, so neither loop reads a binding too early today. A new import can change which module loads first. A cycle check in `check.sh`, with these two as its baseline, would catch a new loop before it throws in one host.
- **Whether omp reloads an extension without `session_shutdown`.** `ompPresses` in `omp/src/host-presses.ts` stops following a session's presses only at `session_shutdown`. In a Herdr app terminal, reload the inbox extension in a running omp session, then press Done in the Herdr look. Check `herdr.log` and the panel. If omp reloads without a shutdown, the old instance still watches the press folder and can take the press. The press then applies once, but the new panel does not redraw until its next change, and an Answer sent through the old instance can fail. No test reloads the extension, so none catches an old watcher left running.
- **What `codex queue` does for an ended thread, and whether it reaches a Codex CLI session at all.** Codex has no hook for a session's end, so its published file and the terminal's `inbox.session` label still name the ended session. A Codex server started later in that terminal applies the look's presses for it, and Answer and Reply run `codex queue --thread <ended id>`. In the VM, end a Codex CLI session in a Herdr app terminal, start another, and press Answer on the first session's row before the second writes. Then press Answer on a running CLI session's row. The first step would catch a row that reads as sent when the message reaches no one. The second would catch `codex queue` failing to reach a CLI session in a terminal, which the tests stand in for.
- **No check catches a row feature the Herdr look does not draw.** `hooks/clients.ts` records each feature for the Claude Code, Codex and omp clients, and has no entry for the Herdr look. So `check-structure.mjs`, which reads that record, passes when the Herdr pane leaves out a row line the other looks draw. The context line of a selected question (`asks-context-line`) shipped in the other four looks and was missing from `herdr/src/draw.ts:rowBody` until a reader noticed. A Herdr entry for each feature in `hooks/clients.ts`, or a Herdr test that draws every `RowView` line field of a demo row, would have caught it.
- **A test cannot tell when its `w.beforeAct` never ran.** `world()` in `tests/hooks-world.ts` runs `w.beforeAct` from its `ui.press` and `ui.input` hooks, just before a press lands. Claude Code 2.1.323 changed which presses a hook hears: one that names no `plugin` hears only its own plugin's. The test file is its own plugin, so the world's hooks stopped hearing the inbox's presses until #398 named `{ plugin: 'inbox' }`. Three tests then pressed on rows that had not changed ([#397](https://github.com/petekp/inbox/issues/397)). They failed on a second send or a missing stale note, and one waited out a 10-second hook budget. A test whose press needs no change would have passed for the wrong reason. A helper that sets the act, presses and fails when the act did not run would catch a kit change that stops the world's hooks hearing presses, and name it.
- **A live check of the Herdr panel's look at the Status.** The rule in `herdr/src/look.ts` comes from a probe of the Herdr app, and these parts of it ran in no live session. Each step names the failure it would catch.
  - Drag the scrollbar thumb with the pointer still. If the drag reaches none of the look's handlers, the offset stays trusted for up to 4 s, so a row on screen for 1 s before the drag can count as seen.
  - Zoom another pane in the panel's tab. If `zoomed` never reads true, the look runs behind the zoomed pane, and every row of a list that fits counts as seen.
  - Close the panel during a look. If `close` does not run or its write does not finish, that look is lost and its rows stay unseen.
  - Resize the panel by dragging its edge. If the block size listeners cost too much, the panel lags during the drag.
  - Check the gap above the first block at other text sizes. The probe saw 7 px against the 8 px the padding gives, and the rule allows 2 px. A larger gap can count a first line that the bottom edge cuts.
  - Switch tabs and come back after a row's height changed. If a block that mounts again reports no size, its old height places the rows below it wrongly.
