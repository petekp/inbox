# The Status tab: decisions on the page's accuracy

Part of [the Status tab plan](../status.md). Decisions 1 to 21 are in [the Status tab decisions](decisions.md).

Status: built.

## Decisions

22. **The Status call writes the head, and checks it against the open and finished subjects at every call.** It writes a new head when the head is empty or has no description, when the person asks for work that is not part of what the head names, or when a working subject is not part of what the head names, as when the work the head names finished and the session started on other work. It also writes one when the description names work that finished or that the session no longer does, keeping the title word for word when it still names the focus. One piece finishing, the next starting, or the person asking for the next does not change the focus. It keeps the head's title while a working subject is part of what it names, and when the work it names is done and nothing else is working. Code holds a head that has a description when the same answer finished work that was working or waiting before it, finished none that it added, and left none working or newly waiting. It holds the description too, since in that answer the call rewrites it into what comes after the work, such as "Wrapping up image support", where the focus did not move. When that answer leaves no work working or waiting, code then clears the description, as decision 30 says. Otherwise a new head that keeps the title keeps the title's wording and takes the new description. When the head keeps its title, code clears its description when the same answer finished a subject the description names, by every word of that subject's name, while other work goes on. That holds for an old description and for a new one the answer wrote. The next call writes a new one.
    - Reason: the call reads one exchange at a time. A rule that moved the head only when an exchange switched tasks left it on finished work all day, because work that drifts over many small exchanges never looks like a switch. The subjects the call reads at every call show a head that fell behind, however many exchanges ago.
    - Reason for the hold in code: in the replays, Sonnet at low effort moved the head to queued work once the work it named finished. The prompt alone did not stop it.
    - Reason a head that keeps its title takes the new description: code once held the whole head then, since Sonnet rewrote the description for each new piece of the same focus. That hold also threw away every correction. In the record of Status calls, every same-title head whose description changed was dropped, so the description went on naming finished work. A description of the current piece is true, and one of finished work is not.
    - Reason the prompt names a stale description: the HEAD rule listed only an empty head and work outside the head, and told the call never to reword a head that still holds. With code taking corrections, 7 of 10 runs of `head-description` still wrote no HEAD line: Sonnet in 2 of 5, Codex in 5 of 5 (`status-2026-11-19T06-13-33.891Z.json`).
    - Reason the hold looks at what the answer closed: work that started and finished in one answer is the session's focus, so a head for it moves. A DONE whose id matches nothing changes no subject, so it holds nothing.
    - Reason code lets a stale description go: a head such as `2.5 release` over `Fixing the sync bug, then shipping 2.5` keeps its title when the sync bug is done, and its description then names finished work, on the page and in Herdr. Clearing it shows the title alone until the next call writes a description, which is true where the old one was not.
    - Code does not derive the head from the subjects. The head sits a level above the rows: `Offline sync` holds while its engine, conflicts and toggle rows take turns being worked, and `2.5 release` over `Fixing the sync bug, then shipping 2.5` spans two rows. A head taken from the working subject that changed last would flip between rows and repeat the top row.
23. **A GOAL may replace an inferred goal whose work is still open when the person changes its outcome.** An example is cutting the store review from "Notes 2.5 in the store" and shipping a web beta. Code takes such a GOAL only when it revises the goal the answer found, as `goalRevision` in `hooks/status-goal-gate.ts` says. It must cut a milestone that was open and that the answer did not finish, by leaving it out or naming it dropped. It must name again, with an open status, a milestone that holds open work. The same answer's SERVES lines must send each other open subject the goal holds to Other work or to a milestone it names again. A milestone named in other words counts as cut. A milestone named again keeps its open work and asks, and, while its status is the same, its text. When a revision leaves open work with no place, the next call reads which work it is. It also reads what to write in each case: SERVES to - when the person cut that work's milestone, DONE when the work is done, and otherwise no GOAL. Every other `work-open` refusal of a GOAL line also says how to revise a goal.
    - Reason: Pete decided on 2026-11-15 that a new goal is as right as a DROP of the cut milestone there. Before this, the 2 of 3 Codex runs and 1 of 3 Sonnet runs that wrote a new goal left the old goal, with the cut milestone still queued (`status-2026-11-15T08-04-46.170Z.json`).
    - Reason for the cut and the work sent to Other work: a rewording, an added milestone or a renamed one is not a change of outcome. So the gate still refuses those while the goal's work is open, and an added outcome stays a MILESTONE line.
24. **Code folds a NEW into an open subject only when the two names have the same key words. The Status call's text, not code, keeps a bug and its fix as one subject.** In one catch-up answer, the call wrote `NEW: Slash command fix` for the open "Slash command bug", and code kept both, because "fix" is not "bug".
    - Reason: two reviews of a wider fold each found it merging different work or losing lines. A fold through `find` reached DROP, so `DROP: Login fix | duplicate` would drop an open "Login bug". A fold on NEW only, with guards for the same answer, still merged a queued "Search" with a new "Search bug". It also ignored the DONE in "NEW for it, then DONE with its name", which kept merged work open.
    - A later fold should meet all of these:
      - Fold only when both names carry a word for the kind of work, as bug and fix, or fix and PR. A name with none, such as "Search", never folds with "Search bug".
      - Map the folded NEW's name to its subject's id for the rest of the answer, so that `find` resolves SET, DONE, LINK, SERVES and WAS lines that name it.
      - Ignore only a DROP that names the folded NEW by name. A DONE by that name applies.
      - A NEW folded into a subject the same answer already SET changes nothing. A NEW whose name differs only by a word for the kind of work from a subject the same answer closed changes nothing too.
25. **Only finished work the person has not seen close reopens a subject.** `<finished>` marks each subject that closed since the person last looked "not seen yet". When the same work turns out not done or breaks again, as a fixed bug that breaks again, the Status call reopens it with SET by its id. A new target or a higher bar for finished work is a NEW subject. A finished subject the person has seen stays finished. Work on it that comes back, new work on the same outcome, a follow-up or a release is a NEW subject. Code's own reopen agrees: a NEW whose whole name repeats a subject closed since the person last looked reopens that subject (`hooks/status-ops.ts:closedUnseen`). A longer name, such as "Retry button release" after "Retry button", is new work.
    - Reason: the call read two rules that disagreed. One said to SET finished work that comes back, and the milestone rules said a done subject stays done. The rules now say one thing in both places, and code's reopen follows the same line.
    - Reason a seen subject stays done: the person read that row as finished. At `milestone-work-done` step 2, where sync breaks again on iPad after "Sync conflicts" closed and was seen, Codex set that subject working in 8 of 9 runs while the rule let any finished work come back (`status-2026-11-19T07-23-53.447Z.json`, `status-2026-11-19T07-28-18.280Z.json`, `status-2026-11-19T07-46-29.452Z.json`), and in 0 of 3 with the sentence that a done subject stays done.
    - Reason a new target is new work: told it could reopen an unseen subject for "a piece found not done", the call reopened the finished "Search index" when the person raised its target to 100 ms, at `long-turn` step 3, in 3 of 6 runs, and let that done row stand for the new piece in 2 more (`status-2026-11-19T11-37-32.301Z.json`).
    - Reason code matches whole names: a name that held a closed name reopened it, so "Retry button release" set the finished "Retry button" working again.
26. **While no goal runs and none is suggested, the Status call is asked for the next goal.** It reads a `<next-goal>` block and answers with GOAL when the goal is clear, else SUGGEST with an outcome the open work clearly leads to, else `SUGGEST: -`. It judges only the subjects open after the exchange. It writes `SUGGEST: -` when none is open, when the open subjects are unrelated pieces with no shared outcome, or when no outcome is clear, so it never makes a suggestion up. One open fix leads to shipping it, as after the met goal in `goal-wait`, and the call suggests that. An answer with none of these lines is asked once more for only that line, including an answer whose own lines meet the goal. Once the call answers `SUGGEST: -`, code notes the goal, open subjects and open asks it judged (`noGoalFor`), and does not ask once more while they stay the same. Code also does not ask once more while the Status holds nothing, before the first subject. So a session with no goal does not pay a second call at each NO CHANGE. Code applies the first answer's lines and adds only the GOAL or SUGGEST line of the second, so a second answer cannot drop the first one's subject lines. Code never writes a goal or a suggestion itself. After a met goal, the suggestion is the next outcome the finished work leads to.
    - Reason: in the Status call records from builds that had the rule to keep a suggestion, calls that read a met goal with no suggestion wrote SUGGEST in 2 of 26, in 3 sessions, and calls that read no goal in 2 of 1,336. Nothing in the prompt asked for it on a given exchange. A person who finishes a goal expects to see the follow-up.
    - Reason for the clear-outcome bar: the goal rules say to wait when the next goal is not clear and never to make a suggestion up. A suggestion for every open subject would turn a few unrelated asks into a goal.
    - Reason it judges only the subjects open after the exchange: told to write `SUGGEST: -` for "a few unrelated asks", both agents wrote it in 6 of 6 runs of `goal-wait` step 1, where a typo fix closed in the same exchange and the share sheet fix was the only open subject (`status-2026-11-19T11-34-37.865Z.json`).
27. **A head description never adds the work that comes after the work under way.** The prompt's example of a description reads "Fixing the sync bug for the 2.5 release", and the rule names "then shipping 2.5" as what it never does. The status rule `head-no-queued` fails a description with a word that puts work after it, such as "then" or "after that".
    - Reason: the prompt's own example, "Fixing the sync bug, then shipping 2.5", taught the pattern, and descriptions that add queued work reached the page.
28. **The page says it is not updated once five Status calls in a row read a reply with agent work and changed nothing.** The status line under the tabs, where a failed update shows, reads "Not updated in 2h", with the time since a Status call or the person last changed what the page says. A call counts when it read a reply after which the agent had done something. A call during a turn does not count, and a goal the person sets, edits or removes counts as a change. A failed Status call or a failed update shows in its place. A Status saved before this build shows no line until a call changes it (`hooks/status-freshness.ts`).
    - Reason: in the Status call records of 11-18, 0.7% of calls came after five or more such calls with no change, in 13 of 543 sessions. The change that ended a long run touched no more subjects than one after a short run, so the page had fallen behind rather than waiting for a large change. Time alone is a poor sign, since most long gaps were the person away. That count included calls during a turn, so counting only replies gives the same rate or a lower one.
    - Reason calls during a turn do not count: one runs every 10 minutes of a long turn and reads work that has not finished. A turn spent on one subject leaves a correct page unchanged, and five such calls would call it stale. The reply that ends the turn counts.
    - Reason a goal press counts: the person just changed the page, so it is not behind.
29. **A milestone never shows blank while open work serves it.** A GOAL line may give each milestone where it stands after a colon, and a milestone keeps its text when its work starts. The Status call reads an open milestone that open work serves and that has no text marked "no text", and writes it. Until then the page shows how much of that work is done, as "1 of 3 done". The status rule `milestone-text` fails a call that read such a milestone and left it blank.
    - Reason: replayed through the code before this change, 49.1% of open milestones shown after a call had no text (1,343 of 2,736, in the records of 10-28 to 11-19). Among those with open work linked, 42.0% had none (742 of 1,765). A blank milestone over working rows tells the person nothing about where it stands.
    - The code alone moves little that people see. In a later copy of the same records, the pages the recording builds saved were already blank for 35.3% of open milestones with open work linked (619 of 1,754). Replaying their answers through this code leaves 606 blank, 0.7 points fewer. What changes on the page is the "N of M done" count in place of a blank. Whether the call now writes the text, only the evals measure.
30. **Once no work is under way, the head shows its title alone.** Work is under way while a subject is working or waiting, an open ask holds one up, or a running child works on one. When an answer leaves nothing under way and finishes the work the head's description was about, code clears the description. Under a kept title, that work is any subject that was open before the answer. Under a new title, it is a subject that was working or waiting before the answer, or one the answer started. Whenever nothing is under way, a description that names a finished subject by every word of its name also clears. A side fix that starts and finishes while the head's own work waits queued leaves the description. While nothing is under way, a HEAD line that keeps the title changes nothing in the answer that finishes the last work, or while the head has no description. In a later answer it corrects a description the head kept, as when work is paused back to queued. A HEAD line with another title still applies, except where decision 22's hold keeps the head (`hooks/status-ops.ts`). The prompt asks for a description only while a subject is working or waiting. While work is under way, code clears a kept title's description that names a subject the answer closed, whether the waiting started in that answer or earlier. The status rule `head-no-finished` fails a description that names a finished piece once no piece is working or waiting, and `head-title` allows a head with no description then.
    - Reason: in the 0.5.1 live pass ([#640](https://github.com/petekp/inbox/issues/640)), once both parts of the work were done the head read "Adding --repeat, deciding pad() trimming" for three calls. A description says what the session is doing about its focus. Once nothing is under way, a description written while it was is untrue, whatever its words, so code clears it without reading them.
    - Reason code clears the description instead of taking the call's new one: taking the description the call wrote in the answer that finished the last part made `head-follows` fail far more often than without it, since the call rewrote it into what comes after the work, such as "Watching crash reports after the release".
    - Reason for the hold on a line that keeps the title: in the answer that finishes the work, and once the description is gone, a description under the same title either tells what comes after the work or retells finished work. The title alone is true, and the rows below show what finished. Without the hold, the Explain after the last answer in the `head-after-done` replay moved the description to the finding being explained in 3 of 4 runs.
    - Reason a side fix that was already under way before the answer clears the description: code cannot tell which subject a description was about. Once the last work under way closes, nothing the description says is being done. A side fix that starts and finishes in one answer never was the session's work under way, so the description over the queued work stays.
    - Reason waiting counts as under way: a release waiting in store review is still what the session is doing, so "Getting 2.5 through store review" stays when a side fix closes.
    - Reason an open ask or a running child counts as under way: a subject queued behind the person's answer, or one a delegate works on, is still the session's work. Without them, the answer that asks a question about its only open subject would clear the description that names it.
    - Reason a later same-title line corrects a description the head kept: a description an earlier build saved, or one kept while work was paused back to queued, can stay untrue. Without a correction it would stay until work started again.
    - Rejected: a prompt block that asks for a description once nothing is working, as the next-goal ask does. It rests on the call's judgment in the moment where the call writes what comes after, and its retry costs a second call. Also rejected: a description code builds from the finished subjects, such as "Done: --repeat, pad() trimming". Code does not derive the head from the subjects (decision 22), and it would repeat the rows just below it.
31. **A reply that says work finished closes it, and nothing waits on the person without an ask.** When the reply says work is finished, merged, pushed to the main branch, published or shipped, even in passing at the end of a long reply, the Status call writes DONE for each open subject and milestone that work finishes, and HEAD when the head's description names it. NO CHANGE is wrong then. A subject waits on the person only through an open ask, so the call never writes that a subject waits on the person's check or answer. Each working or waiting subject idle a day gets its own line through the `<idle>` block (decision 4). The `finished-pass` replay checks both.
    - Reason: in a recorded session, three Status calls in a row answered NO CHANGE after replies that said the work was finished, merged and pushed and that nothing waited on the person. The head kept saying the review was under way, a milestone stayed working with no work linked, and a fix kept saying it waited on the person's check, a day after that check stopped mattering. The `<idle>` block listed only working subjects then, so nothing asked the call about the waiting fix.
    - Reason no subject waits on the person without an ask: the inbox shows what waits on the person through asks. A subject that says it waits on them, with no ask behind it, points at nothing they can answer.
