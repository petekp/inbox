# Client parity

Status: built

Every feature works the same way for the person in every client, unless a host cannot do it. This plan records how the hosts differ today, and the steps that close the gaps.

## Terms

- **Host:** a program that runs the inbox for one agent. There are three: the Claude Code mod, Codex and omp. Their ids in `hooks/clients.ts` are `claude-code`, `codex` and `omp`.
- **Look:** one drawing of the inbox. There are four: the Claude Code terminal, the Claude desktop app's pane, the Codex tab and omp's panel. The mod draws the terminal and desktop looks.
- **Parity record:** `hooks/clients.ts`. For each host and feature it says `full`, `different` or `unsupported`, with a reason for the last two. `scripts/check-structure.mjs` fails when an entry that is not `full` has no row in "Differences on purpose" in `docs/looks.md`.
- **Catch-up:** rebuilding the ledger from the whole conversation, instead of from one reply's exchange.

## Decisions

- Every feature is designed for every client. A gap needs a real host limit as its reason. "Later" is not a reason.
- The choice between designs is made for the person's experience.
- Codex and omp get catch-up, as the mod has it. When a host first sees a session that already has turns, or after a failed update, the next update reads the whole conversation.
- Codex reads shell output, such as PR links and URL lines, from the rollout at Stop. It adds no PostToolUse hook.
- Which links a row may open stays a rule of each host.

## Steps

1. **Parity record and its check.** Add `hooks/clients.ts` with all three hosts and the check. Fix the drift in `docs/looks.md` and `docs/plans/omp-look.md`.
2. **One list for the `record` and `close` tools.** Built: `agentTools(host)` in `hooks/tools.ts` returns each tool's name, description and schema. The mod, Codex, omp and both eval probes build their lists from it, and each keeps its own registration and handlers. The names, descriptions and schemas each agent receives are unchanged.
3. **Shell output in every host.** One shared function in `hooks/session.ts` reads a command's output for local URLs and PR links. The mod calls it from its tool-call handler, Codex from the rollout at Stop, and omp from `tool_result`. Built: `commandFindings` returns the activity lines and PR links, and `noteCommandOutput` applies them to a session, linking only PRs that are new. Codex's `turnIn` in `codex/src/transcript.ts` reads the turn's `CommandExecution` rows, or older shell calls and outputs. A turn that has any `CommandExecution` row uses only those rows, because Codex 0.163 writes both shapes for the same command and merging would count it twice. A turn that mixes the shapes for different commands is not handled. Codex links the PR when the turn ends, which `hooks/clients.ts` records as `different`.
4. **Share `flattenConversation`.** Built: `hooks/conversation.ts` holds `Turn` and `flattenConversation`, with the clipping rules the mod's `transcriptText` had. The mod maps Claude Code's messages to turns, Codex maps its rollout, and omp maps its session branch.
5. **Run `runSessionScript` against Codex storage.** Built: `codex/tests/session.spec.ts` runs the shared session script through `codexStore`, as `omp/tests/session.spec.ts` does for omp.
6. **Update policy and catch-up.** Built, with step 4. `UpdateHost` has an optional `catchUp` member that has the inbox model read the whole conversation and returns its answer unapplied (`CatchUpReply`: a reply, a failure, or an unreadable conversation). `runUpdates` applies it. It catches up when `needsCatchUp` says so: the ledger is `failed` or `behind`, or turns started with nothing pending and no turn running. A catch-up covers the exchanges pending when it began. One that gets no usable answer ends the run. A conversation a host cannot read runs the pending exchanges instead. The mod's `catchUp` forks the conversation, or reads the transcript. Codex's reads the rollout (`readRollout`), and omp's reads the session branch (`conversationOf`), both through `askOverConversation`. The first hook of a Codex session the inbox has recorded nothing of, and omp's `session_start` and `session_switch`, mark the ledger `behind` when earlier turns exist. A reply dropped after two failed updates sets `presence.hasDroppedReply`, which keeps the warning until a catch-up covers it. Codex and omp start an update when an exchange is pending or the ledger is not current. They do not start one for turns started with nothing pending, which only the mod does.
7. **Move the mod onto `sessionView`.** Built. `sessionView` takes `canCatchUp`, whether the host can read the whole conversation. The update-failed warning adds "It retries after your next message." when `canCatchUp` is true or an exchange is pending. The mod and omp always pass true. Codex passes whether the session has a `transcriptPath`. The mod draws its view, the status line and the demo through `sessionView`. While the sample shows, `drawnSession` overlays its ledger, PR views, presses and turn counts on the real session, since a `DemoCopy` is not a `Session`. The mod's PR groups still come from its own `drawnPrs` calls, not `SessionView.prs`.
8. **The remaining gaps.** PR arrivals in the Codex tab, the PRs empty hint in omp, and the ledger of a forked conversation in Codex and omp. Built: PR arrivals in the Codex tab (`prRowIds` and `isPrsTabEmpty` in `hooks/arrivals.ts`, used by the mod, omp and Codex; a PR row in the Codex tab appears without the entering move, as in the mod, which draws no row motion); the PRs empty hint (`prsEmptyHint` in `hooks/pr-tab.ts`, with each host's word for a conversation) and the forked ledger. `forkedFrom` in `hooks/session.ts` gives a fork whose ledger is empty the parent's ledger and nothing else, as the mod does. Codex reads the parent from `forked_from_id` in the rollout's first row at the fork's first hook. omp reads it from the session file that `session_switch` with reason `fork` names. Both copy only when the parent saved a card, an item or a finding (`hasLedger`); otherwise the fork catches up over its conversation. A copied ledger is not caught up, since a catch-up from the branch would offer back what the person already closed. A gap that proves to be a host limit stays, with its reason in `hooks/clients.ts`.
