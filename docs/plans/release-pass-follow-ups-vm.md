# Live pass in the VM: follow-ups

Part of [Scripted release pass: follow-ups](release-pass-follow-ups.md). These are gaps in step 4 of `docs/release.md`, the live pass in the `inbox-ui` VM.

Status: building. Each item stays until the change that does it lands.

## Setting up the guest

- **Check the guest's Claude sign-ins before the pass starts.** In the 0.3.0 pass on b23bb169, both Claude sign-ins in the `inbox-ui` VM had expired. `claude auth status` read `loggedIn: false`, and the Claude app showed "Claude Code needs a new sign-in". Every Claude Code and desktop row then waited for the owner to sign in through Screen Sharing. A step in "3. Get the VM ready" that runs `claude auth status` in the guest and looks at the Claude app before the first row would catch an expired sign-in while the owner is still at hand.
- **Point the PR rows at a test repository.** Section 3 of `docs/release.md` asks for "a sample project whose GitHub remote has an open PR", and the PR order row needs three. The guest's `gh` is signed in to the owner's real account, and 0.6.0's pass ranked and pressed a real PR in another repository by mistake. The pass at 889ce236 made a private test repository, `petekp/inbox-release-sample`, with three open PRs, and set it as `~/greet`'s `origin`. Naming that repository in section 3, and a step before the PRs row that runs `git remote -v` in the sample project, would catch a pass that ranks or presses real PRs.
- **Rerun `check.sh` while the pass holds the slot for the VM.** Section 1 runs `check.sh` through `./scripts/inbox-slot run`, and section 3 takes the slot for the VM with its pid. When `next` moves while the VM is up, as it did in the pass at 889ce236, `run` would wait on the pass's own hold until the VM shuts down. That pass ran `check.sh` directly under the VM's hold, with the guest idle. A sentence in section 1 saying which to do would catch a pass that waits on itself, or one that runs `check.sh` beside another session's VM.
- **Install Herdr in the VM when it is set up.** The `inbox-ui` VM had no Herdr app. The 0.3.0 pass copied the host's Herdr.app and herdr-core into the guest by hand, and the pass names no Herdr version to test. A setup step that installs the newest Herdr in the guest, with the version recorded, would catch a Herdr look that cannot be run at all, or one run on an old Herdr.
- **Hold the Claude app's version for the pass.** The Claude app updated itself from 4.4212.0 to 5.11492.5 at its restart during the 0.3.0 pass, so the desktop rows ran on two app versions, and the first issue report named the wrong one. The pass should record the app version at each desktop row, or turn off the app's updates for the pass.
- **Free the guest's disk.** The guest had 2.9 to 4.4 GB free during the 0.3.0 pass, and macOS showed "Your disk is almost full". A pass that copies builds and keeps captures can fill it mid-row. Setup should check `df -h ~` in the guest and clear old builds and caches first.
- **Give the guest a Claude sign-in with the plugin guard.** On Team and Enterprise sign-ins, and with a managed settings file, a guard runs ahead of user mods and skips the mod's `classic.*` hooks. In the 0.3.0 pass the guest was signed in to a personal plan and had no `/Library/Application Support/ClaudeCode/` folder, so the guard never loaded. A notice the owner saw on a guarded Mac when opening the pane from `/inbox` could not be reproduced, on the build under test or on v0.3.0. Setup should add a managed settings file that turns the guard on, or sign in to a Team account, so the desktop and terminal rows also run the guarded path.
- **Herdr themes need `appearance` in settings.json.** In the 0.3.0 pass, `herdr-app do app.theme` changed the drawn theme only after the app's `settings.json` named an `appearance`. The Themes and width row should say so, or a run reads one theme twice. In the 0.5.0 pass on dd224dfe, setting `appearance` to `light` or `dark` alone switched it, and `app.theme` with `light` failed with `no theme "light"`.
- **Give omp in the guest a model.** omp in the `inbox-ui` VM has no model sign-in, so it records nothing. In the 0.5.0 pass the Herdr look's host rows, Reload omp and the omp Asks rows could not run with omp, since no row existed to press. Setup should sign omp in inside the guest, with a key kept in the guest, or a run skips every omp row in Herdr.
- **Answer Herdr's microphone prompts once at setup.** In the 0.5.0 pass, Herdr in the guest asked for microphone access mid-row, and the dialog covered the panel. Setup should answer it before the first capture, or a row's capture shows the dialog instead of the panel.
- **Make the Codex saved-state thread in the app.** In the pass at 059e65ac, the thread saved by 0.6.0 was made with `codex exec`. Its rollout reads originator `codex_exec`, and the inbox's Codex hooks skip exec sessions on purpose, so `heard` stayed null and every hook row had to move to a new chat. Saying in "3. Get the VM ready" that the Codex session must start in the ChatGPT app or the interactive `codex` would catch a Saved state row that cannot reach the hook rows.
- **omp's earlier-answer line needs a question history 7 days old.** `isEarlierShown` draws the line only once `BASELINE_MS` has passed since the history began, and omp's history in the guest lives under its own `XDG_STATE_HOME`. In the recheck at 879fcf8f it was an hour old, so omp drew no line and the row could only be read from the saved match. Copying a history older than 7 days into omp's state folder when the guest is set up would let the omp look see the line.

## Rows whose steps miss what they check

- **One question per turn in the Codex dialog step.** Asked for two questions, Codex put both in one two-page dialog. The step then cannot answer one question and close the other with its ✕, and the 0.2.14 pass needed an extra turn to check that a dialog closed unanswered leaves an Asks row. Asking for one question per turn would keep that check in the step. In the 0.3.0 pass on b23bb169, asked to "use your question tool", Codex recorded the question with the inbox's `record` tool and asked it in plain text, so no dialog opened. Naming the tool, `request_user_input_async`, opened one. The step should name it, or the run checks the Asks row of a recorded question instead of a dialog's.
- **The PRs row needs an open PR of yours.** A PR that is merged or closed when the inbox first reads it stays off the tab (`isLeftOut` in `core/domain/pr-fetch.ts`), and so does one someone else wrote. In the 0.3.0 pass, linking two merged PRs left the Codex PRs tab empty, and the sample project has no remote, so the tab read "Could not read the PRs: no git remotes found". The row should say to link an open PR you wrote. Its `gh` step should also wait out `PR_SHARED_MS` (2 minutes) before reopening the tab, since a fetch no press asked for reuses a view read within that time. Without both, the row passes on an empty tab or fails on a cached view. The same sample project kept the Herdr PRs tab row from showing a PR's two forms and from running Clear merged and closed.
- **Press Undo before the capture.** The Finding row's Undo lasts `SETTLED_MS` (5.12 s). In the 0.3.0 pass, a capture between Dismiss and Undo took about 6 s, so the row folded before Undo was pressed, and the next try clicked during the short "Sending…" before Undo showed. The row should say to press Undo between 1 and 4 seconds after Dismiss and capture after it. That would stop a run's own timing from reading as a broken Undo.
- **The Herdr PRs tab row's empty-tab result is wrong.** It says that with no PRs on the tab and `gh` renamed, the hint shows "with no banner and no Refresh PRs". The shared plan in `core/view/pr-refresh.ts` draws Refresh PRs there, and so do the terminal and Herdr looks. The row should expect Refresh PRs, or a run fails a look that matches the shared plan.
- **The Herdr Update row needs a Codex session start.** `codex plugin add inbox@inbox` alone did not put the shipped mod back in `mods/inbox/`. Starting the Codex CLI in a Herdr terminal did. The row should say to start a Codex session after the reinstall, or a run reports a broken Codex update that is only an unfinished step.
- **The Ended Codex thread row cannot run in the Herdr panel.** The panel drops an ended session's rows and reads "The session ended. This terminal is back at its shell.", so no Answer press is left to send. In Codex 0.169, `/quit` also only disconnects: the thread runs in `app-server-daemon`, which outlives the CLI. The row should name a way to reach an ended thread's row, such as the terminal look, or be dropped from the Herdr table.
- **The Codex CLI rows need `codex` on PATH.** The ChatGPT app's bundled CLI run by its full path gets ENOENT on every ledger and Status call ([#423](https://github.com/petekp/inbox/issues/423)). Until that is fixed, a run should put the bundled CLI's folder first on PATH before the first Codex CLI session, since the daemon keeps the environment it started with.
- **omp's fresh `HOME` breaks the Herdr rows.** `docs/release.md` runs omp with a fresh `HOME`, and `hc` finds the Herdr app's server under `$HOME/.local/state/herdr-core`. In the second 0.3.0 boot on 6675d57c, `hc` made a new empty state folder under omp's `HOME`, the report failed with `no terminal "t1"`, and the panel read "No inbox in this terminal". The rows ran once that folder was a link to the real one and omp started with `HERDR_APP_HOME` set and `HERDR_PANE_ID` unset. The omp and Herdr sections should say so, or every Herdr row with omp fails for a reason that is the run's own.
- **The #359 check needs more than 40 ended sessions.** The 0.3.0 pass had 39 ended sessions in the store, under the limit of 40, so opening a second session pruned nothing and the prune path did not run. The row should first make sure the store holds 40 or more ended sessions.
- **The desktop Saved state row needs a session the signed-in account lists.** The guest's account listed none of the guest's earlier desktop sessions, so no session the old build saved could be opened. Setup should save one under the account the pass signs in with.
- **The desktop reopen rows need a way to reach an older conversation.** In Claude app 5.11492.5, the back arrow did nothing after an app restart, the `/resume` picker listed only conversations started in the terminal, and search listed only conversations the signed-in account knows. Search also shows private session titles, so its captures had to be deleted. The rows that reopen a conversation should name the path: start the conversation in the terminal in the sample project, then reopen it from `/resume` with "This folder" selected.

- **The Tabs row looks for the Help version on the wrong line.** It says Help's last line reads `Inbox v<version>`. Since d355adba, the terminal's Help draws the version at the right end of its Keys title, and the desktop pane still draws it last. In the 0.5.0 pass on dd224dfe, the terminal's last line held no version. A run that reads the last line fails a correct build, or learns to skip the step and then misses a version that is gone. The row should say where each look draws it.
- **The PR order row needs PRs linked to the session.** `order_prs` links no PR. A PR shows on the tab once the session opens it, links it, or its branch has one, and a reply that names a PR's URL links it (`endTurn` in `core/runtime/session-turns.ts`). In the 0.5.0 pass, the order showed only after the agent's reply named all three URLs. The row should say to have the reply name each URL first, or a run sees "No PRs" and reports a broken order.
- **The Collapse row's title steps do not apply in omp.** omp's panel takes keys only, so there is no title to press, and a key typed while the reply field is open goes into the field. In the 0.5.0 pass, the omp run closed the field with Escape and then used `z`. The row should name those keys for omp, or a run reports steps it could not take.
- **No look showed "Checking for PRs…".** The Empty tabs row expects it while the PRs tab reads. In the 0.5.0 pass the read finished before each capture in the terminal, desktop and omp looks. The slow `gh` stand-in from "A slow gh in each look" in [release-pass-follow-ups.md](release-pass-follow-ups.md) would hold the read long enough to capture, and would catch a tab that shows "No PRs" before its read ends.
- **The Task row expects "✓ Copied" in the Codex tab, which cannot copy.** The tab's frame has no clipboard access, so a copy press shows "Could not copy …: this tab has no clipboard access" and a box to copy from by hand ([#550](https://github.com/petekp/inbox/issues/550)). In the 0.5.0 pass on dd224dfe the Codex run failed the row on that. Until #550 lands, the row should give the Codex result, or every Codex run fails a row whose fallback works as built. A run should also empty the clipboard before the press, since in that pass the clipboard already held `npm login` from the desktop row.
- **The Herdr Help row expects keys per tab.** The Herdr panel's Help draws one page of keys on every tab. In the 0.5.0 pass on dd224dfe the page matched the look's own keys, so the row passed on that page. The row should expect one page, or a run fails a look that draws what it is built to draw.
- **The Herdr Install row cannot reach the Codex CLI's install.** Codex installs a missing Herdr mod only when `herdr-mod.json` holds `yes` (`modStep` in `core/remote/herdr-install.ts`). Any host's Install press saves `yes` and then `installed` once the mod is in place, so no run leaves `yes` behind. In the 0.5.0 pass the Codex CLI step ran only after `yes` was written by hand. The row should say to write it, or a run reports a broken Codex install.
- **The Herdr Following row's ended form depends on the host.** The panel reads "The session ended. This terminal is back at its shell." only while the terminal still carries the session's label. In the 0.5.0 pass, omp's `/exit` removed its label, so the panel read "No inbox in this terminal". Claude Code left its label, and so showed the ended form ([#553](https://github.com/petekp/inbox/issues/553)). The row should give each host's expected form.
- **The Herdr Status seen row is out of date.** It waits on #400, which closed unmerged. [#487](https://github.com/petekp/inbox/pull/487) fixed #388 by having the panel write a look file. The row also needs finished rows on the Status before the look. In the 0.5.0 pass, two short jobs left the Status empty. The row should drop the wait and start from a turn that finishes a milestone.
- **The Herdr Delegate row's helper ends before any Status call.** A `claude -p` helper that ran about a minute finished inside the turn. The mid-turn Status call waits 10 minutes, so the Status after the turn showed no helper row. The row should start a helper that outlives the turn, such as `hc run --bg` with no wait.
- **No row runs a turn past 10 minutes.** The mid-turn Status call runs only once a turn has gone 10 minutes, and a turn that long often holds more than 40 activity lines. Before #549, the Status then stopped changing, and no row would have caught it. In the 0.5.0 recheck on ec725091, a desktop turn of 95 Bash calls showed "81 of 95 calls done" at 10m35s, a count only the latest activity lines held. A Status row step should run such a turn and read the Status after 10 minutes, or a mid-turn Status that stops updating ships unseen.
- **The PRs row with `gh` renamed shows its banner only once a read is due.** In the pass at 059e65ac, the desktop pane still showed cached PRs with Merge, because `prSync` in `core/view/sync-state.ts` keeps a read fresh for `PR_FRESH_MS` and a missing `gh` is not a failed fetch. Herdr showed no banner in 15 s with `gh` renamed. Telling the row to press Refresh PRs, or to wait past `PR_FRESH_MS`, would catch a pass that reads a fresh cache as a missing banner.

## Driving and capturing

- **Start the terminal look with `CLAUDE_CODE_NO_FLICKER=1`.** In the 0.5.0 recheck, Claude Code 2.1.326 in a 142-column tmux opened the pane inline without it and docked with it. `docs/release.md` does not name the variable, so a run can check the docked rows on the inline pane without knowing.

- **Capture moves with a frame burst.** A capture per click, about 350 ms apart, missed an answer press's "Sending…" and every fade in the Herdr panel. One VNC connection that captures about every 55 ms and tiles the frames into a grid caught a row's buttons moving 24 pt ([#420](https://github.com/petekp/inbox/issues/420)). The pass should ship such a tool and name it in the Presses and Themes and width rows. A VNC capture returns only once the screen changes. Frames then come about 75 ms apart during a move, and the tool must move the pointer at the end so the last capture returns. A click sent on the capturing connection waits behind the capture, so presses should go through a script in the guest.
- **Name how each look takes keys.** In the terminal look, Ctrl+X Tab missed once and `j` went to the agent as a message. `/inbox` moves focus into the pane every time. In Herdr, `u` did nothing right after a click on the Finds tab, and Tab and Shift+Tab reach the pane's buttons. In the 0.5.0 pass, the Herdr panel's keys did nothing after a reply was sent until a click on an empty part of the panel. Clicks also do not reach Claude Code's band in a Herdr terminal, so its Open inbox could not be pressed. The Keys rows should say how to give each look focus.
- **Resume a stopped host with `fg`, or run it under `script`.** For Press nobody takes, `kill -STOP` on a host in a shell's foreground leaves it in the background after `kill -CONT`. `fg` brings it back, and Claude Code may then take the terminal's next reply as typed text. In a Herdr app terminal, `fg` fails: the terminal's shell re-runs itself with `exec "$0" -li`, so the stopped host is orphaned, and in the 0.5.0 pass it was lost. Starting the host as `script -q /dev/null claude` kept it in place, and `kill -CONT` resumed it. The row should say so for each look.
- **`omp -p` waits on stdin.** A scripted omp turn hangs until stdin closes. Run it with `< /dev/null`.
- **Loading a debug copy in the Claude app.** `CLAUDE_CODE_PLUGIN_DIRS` in `settings.json`'s `env` did not load a folder in Claude app 5.11492.5. Replacing the installed folder in place did. Run `claude plugin validate <folder>` on a debug copy first: the engine refuses a mod that spells `$` other than `$.noun.event(…)`, and then sends `/inbox` to the model as a prompt.
- **Running the omp look off the test machine.** In the 0.5.0 pass, the omp look ran on the working Mac while the VM was lent to a fix. A fresh `HOME` does not cover two steps. The Task row's copy runs `pbcopy` from `PATH` and overwrites the host's clipboard, and the `gh` rename moves `/opt/homebrew/bin/gh` for every session on the host. A stand-in `pbcopy` first on `PATH` that writes to a file took the copy and showed what it copied. The `gh` rename was not run. The omp section should give that stand-in and say the `gh` steps need the test machine, or a run off the VM changes the host's clipboard and breaks `gh` for other sessions.
