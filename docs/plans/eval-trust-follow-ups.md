# Evals the release can trust: follow-ups

Part of [Evals the release can trust](eval-trust.md).

Status: building. Each item stays until the change that does it lands.

Each item names what it would catch. Remove an item when the change that does it lands.

The Status replays' facts and rules have their own list, in [eval-trust-follow-ups-replays.md](eval-trust-follow-ups-replays.md), the Status checks set aside theirs, in [eval-trust-follow-ups-set-aside.md](eval-trust-follow-ups-set-aside.md), the Status judge and its hand-written pages theirs, in [eval-trust-follow-ups-judge.md](eval-trust-follow-ups-judge.md), and the Status head rules theirs, in [eval-trust-follow-ups-head.md](eval-trust-follow-ups-head.md). What an agent in the agent suite can reach beyond the stand-in inbox has its own list, in [eval-trust-follow-ups-isolation.md](eval-trust-follow-ups-isolation.md), and the agent cases about merging a PR theirs, in [eval-trust-follow-ups-merge.md](eval-trust-follow-ups-merge.md).

- **A second `--set-baseline` run refuses after the first one saves.** `finish` in `evals/harness.ts` saves no baselines when the tree has uncommitted changes, and the first run's own write to `evals/baselines.json` is one. On 2026-11-21 the omp run of the three merge cases (`agent-2026-11-21T21-33-26.455Z.json`, $4.23 metered) saved nothing for that reason alone, since its only change was that file. Leaving `evals/baselines.json` out of the uncommitted-changes check when setting baselines would catch it.
- **`no-task-for-own-step` separates weakly on Claude.** Without the guidance it passed 3 of 5 on one run and 1 of 5 on another, so a run of 5 does not reliably tell guided from unguided. A case where the unguided agent fails every run would catch the loss of the "take the step yourself" rule.
- **Most agent cases pass on Claude with only the tool texts.** In the control at ff9f3648 (`--no-guidance --runs 3`, `agent-no-guidance-2026-11-19T07-57-28.552Z.json`), 38 of 43 cases passed 3 of 3 with only the tool texts and the `inbox:` texts. Three runs bound each unguided pass rate only above 0.37 (95% one-sided). Only `close-done-finding` and `inferable-choice-not-asked` failed every run. If the guidance's other rules were cut, garbled or truncated past the 4096-character cap, most of those 38 could still pass. A case for each rule that fails without it would catch that. Codex and omp were not run.
- **The direct-question rule under realistic replies.** `no-finding-user-only` passes 5 of 5, but in 0.2.10's live pass the agent missed the rule three times. Opus ended replies with "let me know which you prefer" and "I recommend no". Haiku ended one with "my recommendation: accept both". Cases where the reply ends with a recommendation or a list of options would catch it.
- **No model-suite control without `systemText`'s rules.** The agent suite has `--no-guidance`, but no run takes the rules out for the model cases. Such a control would catch a case that passes on the model's own habits.
- **The agent suite on Haiku and Sonnet.** A past id leak (30e03f0) showed only on Haiku, and the desktop app in the release VM runs Haiku.
- **No-guidance controls on Codex and omp,** as step 2 ran on Claude, before M4 is run there.
- **M2, restoring the old rule for unrelated items.** Step 4 settled its cases, so it can run now.
- **A harder positional-answer case.** `close-answered-says-answer` passes, but in a live pass Codex saved "the second one" as the answer. A case with more options, or the answer in a longer message, would catch it.
- **A false "done:" close.** In 0.2.10's live pass, the inbox model closed a question the agent had just asked. Its reason was "done: sleep ran in foreground, so the question is moot", but the command had been blocked. The guard in `applyUpdate` catches only "no longer applies" reasons with no grounds. A model case would measure how often it happens.
- **`task-about-finding-replaces-it` back to its 0.2.9 rate.** It passes 16 of 20 on Sonnet, against 46 of 48 on 0.2.9's NEW rule. The live pass saw the miss: the inbox model added the question but wrote no ASKED line, so the finding stayed open.
- **Two Codex update processes whose Status calls run newer-first.** No test runs that order, because a test cannot make the newer call run first without a hold point in `codex/src/update.ts`. With one, a test would catch an older Status answer overwriting a newer one, which nothing prevents today: #153.
- **The two dismissed-question cases swing too much on Sonnet to judge a text change.** On `main` at 67f1c82, with the same text and model, they passed 13 and 21 of 32 in one run and 89 and 78 of 96 in the next. Most failures are not misses. `old-dismissed-question-stays-closed` fails on its `dropped: 0` check when the code has already dropped the repeated question, so nothing reaches the person. `dismissed-question-stays-closed` counts "Merge PR #41 now, without a feature flag?" as the dismissed question, because its `notNew` pattern matches any "flag". Passing a repeat the code dropped, and matching only the dismissed question, would let a run of these cases show what a text change did.
- **Check patterns that miss a correct wording.** `answered-question-follow-up-added` matched only "size", so Codex failed 2 of 8 runs that added the follow-up as "Should the product API cache use 64 MB or 256 MB?" (`model-2026-10-26T06-30-33.393Z.json`). Its pattern now also takes a size in MB. A pass over the other `new` and `notNew` patterns, against the wordings in past results, would catch a case that fails a correct answer or passes a wrong one. The agent suite's `reply` patterns need the same pass: `no-finding-progress` looks for "memoiz", and failed 2 of 5 Claude replies that described the per-request cache in plain words (`agent-2026-10-26T19-39-22.773Z.json`).
- **Two versions compared in separate runs.** The low run above ran beside two other eval runs, and the cause of its drop is not known. Running both versions in the same hour, one after the other, at 96 runs each, would keep load or a model change from reading as an effect of the text.
- **omp's inbox model,** and its fallback to omp's `@smol` model.
- **Agent cases showing the closed, carried-over and answer notes,** and Codex's guidance delivered as the plugin delivers it, at session start.
- **Agent cases that send the press messages.** Every agent reads the texts in `messages` in `core/domain/press-messages.ts`, but agent cases hold a fixed prompt, so no suite runs those texts. A case whose prompt is built from `messages.explain` or `messages.finding` would catch an Explain text that makes the agent rename a question's options, act on the item, or answer at length. With a draft of the short Explain text, 8 of 10 Claude replies did not use both listed names for "Redis / In-memory", and one called them "Shared store / Each its own".
- **An agent case that sends the Compare message.** `messages.compare` asks for a lot: work outside tracked files, a background subagent where one can run, a page built from the template with measures ranked by what the person would notice, a reply with no table, and a closing `record` of the question. A case whose prompt is `messages.compare` on a small repo would catch an agent that edits a tracked file, ranks the choices by how much code each takes, writes data the page cannot draw, or never records the question again. That last miss leaves the row reading "Comparing…" until the person presses Compare again or dismisses it. `record-repeat-adds-step` and `compare-page-step-is-built-page` cover only the closing reply and `record`, from a fixed prompt, since an agent case cannot build the page.
- **A reply that changes its recommendation and still leaves the old one showing.** `changed-recommendation-reaches-agent-question` passes 8 of 8 on Sonnet and on Codex, and every answer is a correct `UPDATE` line (`rec-update-ledger.json`). A live reply that changed its recommendation still left the old one showing. Its ledger answer was not looked at, so the cause is not known. A case built from that reply's wording would catch the miss.
- **A target counted as reproduced when its rule fails on another piece.** The status report lists a step's target as reproduced when its rule fails in 2 of 3 runs for any piece. Step 9 of Replay B targets `marks-true` on the Sync engine. Sonnet closed the engine in 3 of 3 runs, yet the report listed step 9 `marks-true` as reproduced, because each of its `marks-true` failures there named the Offline banner, which step 8 had left open (`status-2026-10-31T04-55-37.274Z.json`). Counting only failures on the pieces the step changes would catch a step reported as reproducing its target when the model handled the targeted piece correctly.
- **`order-prs-rank-again` on Codex fails when `gh` cannot reach GitHub.** The prompt names a made-up repo, `acme/shop`, and Codex has a shell, so in most runs it calls `gh pr view` first. The call fails, and Codex records a finding that it could not refresh the PRs, which the case's `record` count of 0 fails. It passed 2 of 5 with `gh` signed out (`agent-2026-11-02T07-08-05.113Z.json`) and 3 of 5 in the 0.3.0 release pass, where the sandbox blocked the network. The guidance asks for a finding when the agent works around a problem, so these findings may be right. A prompt that says the PR states it gives are current, or a check that allows a finding about the failed read, would let the case test the ordering rule.
- **An agent case that sends the Compare press's own message.** The three cases in `evals/agent-cases/compare.json` start after a background subagent has reported, with a prompt that quotes only the end of the Compare request. None sends `messages.compare`, so no case reads the opening that differs by host. A case that sends each host's Compare message and checks the reply holds the pick and the page's path in the same turn would catch a Codex agent that hands the work to a subagent and ends its turn, as #134 did.
- **Baselines for the cases of #38 and #25 at release.** `dismissed-question-stays-closed`, `old-dismissed-question-stays-closed`, `reason-not-recommendation` and `ask-names-finding-not-id` pass on Sonnet at 47% to 85% in the issues, so 5 runs cannot tell a fix from luck. The last two have no baseline. `ask-names-finding-not-id` passed 5 of 5 at 47c1b124 (`model-2026-11-03T08-22-22.994Z.json`), then 8 of 32 at dbc518ee (`model-2026-11-13T06-12-40.027Z.json` and its rerun). A 20-run `--set-baseline` at release would catch either issue coming back.
- **omp's reply can leave out the question it records.** In `close-already-closed`, 2 of 20 omp runs at 3701e97c recorded a new question and replied only "I've also put this question in your inbox." A check that the reply holds each recorded ask would catch it.
- **omp's stand-in shows the case's ledger without `upgradeLedger`.** `evals/omp-probe.ts` builds what omp is shown from the raw case ledger. An old Status shape there shows omp nothing.
- **`tab-open-needs-you-records-new-task` sits at the bar on Codex.** Codex kept the open question open after "ok, carry on" in 25 of 32 runs on `next`, and in 21 of 32 with the ledger text of the dismissed-findings change. The difference is within chance at that sample, and the case has no baseline. A 20-run `--set-baseline` would tell a real regression from noise. In the 0.5.0 release pass at e9ef852d, on Codex CLI 0.169.0-alpha.11.1, it passed 5 of 8, then 26 of 32 with its rerun. 0.4.0's pass had 7 of 8. That gap is within chance (Fisher's exact p about 0.57). Codex's system text hash matched 0.4.0's, but the runner hash did not, and this case's ledger goes through `upgradeStatus`, which changed. Printing `buildPrompt`'s output for this case at 3701e97c and at e9ef852d, with no model call, would show whether the prompt Codex reads changed.
- **Codex closes an unanswered question after "ok, carry on" in `status-shown-records-question` too.** It passed 24 of 32 at 3701e97c (`model-2026-11-15T07-25-34.986Z.json` and its rerun). Each failure closed a question with no rec as "Yes". Adding "A go-ahead that names no item, such as "ok, carry on", answers an item only with its rec. An item with no rec stays open unless the reply or <activity> shows it done or no longer applies." to the CLOSED rule kept it open in 10 of 10 Codex calls against 8 of 10. It was rejected: it made `agent-pick-not-person-answer` record the agent's pick as the person's answer in 5 of 5 against 0 of 5.
- **Two runs that start in the same instant write one results file.** `resultsPath` in `evals/harness.ts` names the file by the run's start date, to the millisecond. A Sonnet run and a Codex run of the Status suite started by two background commands at once both wrote `status-2026-11-05T23-33-02.484Z.json`, and the Codex run's write replaced the Sonnet run's, so only its log kept the Sonnet counts. Adding the agents or a random suffix to the name would keep both.
- **`no-finding-own-check` tells Claude it may run the tests in a session with no shell.** The prompt says the agent is allowed to run `npm test`, and the suite gives Claude Code no tool but the stand-in inbox's. On ac4026ea (2026-11-12) the case passed 17 of 20. In all three failing runs the reply said the session had no shell tool, and the agent recorded a finding that the tests were not run. The guidance asks for that finding when part of a change cannot be checked from where the agent is. Giving Claude a shell in this case, as Codex and omp have, would test the rule the case is about.
- **`inferable-choice-not-asked` was failing for lack of `cli.js`.** The sandbox was empty. omp looked, found no file, and recorded a question asking where it is in 5 of 5 runs on ffee0e44. Claude Code has no file tool and, in 0 of 5 runs on 35c45c7c, asked for the name because it could not check whether `-v` was taken. The case now has a `files` entry with a `cli.js` that parses `--quiet` and `-q`, and its prompt quotes the same file, so all three agents have the same facts. Still open: the reruns on all three agents, and that Claude Code gets the file only through the prompt.
- **No case has the person ask to record a question they answered before.** `earlier-answer-same` once said "Record that question for me". In `agent-2026-11-20T23-38-45.941Z.json`, omp saw the earlier answer in all 5 runs and kept the question open each time, reading the request as the person reconsidering. That reading is reasonable: a person's explicit "record this" may rightly keep a repeat open. The case now has the agent reach the question itself. A case where the person asks for a question they answered before, passing either a close or an open question that names the earlier answer, would catch an agent that drops the request or ignores the earlier answer.
- **`earlier-answer-same`'s prompt ending changed after its last run.** In `agent-2026-11-20T23-45-54.271Z.json`, all 15 runs closed the question as answered before. In 2 of 5 Claude Code runs the agent then went on to build the cache and recorded a second question asking where the code is, which failed the case. The prompt now ends at the choice: "Once the cache is chosen, tell me which one you will build with. Building it is a later step". That ending is first run at the next release pass, which would catch it still sending an agent after the code.
- **The earlier-answer cases that keep a question open would pass without the earlier answers.** `earlier-answer-covered`, `earlier-answer-follow-up` and `earlier-answer-put-off` each have the person ask for the question. A person's request alone can keep a question open, as omp showed on `earlier-answer-same`. So these cases cannot catch a `record` answer that leads agents to close a near miss wrongly. Prompts where the agent reaches the question itself would catch it. `earlier-answer-covered` also passes an agent that leaves open a question the person's own rule settles.
- **`record-question-with-0.3.0-tools` does not check the `record` answer.** On 35c45c7c it passed 10 of 10, but in the 77 runs of that suite told "record it again", no agent recorded again. So it would likely pass without the fix for #417. A `result` on its record check would catch a changed answer.
- **No agent case checks for a duplicate row after recording again.** A reworded record in the same turn still adds one, tracked in #406. A row count would catch it.
- **No agent case covers an answer worded as a question, such as "Sure, why not".** `close` may refuse it. A case expecting the close would catch that.
- **A question already answered in a dialog has no agent case for the tool answer.** A case that records after the dialog would catch a changed answer.
- **`evals/cases/dialogs.json` quotes a dialog answer Claude Code no longer sends.** Its activity lines use "User has answered your questions:", the wording of 2.0.77 and 2.1.100. Versions 2.1.318 to 2.1.323 send "Your questions have been answered:" or "The user answered:", whose closing words say "that you not proceed". Cases in that wording, and with "The user did not answer the questions.", would catch an inbox model that closes a question as No from those words, or as answered when nothing was.
- **The Status suite's page text leaves out the line that holds a held subject's ask, and its no-restating check would fail it.** `rowText` in `evals/status-page-text.ts` prints no `waitsOn`, so the judge reads a page the looks draw differently. `docs/plans/status/good-status.md` property 9 calls a copied question Bad. Printing the line needs `no-restating` scoped to text the model wrote. A held subject in a replay would then pass the check.
- **`scripts/eval.sh` states an old Status pass rule.** Its header says a replay fails a check "that fails at a step in more than one run of three". The rule in `evals/status-bar.ts` is an exact binomial test per check, and a replay step's target pools both models' runs. The 0.5.0 release report first copied the old rule and so misread which checks could block. Rewriting the comment from `status-bar.ts` would catch that.
- **`reload-step-is-task` sits at the bar on Sonnet, with no baseline.** It passed 8 of 8 on 11-13 and 11-15. At 00ef6f65 it passed 19 of 24, 17 of 24 with the first agent-wait skip, and 24 of 24 with the narrowed one. Each failure answered NONE and dropped the person's `/reload-plugins` step. A 20-run `--set-baseline` would tell a real regression from noise.
- **A one-model failure at one replay step rarely blocks.** A replay step pools both models' runs. At `coordinator-day` step 11, Codex left out the 2.6 milestone in about half its runs while Sonnet passed, and 6 runs cannot block that. The short case `goal-names-release` judges each model apart, but at 5 runs it blocks a 50% rate in only 19% of release runs, and at 12 runs in 61%. A case where the failing model fails nearly every run would catch such a change.
