# Evals the release can trust: follow-ups

Part of [Evals the release can trust](eval-trust.md).

Status: building. Each item stays until the change that does it lands.

Each item names what it would catch. Remove an item when the change that does it lands.

The follow-ups for the Status suite, its replays and its judge are in [eval-trust-follow-ups-status.md](eval-trust-follow-ups-status.md).

- **Agent cases that fail without the guidance,** one for each of its rules, so a change to `guidanceText` is tested.
- **`no-task-for-own-step` separates weakly on Claude.** Without the guidance it passed 3 of 5 on one run and 1 of 5 on another, so a run of 5 does not reliably tell guided from unguided. A case where the unguided agent fails every run would catch the loss of the "take the step yourself" rule.
- **A second agent case that separates guided from unguided runs on Claude.** With the guidance in `close`'s description, the control (`--no-guidance`, 5 runs) failed one case of 16, `no-finding-user-only` at 3 of 5. If the guidance's other rules were cut, garbled or truncated past the 4096-character cap, the other 15 cases would still pass. A case for each rule that fails without it would catch that.
- **The direct-question rule under realistic replies.** `no-finding-user-only` passes 5 of 5, but in 0.2.10's live pass the agent missed the rule three times. Opus ended replies with "let me know which you prefer" and "I recommend no". Haiku ended one with "my recommendation: accept both". Cases where the reply ends with a recommendation or a list of options would catch it.
- **The agent suite on Haiku and Sonnet.** A past id leak (30e03f0) showed only on Haiku, and the desktop app in the release VM runs Haiku.
- **No-guidance controls on Codex and omp,** as step 2 ran on Claude, before M4 is run there.
- **M2, restoring the old rule for unrelated items.** Step 4 settled its cases, so it can run now.
- **A harder positional-answer case.** `close-answered-says-answer` passes, but in a live pass Codex saved "the second one" as the answer. A case with more options, or the answer in a longer message, would catch it.
- **A false "done:" close.** In 0.2.10's live pass, the inbox model closed a question the agent had just asked. Its reason was "done: sleep ran in foreground, so the question is moot", but the command had been blocked. The guard in `applyUpdate` catches only "no longer applies" reasons with no grounds. A model case would measure how often it happens.
- **`task-about-finding-replaces-it` back to its 0.2.9 rate.** It passes 16 of 20 on Sonnet, against 46 of 48 on 0.2.9's NEW rule. The live pass saw the miss: the inbox model added the question but wrote no ASKED line, so the finding stayed open.
- **Two Codex update processes whose Status calls run newer-first.** No test runs that order, because a test cannot make the newer call run first without a hold point in `codex/src/update.ts`. With one, a test would catch an older Status answer overwriting a newer one, which nothing prevents today: #153.
- **The two dismissed-question cases swing too much on Sonnet to judge a text change.** On `main` at 67f1c82, with the same text and model, they passed 13 and 21 of 32 in one run and 89 and 78 of 96 in the next. Most failures are not misses. `old-dismissed-question-stays-closed` fails on its `dropped: 0` check when the code has already dropped the repeated question, so nothing reaches the person. `dismissed-question-stays-closed` counts "Merge PR #41 now, without a feature flag?" as the dismissed question, because its `notNew` pattern matches any "flag". Passing a repeat the code dropped, and matching only the dismissed question, would let a run of these cases show what a text change did.
- **Check patterns that miss a correct wording.** `answered-question-follow-up-added` matched only "size", so Codex failed 2 of 8 runs that added the follow-up as "Should the product API cache use 64 MB or 256 MB?" (`model-2026-10-26T06-30-33.393Z.json`). Its pattern now also takes a size in MB. A pass over the other `new` and `notNew` patterns, against the wordings in past results, would catch a case that fails a correct answer or passes a wrong one. The agent suite's `reply` patterns need the same pass: `no-finding-progress` looks for "memoiz", and failed 2 of 5 Claude replies that described the per-request cache in plain words (`agent-2026-10-26T19-39-22.773Z.json`).
- **Two versions compared in separate runs.** The low run above ran beside two other eval runs, and the cause of its drop is not known. Running both versions in the same hour, one after the other, at 96 runs each, would keep load or a model change from reading as an effect of the text.
- **omp's inbox model,** and its fallback to omp's `@smol` model.
- **Agent cases showing the closed, carried-over and answer notes,** and Codex's guidance delivered as the plugin delivers it, at session start.
- **Agent cases that send the press messages.** Every agent reads the texts in `messages` in `hooks/press-messages.ts`, but agent cases hold a fixed prompt, so no suite runs those texts. A case whose prompt is built from `messages.explain` or `messages.finding` would catch an Explain text that makes the agent rename a question's options, act on the item, or answer at length. With a draft of the short Explain text, 8 of 10 Claude replies did not use both listed names for "Redis / In-memory", and one called them "Shared store / Each its own".
- **An agent case that sends the Compare message.** `messages.compare` asks for a lot: work outside tracked files, a background subagent where one can run, a page built from the template with measures ranked by what the person would notice, a reply with no table, and a closing `record` of the question. A case whose prompt is `messages.compare` on a small repo would catch an agent that edits a tracked file, ranks the choices by how much code each takes, writes data the page cannot draw, or never records the question again. That last miss leaves the row reading "Comparing…" until the person presses Compare again or dismisses it. `record-repeat-adds-step` and `compare-page-step-is-built-page` cover only the closing reply and `record`, from a fixed prompt, since an agent case cannot build the page.
- **`carry-status-answers-where-we-are` cannot pass, and 0.2.13 and 0.2.14 shipped with it waived.** It failed 0 of 5 on Claude, each reply without "queue". The case saves an Status in the shape from before subjects, with `headline` and `status`. `message()` in `evals/agent-cli.ts` spreads it into the ledger without `upgradeStatus`, so `statusCarryText` finds no head and carries nothing. The agent never sees the headline it is asked about. Passing the case's Status through `upgradeStatus`, or rewriting it with `head` and `subjects`, would let the case test the carry again.
- **The `runner` hash changes with code no model reads.** It hashes the esbuild bundle of the eval runner, which pulls in `hooks/gh.ts`, `hooks/pr-tab.ts` and `codex/src/run.ts`. #175 changed only gh's exit codes, and every other hash in the results files still matched. Yet `--with` (`evals/harness.ts:168`) would refuse those files as having run other code, so the release carried them over by hand. A hash of only the code that builds prompts and grades answers would let `--with` and a release tell a change the models read from one they don't.
- **A reply that changes its recommendation and still leaves the old one showing.** `changed-recommendation-reaches-agent-question` passes 8 of 8 on Sonnet and on Codex, and every answer is a correct `UPDATE` line (`rec-update-ledger.json`). A live reply that changed its recommendation still left the old one showing. Its ledger answer was not looked at, so the cause is not known. A case built from that reply's wording would catch the miss.
- **`order-prs-rank-again` on Codex fails when `gh` cannot reach GitHub.** The prompt names a made-up repo, `acme/shop`, and Codex has a shell, so in most runs it calls `gh pr view` first. The call fails, and Codex records a finding that it could not refresh the PRs, which the case's `record` count of 0 fails. It passed 2 of 5 with `gh` signed out (`agent-2026-11-02T07-08-05.113Z.json`) and 3 of 5 in the 0.3.0 release pass, where the sandbox blocked the network. The guidance asks for a finding when the agent works around a problem, so these findings may be right. A prompt that says the PR states it gives are current, or a check that allows a finding about the failed read, would let the case test the ordering rule.
- **An agent case that sends the Compare press's own message.** The three cases in `evals/agent-cases/compare.json` start after a background subagent has reported, with a prompt that quotes only the end of the Compare request. None sends `messages.compare`, so no case reads the opening that differs by host. A case that sends each host's Compare message and checks the reply holds the pick and the page's path in the same turn would catch a Codex agent that hands the work to a subagent and ends its turn, as #134 did.
- **Baselines for the cases of #38 and #25 at release.** On `next` at 47c1b124, `dismissed-question-stays-closed`, `old-dismissed-question-stays-closed`, `reason-not-recommendation` and `ask-names-finding-not-id` passed 5 of 5 on Sonnet (`model-2026-11-03T08-22-22.994Z.json`), so the issues did not reproduce. Five runs cannot tell them from their rates in the issues, 47% to 85%, and `reason-not-recommendation` and `ask-names-finding-not-id` have no baseline. A 20-run `--set-baseline` at release would let a later run catch either issue coming back.
- **The Codex agent suite stops before it reaches most cases.** On 2026-11-04, Codex searched the web in `close-no-self-answer` and called `list_mcp_resources` in `side-request-leaves-question-open`. Each stops the whole Codex run with exit 3. The web search stopped `close-no-self-answer` on `next` at 31de0c1d too. The cases after the stop never run, so a guidance change gets no Codex result unless its cases are run alone. Grading such a run as failed, instead of stopping the suite, would let the other cases still run.
- **omp runs the real `gh`, which is signed out in the suite.** In `no-task-for-own-step` and `merge-asked-before-taken`, omp often runs `gh pr ready` or `gh pr merge`, gets an auth error and records a task for the person. That is right for the sandbox and wrong for the case. It passed `no-task-for-own-step` 13 of 15 on `next` and 11 of 20 once the guidance stopped naming marking a PR ready as a step to ask about. That case also still expects a question before marking a PR ready, which the principles no longer ask for (principle 1). A prompt that says `gh` is signed in and the step succeeds, or a check that allows a task about the failed sign-in, would let both cases test the guidance.
- **`tab-open-needs-you-records-new-task` sits at the bar on Codex.** Codex kept the open question open after "ok, carry on" in 25 of 32 runs on `next`, and in 21 of 32 with the ledger text of the dismissed-findings change. The difference is within chance at that sample, and the case has no baseline. A 20-run `--set-baseline` would tell a real regression from noise.
