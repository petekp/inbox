Part of [Evals the release can trust](eval-trust.md).

Status: building. Each item stays until the change that does it lands.

Each item names what it would catch. Remove an item when the change that does it lands.

- **Agent cases that fail without the guidance,** one for each of its rules, so a change to `guidanceText` is tested.
- **`no-task-for-own-step` separates weakly on Claude.** Without the guidance it passed 3 of 5 on one run and 1 of 5 on another, so a run of 5 does not reliably tell guided from unguided. A case where the unguided agent fails every run would catch the loss of the "take the step yourself" rule.
- **A second agent case that separates guided from unguided runs on Claude.** With the guidance in `close`'s description, the control (`--no-guidance`, 5 runs) failed one case of 16, `no-finding-user-only` at 3 of 5. If the guidance's other rules were cut, garbled or truncated past the 4096-character cap, the other 15 cases would still pass. A case for each rule that fails without it would catch that.
- **The direct-question rule under realistic replies.** `no-finding-user-only` passes 5 of 5, but in 0.2.10's live pass the agent missed the rule three times. Opus ended replies with "let me know which you prefer" and "I recommend no". Haiku ended one with "my recommendation: accept both". Cases where the reply ends with a recommendation or a list of options would catch it.
- **The agent suite on Haiku and Sonnet.** A past id leak (30e03f0) showed only on Haiku, and the desktop app in the release VM runs Haiku.
- **No-guidance controls on Codex and omp,** as step 2 ran on Claude, before M4 is run there.
- **M2, restoring the old rule for unrelated items.** Step 4 settled its cases, so it can run now.
- **A harder positional-answer case.** `close-answered-says-answer` passes, but in a live pass Codex saved "the second one" as the answer. A case with more options, or the answer in a longer message, would catch it.
- **A false "done:" close.** In 0.2.10's live pass, the inbox model closed a question the agent had just asked. Its reason was "done: sleep ran in foreground, so the question is moot", but the command had been blocked. The guard in `applyUpdate` catches only "no longer applies" reasons with no grounds. A model case would measure how often it happens.
- **`task-about-finding-replaces-it` back to its 0.2.9 rate.** It passes 16 of 20 on Sonnet, against 46 of 48 on 0.2.9's NEW rule. The live pass saw the miss: the inbox model added the question but wrote no ASKED line, so the finding stayed open.
- **Two Codex update processes whose Status calls run newer-first.** No test runs that order, because a test cannot make the newer call run first without a hold point in `codex/src/update.ts`. With one, a test would catch an older Status answer overwriting a newer one, which nothing prevents today: #153.
- **The two dismissed-question cases swing too much on Sonnet to judge a text change.** On `main` at 67f1c82, with the same text and model, they passed 13 and 21 of 32 in one run and 89 and 78 of 96 in the next. Most failures are not misses. `old-dismissed-question-stays-closed` fails on its `dropped: 0` check when the code has already dropped the repeated question, so nothing reaches the person. `dismissed-question-stays-closed` counts "Merge PR #41 now, without a feature flag?" as the dismissed question, because its `notNew` pattern matches any "flag". Passing a repeat the code dropped, and matching only the dismissed question, would let a run of these cases show what a text change did.
- **Check patterns that miss a correct wording.** `answered-question-follow-up-added` matched only "size", so Codex failed 2 of 8 runs that added the follow-up as "Should the product API cache use 64 MB or 256 MB?" (`model-2026-10-26T06-30-33.393Z.json`). Its pattern now also takes a size in MB. A pass over the other `new` and `notNew` patterns, against the wordings in past results, would catch a case that fails a correct answer or passes a wrong one. The agent suite's `reply` patterns need the same pass: `no-finding-progress` looks for "memoiz", and failed 2 of 5 Claude replies that described the per-request cache in plain words (`agent-2026-10-26T19-39-22.773Z.json`).
- **Two versions compared in separate runs.** The low run above ran beside two other eval runs, and the cause of its drop is not known. Running both versions in the same hour, one after the other, at 96 runs each, would keep load or a model change from reading as an effect of the text.
- **omp's inbox model,** and its fallback to omp's `@smol` model.
- **Agent cases showing the closed, carried-over and answer notes,** and Codex's guidance delivered as the plugin delivers it, at session start.
- **Agent cases that send the press messages.** Every agent reads the texts in `messages` in `hooks/press-messages.ts`, but agent cases hold a fixed prompt, so no suite runs those texts. A case whose prompt is built from `messages.explain` or `messages.finding` would catch an Explain text that makes the agent rename a question's options, act on the item, or answer at length. With a draft of the short Explain text, 8 of 10 Claude replies did not use both listed names for "Redis / In-memory", and one called them "Shared store / Each its own".
- **An agent case that sends the Compare message.** `messages.compare` asks for a lot: work outside tracked files, a background subagent where one can run, a page built from the template with measures ranked by what the person would notice, a reply with no table, and a closing `record` of the question. A case whose prompt is `messages.compare` on a small repo would catch an agent that edits a tracked file, ranks the choices by how much code each takes, writes data the page cannot draw, or never records the question again. That last miss leaves the row reading "Comparing…" until the person presses Compare again or dismisses it. `record-repeat-adds-step` and `compare-page-step-is-built-page` cover only the closing reply and `record`, from a fixed prompt, since an agent case cannot build the page.
- **`carry-status-answers-where-we-are` cannot pass, and 0.2.13 and 0.2.14 shipped with it waived.** It failed 0 of 5 on Claude, each reply without "queue". The case saves an Status in the shape from before subjects, with `headline` and `status`. `message()` in `evals/agent-cli.ts` spreads it into the ledger without `upgradeStatus`, so `statusCarryText` finds no head and carries nothing. The agent never sees the headline it is asked about. Passing the case's Status through `upgradeStatus`, or rewriting it with `head` and `subjects`, would let the case test the carry again.
- **The `runner` hash changes with code no model reads.** It hashes the esbuild bundle of the eval runner, which pulls in `hooks/gh.ts`, `hooks/pr-tab.ts` and `codex/src/run.ts`. #175 changed only gh's exit codes, and every other hash in the results files still matched. Yet `--with` (`evals/harness.ts:168`) would refuse those files as having run other code, so the release carried them over by hand. A hash of only the code that builds prompts and grades answers would let `--with` and a release tell a change the models read from one they don't.
- **A Herdr focus in the Status replays.** The `child-labels` rule in `evals/status-rules.ts` still waits on #149, which is built. The replays name their delegates by ids, `vn2` in `coordinator-day.ts` and `sm4` in `coordinator-day-start.ts`, and no replay step reads Herdr, so a delegate never takes its session's focus. A replay event that answers a Herdr check with each delegate's `inbox-focus`, run through `delegatesSettled`, would let the rule block again and catch a delegate row that keeps its id.
- **The judge-pages check after #148.** The Status page's head is now a title with a description under it. The hand-written pages that `--judge-pages` checks the judge on save their states with a `goal`, which loads as a title with no description, so the judge never sees a head drawn with both lines. `evals/status-judge/context.md` also still says the head is "one goal line" today. Rewriting the pages' states with head descriptions would let the check catch a judge that passes a description naming finished work, or fails a good head for drawing two lines.
- **A rule that reads the head's description when no goal is set.** While a goal is set, `head-follows` reads the description, which the page draws as "Now:". Without a goal it matches `pastMatch` against the title only, and `head-title` checks only that a description exists. A head of `2.5 release` over `Fixing vanishing notes, then shipping 2.5` passes both after the fix merges. Matching `pastMatch` against the description too, at steps whose facts close a piece a description named, would catch a description that keeps naming finished work, as the first hold allowed until code cleared it.
- **A reply that changes its recommendation and still leaves the old one showing.** `changed-recommendation-reaches-agent-question` passes 8 of 8 on Sonnet and on Codex, and every answer is a correct `UPDATE` line (`rec-update-ledger.json`). A live reply that changed its recommendation still left the old one showing. Its ledger answer was not looked at, so the cause is not known. A case built from that reply's wording would catch the miss.
- **A target counted as reproduced when its rule fails on another piece.** The status report lists a step's target as reproduced when its rule fails in 2 of 3 runs for any piece. Step 9 of Replay B targets `marks-true` on the Sync engine. Sonnet closed the engine in 3 of 3 runs, yet the report listed step 9 `marks-true` as reproduced, because each of its `marks-true` failures there named the Offline banner, which step 8 had left open (`status-2026-10-31T04-55-37.274Z.json`). Counting only failures on the pieces the step changes would catch a step reported as reproducing its target when the model handled the targeted piece correctly.
- **A milestone a plan change drops or adds, with no was line.** `was-on-reversal` reads subjects only. Replay A's step 14 drops two milestones when the person types a new goal, and nothing checks that the page says what plan they belonged to. Extending the rule to milestones would catch a goal change that silently replaces its milestones.
- **A regrade from a results file of another replay version.** `evals/status-regrade.ts` feeds a results file's recorded answers to the replays by step order. Replay C lost a step in this build, so a results file from before it lines its answers up with the wrong steps, and nothing refuses the file. Checking a hash of each replay against the one the file recorded would catch a regrade that grades answers against the wrong steps.
- **A missed goal that fails every later step.** In Replay A, Sonnet set no 2.5 goal at the step where the person asks for it, in all 3 of its runs (`status-2026-11-01T15-41-24.467Z.json`), so the 2.4 goal stayed. Every later step judged that page against facts that assume the 2.5 goal, so `milestones`, `split` and `milestones-true` failed on one miss. Grading the steps after a missed goal against the goal the page holds would keep one miss from reading as many.
- **The mid-turn wording follow-up: Sonnet still writes the agent's edits mid-turn.** `statusMidTurnPrompt` says how to write a piece that has started with nothing working yet: "PDF export started, not working yet", not "PDF edits begun, untested". The judge passes "started, not working yet" and "incomplete", as property 6 in `docs/plans/status/good-status.md` allows, and fails "edits begun". In `status-2026-11-02T01-28-54.089Z.json`, `mid-turn-activity` failed `where-it-stands` in 5 of 5 Sonnet runs and 0 of 5 Codex runs. Sonnet kept the edits as the subject: "Ranking edits started, not working yet" and "ranking edits started, not verified". The step lists `where-it-stands` in `judgeUntil` until a wording fix passes the case. A rule in `STATUS_SYSTEM` itself that calls an edit an activity, as in "edits started" or "edited, untested", tested on this case, would show whether the mid-turn line is too weak where it sits.
- **The 220-call stop leaves little room for retries.** A default Status run plans 202 Status calls, and every re-ask and retry counts toward `STATUS_CALLS_MAX`, 220, in `evals/status-run.ts`. The full run on 2026-11-01 used 185 of 200 when the plan was 184, so 10 more retries on a bad day stop a release run with exit 2 even when every case would pass. It also cuts selections short: the first full run of the goal replays hit the cap, and every Codex run of the seven new ones went ungraded (`status-2026-11-05T00-09-31.659Z.json`). A cap set from the planned calls of the selected replays, plus a share for retries, would let a run stop only when calls run away.
- **`order-prs-rank-again` on Codex fails when `gh` cannot reach GitHub.** The prompt names a made-up repo, `acme/shop`, and Codex has a shell, so in most runs it calls `gh pr view` first. The call fails, and Codex records a finding that it could not refresh the PRs, which the case's `record` count of 0 fails. It passed 2 of 5 with `gh` signed out (`agent-2026-11-02T07-08-05.113Z.json`) and 3 of 5 in the 0.3.0 release pass, where the sandbox blocked the network. The guidance asks for a finding when the agent works around a problem, so these findings may be right. A prompt that says the PR states it gives are current, or a check that allows a finding about the failed read, would let the case test the ordering rule.
- **`coordinator-day` fails `open-pieces-kept` and `asks-linked` on both models, and 0.3.0's release pass accepted it.** In `status-2026-11-02T03-43-15.258Z.json`, at 261a0455, all 6 runs (3 Sonnet, 3 Codex) failed the same way. At step 5, the ask "Should 2.5 wait for the archive fix, or ship without it?" was linked to the archive bug's subject on Sonnet and to no subject on Codex. Neither rule lists these steps in `until`. Reading the recorded answers would show which is wrong: a Status call that drops a piece the goal holds, or rules that expect a subject where the page now draws the goal or a milestone. The missed 2.5 proposal above may have the same cause.
- **The 24 original judge pages expect a verdict from every check, and 0.3.0's release pass accepted the judge-pages step as failing.** Since 2066a493 the judge has `goal`, `milestones` and `split` checks and may answer n/a. `evals/status-judge.ts:129` expects n/a only for the checks a page lists in `na`. The 24 pages in `.scratch/status-judge-pages/set-1.json` and `set-2.json` list none. So a judge that rightly answers n/a on a page with no goal fails every page: 0 of 24 called right in `status-judge-2026-11-02T04-06-03.017Z.json`. The 21 goal pages in `goal/` have `na`, and `docs/release.md` names only the top folder. Adding `na` to the 24 pages, and keeping all 45 in one folder, would let the release step catch a judge mistake again.
- **An agent case that sends the Compare press's own message.** The three cases in `evals/agent-cases/compare.json` start after a background subagent has reported, with a prompt that quotes only the end of the Compare request. None sends `messages.compare`, so no case reads the opening that differs by host. A case that sends each host's Compare message and checks the reply holds the pick and the page's path in the same turn would catch a Codex agent that hands the work to a subagent and ends its turn, as #134 did.
- **Baselines for the cases of #38 and #25 at release.** On `next` at 47c1b124, `dismissed-question-stays-closed`, `old-dismissed-question-stays-closed`, `reason-not-recommendation` and `ask-names-finding-not-id` passed 5 of 5 on Sonnet (`model-2026-11-03T08-22-22.994Z.json`), so the issues did not reproduce. - **`single-task` accepts conflict handling as done at step 4, and then fails it for being done.** At step 4 the person reverses the conflict plan, and the facts give the conflicts piece `alsoRight: ['done']`, so `marks-true` accepts a subject closed as done. `open-pieces-kept` still counts the piece as open at step 4, and step 5's facts keep it open. A run that closes it at step 4 therefore fails `open-pieces-kept` at step 4 and at every step after it. In `status-2026-11-04T06-54-19.784Z.json`, at a1e9e125, all 3 Codex runs closed it at step 4 and failed `open-pieces-kept` at steps 4 through 9. Two of 3 Sonnet runs closed it at step 5, where the reply says last-write-wins works on both test devices, and failed at steps 5 through 9. Making the two rules agree, by letting `open-pieces-kept` also take `alsoRight`, or by dropping `done` from `alsoRight`, would let the step 5 target catch a model that loses the conflicts subject, not one that closed it as the facts allow.
- **`single-task` step 8 expects the banner done once the person drops its last open question, and both models keep it working.** Step 8's facts mark the offline banner done after the person says "Drop the web question" about it. At a1e9e125, `marks-true` failed there in 6 of 6 runs, 3 Sonnet and 3 Codex, each with the banner still working (`status-2026-11-04T06-54-19.784Z.json`). Sonnet failed it the same way at 261a0455 (`status-2026-11-02T03-43-15.258Z.json`), and Codex failed it 2 of 3 on `next` at ca34e23c, in the runs that had a banner subject. That run's results file was not kept. Deciding whether a dropped last question finishes the piece would settle it. If it does, a rule in `STATUS_SYSTEM` tested on this step would catch a piece left working after its last question goes. If it does not, facts that keep the banner working would let `marks-true` catch a banner wrongly closed instead of failing every run.
- **`single-task` step 2 expects conflict handling queued while its question is open, and `STATUS_SYSTEM` calls that working.** At step 2 the agent asks "last-write-wins or manual merge?", which holds up conflict handling. The facts keep the piece queued. The prompt's working status covers work "stopped until the person answers an ask", so a run that sets it working follows the prompt and fails `marks-true`. Letting the piece be `working` too, with `alsoRight`, would let `marks-true` catch a status the prompt does not allow.
- **Sonnet and omp still lack the subject-split rule, so `single-task` step 1 checks the split on Codex only.** Only Codex reads `PARTS_STATUS_SYSTEM` (see "The Status call's subject rule" in `docs/looks/differences-status-and-marks.md`). - **A removed goal comes back in every answer.** In `removed-goal`, both models wrote the removed goal again in 10 of 10 runs (`status-2026-11-05T00-09-31.659Z.json`). Code drops a GOAL line that restates a removed goal, so the page never showed it, and the case cannot fail on it. `<removed>` lists each goal as its sorted key words, such as "demo import ready", which the model may not read as the goal it just saw. A model case that counts GOAL lines restating `<removed>`, before code drops them, would show whether giving the goal's own words there helps.
