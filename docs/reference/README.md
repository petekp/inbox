# Platform reference

This folder records what each client platform lets the inbox do, with a source for every fact. It was checked on 2026-10-08 against these versions:

- Claude Code 2.1.295 in the terminal.
- The Claude desktop app 2.31226.0. Its sessions ran the app's own Claude Code copy, 2.1.293. A 2.1.289 copy was also on disk.
- Codex CLI 0.160.1, bundled in the ChatGPT desktop app. `codex` on `PATH` was 0.154.0. The latest release was 0.162.0.
- The MCP Apps spec `2026-01-26` with ext-apps SDK 2.0.3, and core MCP `2026-07-28`.
- This repo at commit `55ab122`.

To keep it current, re-check those versions first: `claude --version`, `/status` in a Code-mode session, and `codex --version`. Then re-run the live checks in each file.

For Claude Code, prefer the engine's local types (`.claude-plugin/types/claude-code/index.d.ts`) when they disagree with the public docs. The docs say to "trust these files over any page, this one included, when they disagree" ([claude-code-mods.md](claude-code-mods.md#engine-types)). The file is gitignored, and whichever engine last loaded the repo folder rewrites it. On 2026-10-08 its header read 2.1.292, 2.1.293, 2.1.294 and 2.1.295 at different times (`claude-code-mods.md:14`). Record the header version with any fact you cite from it.

Terms used here:

- **Mod**: a Claude Code plugin whose hooks module watches engine events and draws. The inbox's Claude client is one (`hooks/`).
- **Engine**: the Claude Code program that runs a session and loads mods.
- **Surface**: the app that draws a session: `terminal` or `desktop` in the docs. The engine types also define `mobile` and `vscode`.
- **Guard**: the built-in mod `cc-plugin-sec-default`. It loads ahead of user mods on a Team or Enterprise sign-in or on a machine with managed settings, and limits what they can change.
- **Code mode** and **Claude mode**: the desktop app's two modes. The public docs still say Code tab, and Chat plus Cowork. A third-party build's changelog says "Unified Claude ... combines Chat and Cowork" ([mcp-apps.md](mcp-apps.md#where-sources-disagree)).
- **SDK host**: an app that runs the engine headless and drives it over the Agent SDK's stream-json protocol. The desktop app is one.
- **MCP App**: an MCP tool that names a `ui://` HTML view for the host to render in an iframe. The Codex Inbox tab is one.

Evidence tags in the four files: doc, local (types or repo code), live (checked on a Mac), inference. A `*` in the matrix marks an inference.

Notes:

1. Docs: "SSH sessions support permission modes, connectors, plugins, and MCP servers". Whether the mod's hooks run or draw there is unverified. The plugin must be installed on the remote host; the local `CLAUDE_CODE_PLUGIN_DIRS` does not apply.
2. A user-installed plugin does not reach a cloud session. Only server-managed or claude.ai-synced plugins do, and nothing a mod draws appears there.
3. Chat ignores plugin hooks, mods and local MCP servers. Cowork loads hooks and local MCP servers when it runs on the person's machine; whether it runs mod `modules` is unknown. A local MCP server in `claude_desktop_config.json` or a `.mcpb` extension reaches Claude mode.
4. Hooks run in the VS Code chat panel and nothing draws. Today the inbox's gate keeps it off there, so it makes no model call.
5. The mod runs in the session on the host machine and draws only in that machine's terminal. A phone or claude.ai viewer sees no band or pane. Prompts typed there arrive with origin `bridge`, which the inbox counts as the person's words.
6. Codex runs a plugin's hooks only after the person trusts each hook definition. A changed definition is skipped until trusted again.
7. Claude: `$.model.complete` uses "the user's plan or API key", and `sonnet` resolves to Sonnet 5.5, 4.6 or 4.5 by provider. Codex: `codex exec` reuses the person's saved Codex sign-in; it measured 21.5k input tokens per call, 12.5k at best.
8. The inbox's cached call needs engine 2.1.292. The app's sessions ran 2.1.293; its 2.1.289 copy is older.
9. A pane docks beside the transcript in a fullscreen terminal from 110 columns. Otherwise it is a framed region above the prompt. A pane the mod opens on its own waits for 144 columns, or 110 once the person has opened that pane.
10. The pane draws on desktop. Where it docks, and its `placement`, `bodyColumns` and `maxRows`, are unknown.
11. The thread tab comes from the Codex-only key `_meta["openai/ui"].entrypoints`. It opened live from this repo's local plugin.
12. The engine types say "A desktop draws its native button either way", plain or bracketed (`ButtonProps.plain`). Whether it honors hotkeys on the inbox's hidden `Button`s, focus keys and `keybindings.json` is unverified.
13. Not covered by any of the four files.
14. `$.prompt.submit` exists, but its behavior under an SDK host is unverified. `$.prompt.read`, `fill` and `suggest` do nothing headless.
15. A press from the inbox server through `codex queue` arrived as a plain user message (live). A tab's own `ui/message` arrives wrapped as untrusted input. A press from the tab in the desktop app is not yet confirmed end to end.
16. Redraws are "Throttled to 10 a second, or 30 in the terminal for the visible pane, the expanded band, and the hint line under the prompt". Inference: 10 a second on desktop.
17. Model tool calls carry `x-codex-turn-metadata`, tab calls carry `_meta.thread_id`. In a forked chat, `sessionOf` reads the root's `session_id` first and may route a press to the wrong chat (inference, not checked).
18. Where: Claude clients write `$.store` to `~/.claude/plugins/store/<name>_<source>-<hash>.json`, one file per plugin id, shared by all sessions, 4 MiB cap, no atomic update. The Codex plugin keeps one JSON file per session under `~/.codex/plugins/data/inbox-inbox` with an mkdir lock. A Claude-mode view's own storage is per conversation, so state would live in the server.
19. The engine types mark `$.process` "CLI only". The desktop app also passes only `PATH` and a fixed set of variables from the shell profile, so a profile-only `GH_TOKEN` may be missing.
20. The Anthropic-hosted GitHub proxy returns 403 to GraphQL, which the inbox's PR block uses.
21. A local stdio MCP server is an ordinary process on the Mac.
22. The inbox's MCP server runs `codex queue` and `codex exec` (live). Whether hooks and MCP servers run inside Codex's sandbox is undocumented.
23. Inference, not checked: on desktop the inbox may first register its tools at `session.attach`. If that comes after the first prompt, the tools are missing for that turn. Where the guard loads and managed settings set `allowedMcpServers`, the guard's source refuses the inbox's `$.tool.register` calls in every client.
24. `default_tools_approval_mode: "approve"` in the plugin's `.mcp.json` skips approval (live). It is documented only for the person's own `config.toml`.
25. Inference: the terminal surface is wherever `claude` runs, so a terminal over SSH draws, and that machine's `~/.claude` holds the store.

27. Cloud chats run on a remote environment without the person's local processes, so the local hooks and stdio server cannot run there.

## Facts that most constrain the architecture and UI

1. Only the terminal and desktop Code mode draw a mod: "Drawing is narrower: only the terminal and the Desktop app show a mod's panes, bands, and replaced rows" ([mods](claude-code-mods.md#where-mods-run-and-draw)).
2. Desktop Code mode runs the engine headless as an SDK host (live process arguments). Inference from the types: such a session starts with `isInteractive` false. Live, while the inbox gated on `isInteractive` alone, `/inbox` and its tools did not exist in Code mode (`docs/plans/clients.md:56`). The inbox now also turns on through `$.session.surfaces()` or `session.attach`. The mods reference lists `session.attach` in one row of its events table. No public doc says how a desktop session starts, or in which order the two events fire ([desktop](claude-desktop-app.md#how-the-app-runs-claude-code), [mods](claude-code-mods.md#how-the-desktop-app-runs-a-code-mode-session-live-types-repo)).
3. Engine versions differ by client (terminal 2.1.295, desktop 2.1.293 and 2.1.289). The inbox's cached model call needs 2.1.292, and `plugin.json` has no minimum-engine field ([desktop](claude-desktop-app.md#engine-versions-and-updates), [mods](claude-code-mods.md#manifest-facts-that-matter-to-the-inbox)).
4. On desktop, the render sites `ToolProgress`, `TurnDuration` and `InfoNotice` and the elements `Raster` and `Image` do not work. `$.ui.copy` may not work: the types say "a remote surface has no path yet" in one place and allow a remote copy in another (unverified). A `Link` is live only for `https:`; the docs also allow `http://localhost`, the types do not ([desktop](claude-desktop-app.md#what-draws-on-the-desktop), [mods](claude-code-mods.md#where-sources-disagree) row 112).
5. No MCP Apps host gives a view a persistent place: the modes are `inline`, `fullscreen` and `pip`, and Codex's thread tab is a Codex-only key ([mcp-apps](mcp-apps.md#facts-that-most-constrain-the-inbox)).
6. Claude Code in the terminal does not render MCP Apps: "Claude Code calls the tool as text and doesn't render the UI" ([mcp-apps](mcp-apps.md#which-hosts-support-it)).
7. Nothing pushes updates into an MCP App view in any host, so every view polls; the Codex tab polls every 3 s ([codex](codex-plugins.md#live-updates)).
8. Claude gives an MCP server no conversation id ("Neither `hostContext` nor the tool-call arguments include a Claude-provided conversation ID"), so the Codex server's `sessionOf` would fail every call there ([mcp-apps](mcp-apps.md#identity-and-instances)).
9. Each model tool call in Claude mounts a new live view and old ones stay, so presses need a server-checked target ([mcp-apps](mcp-apps.md#identity-and-instances)).
10. Claude mode reaches local state only through `claude_desktop_config.json` or a `.mcpb` extension; Chat ignores plugin hooks, mods and local MCP servers ([mcp-apps](mcp-apps.md#routes-into-claude-mode)).
11. Codex wraps a tab's `ui/message` as untrusted input, so presses depend on the undocumented, `#[experimental]` `codex queue` and `thread/queue/add` ([codex](codex-plugins.md#sending-a-press-codex-queue-and-threadqueue)).
12. Codex skips plugin hooks until the person trusts each definition, and a plugin with hooks cannot be listed in the public directory ([codex](codex-plugins.md#where-codex-finds-hooks-and-trust), [codex](codex-plugins.md#public-directory-and-submission)).
13. Codex's `Stop` hook cannot add model context, and hook context is capped near 2,500 tokens by default ([codex](codex-plugins.md#output)).
14. Codex calls its transcript format and app-server unstable, and the inbox depends on both ([codex](codex-plugins.md#transcripts), [codex](codex-plugins.md#app-server)).
15. The per-turn update bills the person in both clients, and `sonnet` is a different model per provider ([mods](claude-code-mods.md#what-the-inboxs-model-calls-cost), [codex](codex-plugins.md#codex-exec-the-per-reply-update)).
16. `$.store` is one JSON file per plugin id (`inbox@inline` today), shared by all sessions, with a 4 MiB cap and no atomic update. Inference: a marketplace install would be `inbox@<marketplace>` and get a separate file ([mods](claude-code-mods.md#store-and-state)).
17. `/clear`, `/resume` and `/branch` switch the conversation without a new `session.start`. All `session.end` work shares one bound, 1.5 s by default ([mods](claude-code-mods.md#lifecycle-what-fires-and-what-resets), [mods](claude-code-mods.md#shutdown-and-the-15-second-end-bound)).
18. On Team or Enterprise sign-ins and managed machines, the guard's public source skips user mods on `prompt.compose`, `prompt.context` and `classic.*`. Those carry the inbox's guidance, its carry text and its reload after `/clear` and `/resume`. When managed settings set `allowedMcpServers`, the same source refuses `$.tool.register`, so `record_finding`, `close` and `run_check` would not exist while the band still draws. This is from the guard's main branch at `684800b`; the effect is not verified live ([mods](claude-code-mods.md#what-the-guards-source-skips-not-in-the-docs)).
19. Every platform already shows which session waits on the person (Claude's agent view and `claude agents --json`, the desktop app's Projects, Codex's Activity view), so the inbox's distinct value is item level ([mods](claude-code-mods.md#claude-agents---json-the-supported-session-list), [codex](codex-plugins.md#the-desktop-apps-own-attention-features)).
20. Orgs can turn the inbox off. A plugin installed from GitHub "counts as a user's, even when managed `enabledPlugins` enables it". So managed `allowManagedModsOnly`, `allowManagedHooksOnly` or `disableAllHooks` stops it. Only a directory marketplace that device management copies to every machine counts as the org's ([mods](claude-code-mods.md#what-counts-as-the-organizations-mod), [mods](claude-code-mods.md#what-can-turn-the-inbox-off)).
21. The inbox can vanish, and the person sees only a missing band. Causes: three hooks-worker crashes, which unload every non-built-in mod until `/reload-plugins`; `--safe-mode` or `--bare`; an untrusted folder; Anthropic's remote rollout switch; and the org policies in 20. For an installed mod, only the worker-crash line reaches the transcript. Other reasons go to the debug log only, and a guard refusal follows a `loaded` line for the same mod. `claude plugin test` in an empty folder reports whether mods can load, but exits 1 even when they can (live) ([mods](claude-code-mods.md#the-hooks-worker), [mods](claude-code-mods.md#how-a-refusal-shows), [mods](claude-code-mods.md#troubleshooting-and-the-debug-log)).
22. The band is shared. A mod's band tree "replaces what the mods after yours draw there" unless it includes `await next(e)`, and the inbox's band does not (`hooks/register.tsx:2297`). The built-in `cc-plugin-you-should-know`, off by default, also "shows you a note above the prompt" and spends model calls. How the two share the band is unknown ([mods](claude-code-mods.md#built-in-mods), [mods](claude-code-mods.md#drawing-render-sites)).
23. Desktop Code mode has no `/plugin install`, so a desktop user installs from a shell at user scope, which the app's local sessions read. With no `version` in `plugin.json`, the installed version is a commit SHA, so commits that touch only `codex/` likely count as updates too. Auto-update is off by default for a custom marketplace ([mods](claude-code-mods.md#install-by-app), [mods](claude-code-mods.md#versions-updates-and-the-cache)).
