# Subagents, guardians and hooks

Part of [Codex plugins and the Codex app](../codex-plugins.md).

Checked on 2026-10-21 against `rust-v0.163.0` (`8308618`). Paths are under `codex-rs/`. Live answers sit under "Live checks" in this section and name their version and log.

## Facts from the source [source 0.163.0]

- **A rollout keeps `turn_aborted`.** The rollout policy persists `EventMsg::TurnAborted` beside `TurnStarted` and `TurnComplete` (rollout/src/policy.rs:136-138).
- **Interrupt skips subagents.** `run_turn_interrupt_hooks` returns at once when the turn's source is any `SessionSource::SubAgent` (core/src/hook_runtime.rs:507-509).
- **An Interrupt hook gets 1 s by default and 3 s at most.** SessionEnd and Interrupt default to 1 s, clamp to 1-3 s, and warn when a hook asks for more (hooks/src/engine/discovery.rs:742-760; hooks/src/events/session_end.rs:20,23). Every other hook defaults to 600 s.
- **SubagentStart fires once per spawned subagent, and never for a guardian review.** It runs from the pending session-start source. Only a `ThreadSpawn` subagent whose start source is `Startup` or `Fork` dispatches it. Any other subagent source, which includes the guardian's `SubAgentSource::Other`, returns without a hook (core/src/hook_runtime.rs:128-150; guardian source at core/src/guardian/review_session_setup.rs:218).
- **SessionStart does not run in a subagent or guardian thread.** The same function returns for every `SubAgent` source that is not a `ThreadSpawn` start, and a `ThreadSpawn` start dispatches SubagentStart instead (core/src/hook_runtime.rs:133-150).
- **SubagentStop runs only when a subagent's sampling loop ends.** The turn loop calls `run_turn_stop_hooks` only when there is no follow-up, and an aborted turn returns before that (core/src/session/turn.rs:718-725). For a `ThreadSpawn` source the hook is SubagentStop. For any other subagent source, Stop and SubagentStop both do nothing (core/src/hook_runtime.rs:400-440).
- **Stop in a subagent is SubagentStop, with the parent's transcript.** SubagentStop's `transcript_path` is the parent's rollout, found by `parent_thread_id`. The subagent's own rollout comes as `agent_transcript_path` (core/src/hook_runtime.rs:401-433). SubagentStart's `transcript_path` is the subagent's own rollout (core/src/hook_runtime.rs:159).
- **A subagent's hooks carry its thread id as `agent_id`.** `subagent_hook_context` sets `agent_id` to `sess.thread_id()` and `agent_type` to the role, or the default role name (core/src/hook_runtime.rs:1054-1061). PreToolUse, PostToolUse, PermissionRequest and UserPromptSubmit take this context from `thread_spawn_subagent_hook_context`, which is `Some` only for a `ThreadSpawn` subagent (core/src/hook_runtime.rs:199, :268, :310, :1042-1052).
- **`session_id` on a subagent's hooks is the parent's, and a user fork gets its own.** A subagent (a non-root agent) takes the agent controller's session id. A forked or new root thread uses its own thread id (core/src/session/session.rs:928-950). `SessionMeta.session_id` is documented "equal to the root thread's ID" (protocol/src/protocol.rs:3252).
- **A subagent's first `session_meta` row holds `parent_thread_id`, `depth` and `agent_path`.** `SessionMeta` has `parent_thread_id`, `source`, `agent_nickname`, `agent_role` and `agent_path` (protocol/src/protocol.rs:3245-3290). `depth` is not a top-level field. It sits in `source.subagent.thread_spawn.depth`, beside `parent_thread_id`, `agent_path`, `agent_nickname` and `agent_role` (protocol/src/protocol.rs:3030-3042). The Progress plan's "`session_meta` row holds `depth`" means that nested field.
- **Hook matchers are Rust regexes with three shortcuts.** An empty pattern or `*` matches all. A pattern of only letters, digits, `_` and `|` is an exact match against each `|`-separated name. Anything else compiles as a `regex::Regex`, which has no lookahead (hooks/src/engine/matcher.rs:10-40).

## Where the sources disagree

- The app-server doc says "forked threads keep the session id of the root they came from" (L/app-server#start-or-resume-a-thread). The source gives a user fork its own session id (core/src/session/session.rs:946-950). The live fork check below settles it.

## Live checks

Tested 2026-10-21 in the inbox-ui VM with `codex-cli 0.163.0-alpha.11`, the CLI bundled in ChatGPT app 26.1016.51333. Runs used a scratch `CODEX_HOME` with my own logging hooks on all 12 events and a stand-in MCP server named `probe`, not the inbox. `codex exec` runs used `--dangerously-bypass-hook-trust`. App-server runs used a probe client over stdio with trust entries for the logging hooks in the scratch `config.toml`. Logs are in the VM share folder under `step0/logs/`, named by run below. This build exposes `spawn_agent` (with `task_name`), `followup_task`, `interrupt_agent`, `list_agents`, `send_message` and `wait_agent`. It has no `send_input`, `close_agent` or `resume_agent` (`r2.out`, `r8.out`, also with `--enable multi_agent_v2`).

- **The task name and depth are in the subagent's first rollout row, and the row is there when SubagentStart runs.** `session_meta.payload.agent_path` is `/root/<task_name>`, and `source.subagent.thread_spawn.depth` is 1. A subagent's own subagent has `agent_path` `/root/outer/inner`, `depth` 2, and `parent_thread_id` the outer's id. SubagentStart still fires for it, with the root's `session_id` (`r7.hooks.jsonl`, `r7-rollouts/`). The hook logger read the first row of `transcript_path` at SubagentStart time and found `agent_path` in it (`first.row0` in `r2.hooks.jsonl`).
- **A subagent's rollout starts with two `session_meta` rows.** The first is its own. The second is its parent's, copied in (`r1-rollouts/`). Read only the first row.
- **Hook input in a subagent.**
  - SubagentStart: `session_id` is the controller's session id (the root's, also for a subagent's own subagent), `agent_id` is the subagent's thread id, `agent_type` is `default`, `transcript_path` is the subagent's rollout.
  - SubagentStop: `transcript_path` is the parent's rollout and `agent_transcript_path` the subagent's.
  - PreToolUse and PostToolUse carry `agent_id`.
  - SessionStart, Stop and UserPromptSubmit did not fire in a subagent (`r1`, `r2`, `r7` hooks logs).
- **A follow-up turn runs no SubagentStart and no UserPromptSubmit.** `followup_task` on a finished subagent started a new turn. For task_a, whose follow-up turns called no tool, the first hook with the subagent's `agent_id` was its SubagentStop. For task_b, interrupted during `sleep 90` and then given a follow-up, the first hook in the new turn was a PostToolUse for the old call: the old `tool_use_id` under the new `turn_id`, with no PreToolUse before it. A follow-up turn that calls a tool was not seen. SubagentStop fired at the end of every turn that ended normally (`r2.hooks.jsonl`).
- **`interrupt_agent` aborts a subagent's turn and writes `turn_aborted`.** The row (`reason: "interrupted"`) was timestamped 59 ms after the parent's PreToolUse for `interrupt_agent`. The aborted turn got no SubagentStop and no Interrupt hook. A later `followup_task` started a new turn that ended with SubagentStop (`r2.hooks.jsonl`, `r2-rollouts/`).
- **A main-turn interrupt writes its abort row at once and does not stop subagents.** `turn/interrupt` on the main turn fired the Interrupt hook 34 ms after the call and wrote the main rollout's `turn_aborted` row with a timestamp 35 ms after the call. A 20 ms file poller saw the row within 13 ms of its timestamp. The subagent, in a 120 s shell sleep, got no abort row, no PostToolUse and no SubagentStop for the 30 s the run kept watching (`r4.rpc.jsonl` rows with `kind: "rollout-row"`, `r4.hooks.jsonl`). The plan's "one poll late" threshold for an Interrupt hook entry is not reached.
- **Guardian reviews fire no hooks of their own.** With `approvals_reviewer=auto_review` an escalated shell command made a guardian thread (`source: {subagent: {other: "guardian"}}`, `thread_source: "guardian_review"`, `parent_thread_id` and `session_id` the main thread's). It ran no SessionStart, UserPromptSubmit, PreToolUse, Stop or SubagentStart. The one hook around it was PermissionRequest, under the main thread's ids with no `agent_id` (`r3.hooks.jsonl`, `r3-rollouts/`). That guardian called no tools. One that does was not seen.
- **A subagent is offered plugin tools, and SubagentStart `additionalContext` reaches it.** The subagent called `mcp__probe__step` and `mcp__probe__close`. A sentinel in SubagentStart's `additionalContext` appeared as a developer message in the subagent's rollout and not in the main rollout (`r1-rollouts/`, `default.mcp.jsonl`).
- **Hook `tool_name` for the multi-agent tools is `collaborationspawn_agent`,** and likewise `collaborationwait_agent`, `collaborationfollowup_task`, `collaborationinterrupt_agent` (`r2.hooks.jsonl`). Other non-shell tools keep their plain names, such as `clocksleep`, and hooks fired for them in a subagent (`r8.hooks.jsonl`). The matcher text `spawn_agent` that L/hooks lists as an alias was not tried.
- **MCP call metadata keys a call to the right row.** For the main agent: `session_id` equals `thread_id` and there is no `parent_thread_id`. `thread_source: "user"` appeared only in a `codex exec` run (`default.mcp.jsonl`); the app-server main calls in `r5.mcp.jsonl` have no `thread_source` key. For a subagent: `session_id` is the controller's session id (the root's), `thread_id` is the subagent's, `parent_thread_id` and `forked_from_thread_id` are the spawning thread's (seen at depth 1 only), `subagent_kind: "thread_spawn"`, `thread_source: "subagent"`. In a user fork's main agent, `forked_from_thread_id` is the base chat and `parent_thread_id` is absent (`r5.mcp.jsonl`).
- **One keying rule fits hooks and server.** The conversation key is `session_id` in a hook and in `x-codex-turn-metadata`. A subagent's key is `agent_id` in a hook and `thread_id` in the metadata. The main agent is the call with no `agent_id`, and no `parent_thread_id`. A fork's main agent has `forked_from_thread_id` and no `parent_thread_id`. This held for a base thread, a fork, a subagent of the base thread and a subagent of a fork (`r1`, `r5`, `r7`). A subagent's `session_id` is the controller's, which is the root's, so a nested subagent's parent comes from `parent_thread_id` (its session_meta row), not from `session_id`. Today's keying by `session_id` is already this rule.
- **MCP servers get env only from the plugin's `env_vars`.** The probe saw `STEP0_RUN` only after `env_vars = ["STEP0_RUN"]` (`r2.mcp.jsonl`).
- **A killed app-server leaves no end row and runs no hook on reopen.** `SIGKILL` of the app-server 20 s into a shell sleep, then a new app-server and `thread/resume`: the rollout's last rows were the tool call and its token usage, then `thread_settings_applied` written at resume. It had no `turn_aborted` or `task_complete` row. The resumed thread reported status `idle`. No SessionStart ran (`r6.rpc.jsonl`, `r6.hooks.jsonl`, `r6-sessions-all/`). This is a killed app-server, not the ChatGPT app quitting, so the app's own quit path was not seen.
- **Quitting the ChatGPT app during a turn ends the turn in the rollout.** Tested 2026-10-22 in the inbox-ui VM, ChatGPT app 26.1016.61520 with `codex-cli 0.163.0-alpha.11.1`, during a shell `find`. Quit asked "Quit ChatGPT? Active local chats on this machine will be interrupted", then the rollout got `turn_aborted` with `reason: "interrupted"`. `kill -9` of the app's main process did the same: its `codex` child wrote `turn_aborted` before it exited. `kill -9` of that `codex` child alone wrote no end row. The chat then showed idle, the inbox tab read "Couldn't display Inbox" until Try again, and the inbox's flag stayed running until the next message's Stop. A `/compact` in the app runs as its own turn, from `task_started` to `task_complete`.
- **Hooks need trust in app-server.** `hooks/list` showed all 12 hooks `untrusted` before trust entries were set (`h1.rpc.jsonl`). The r4, r5 and r6 runs passed the top-level `codex --dangerously-bypass-hook-trust app-server` together with trust entries in `config.toml` and ran hooks, so the flag alone was not isolated. The probe's first spelling, `app-server --dangerously-bypass-hook-trust`, was replaced by the top-level one; its failure output was not kept.
