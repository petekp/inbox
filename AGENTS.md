# Working on the inbox

The inbox is drawn in four looks: the Claude Code terminal, the Claude desktop app's pane, the Codex tab, and omp's panel. Before you change the UI or a rule, read [docs/looks.md](docs/looks.md). It says which file owns each rule, where the looks differ on purpose, and what to check after each kind of change. [GLOSSARY.md](GLOSSARY.md) defines the terms.

## New features

- Design each feature for every client from the start: the Claude Code terminal, the Claude desktop app, Codex and omp. Work out how each host gets the events and data the feature needs.
- Put shared logic in the owner `docs/looks.md` names, so each host calls it.
- Leave a host out only for a real host limit, recorded in "Differences on purpose" with its reason. Doing a host later is not a reason.
- Give the feature a `FeatureId` in `hooks/clients.ts`, with an entry for every client. `./scripts/check.sh` fails on an entry that is not `full` and has no row.

## Every change

- The repo is public. Keep private paths, other people's names and session content out of commits.
- Run `./scripts/check.sh` after every change.
- Change shared behavior in the owner listed in `docs/looks.md`. Adapters map shared row and action descriptions to native controls. Hosts run events, storage and effects. Rebuild the Codex bundles after a shared-module change with `npm --prefix codex run build`, and the omp bundle with `npm --prefix omp run build`.
- When you finish a change to a shared module or a look's drawing code, say for each look whether the change applies and what you checked there. A difference between looks that is not in the "Differences on purpose" table in `docs/looks.md` is drift: fix it, or add it to the table with its reason.
- Before you bump the version, run every check in [docs/release.md](docs/release.md).
- When an eval run, a review or a release pass shows a bug or a gap in the evals, tests or release pass, write it down in the repo before you finish, with the failure it would catch. File a product bug as a GitHub issue. Add a gap in the checks to the follow-ups in `docs/plans/eval-trust.md` or `docs/plans/release-pass.md`.
- Saved state outlives the code. The mod uses `PluginState` in `types/index.d.ts`; Codex uses `SessionState` in `codex/src/state.ts`; omp uses `OmpState` in `omp/src/state.ts`. Convert old shared fields in `upgradeLedger` or `upgradeLastActions`, and old host fields in `upgradeState` and `upgraded`.

## Text a model reads

Test a change to text a model reads before keeping it. Small rewordings change behavior: a one-word edit to the findings rule in `systemText` made the inbox model re-add questions the user had dismissed.

- Claude, Codex and omp read the guidance `guidanceText` builds, and the `inbox:` texts that `inboxText`, `closedText`, `carryText` and `answerNote` build, all in `hooks/model-text.ts`. Each host's `Host` supplies its names and the guidance's first paragraph, so a change there reaches every agent.
- Claude reads the tool descriptions and results from `hooks/tools.ts`. Codex reads those too, and its own tool texts in `codex/src/texts.ts`. omp registers `record` and `close` with the same descriptions, and its names are in `omp/src/texts.ts`.
- Every agent reads the message each press sends, from `messages` in `hooks/presses.ts` and `prompts` in `hooks/prs.ts`.
- The inbox model makes two calls after each reply, in parallel. The ledger call reads `systemText` and the blocks from `buildPrompt` in `hooks/model-text.ts`. The results call reads `RESULTS_SYSTEM` and `resultsPrompt` (`resultsCatchUpPrompt` for a catch-up), and only its DONE lines become results: the ledger call's own DONE lines are dropped. A failed results call leaves the ledger update applied with no new results. In the mod it is a Sonnet call after each reply. In Codex it is `codex exec` with the model in `MODEL` in `codex/src/update.ts`. In omp it is a Sonnet model from the person's providers, else omp's `@smol` role, chosen by `inboxModel` in `omp/src/host.ts`.
- After a change to `guidanceText`, a tool description in `hooks/tools.ts` or a tool answer, run `./scripts/eval.sh --suite agent`, and run it before a release. It gives Claude Code on Opus, Codex and omp the shipped guidance and a stand-in for the inbox, which uses the real tool descriptions, schemas and answers. Claude Code and Codex get an MCP server named `probe` (`evals/probe.ts`). omp gets an extension, `evals/omp-probe.ts`, that registers `record` and `close` as native tools, adds the guidance to the system prompt and delivers the inbox text as a hidden message, as `omp/src/host.ts` does. It checks the `record` and `close` calls and the reply for each case in `evals/agent-cases.json`, with the same pass bar as the model suite and 5 runs by default. Use `--agent` (`claude`, `codex`, `omp`, `both` for claude and codex, or `all`), `--omp-model`, `--runs`, `--case` and `--out` as in the model suite. An omp run needs a Claude sign-in in your omp (run `omp`, then `/login`). It uses a temporary `HOME` that holds nothing of your omp config, and gets the sign-in's token from `omp token anthropic` through `ANTHROPIC_OAUTH_TOKEN`. It defaults to Claude Opus 5.5. A Codex run uses a temporary `CODEX_HOME` that holds only a link to `auth.json`, so Codex loads neither your installed inbox plugin nor your `AGENTS.md`. `--no-guidance` runs the cases without the guidance, as a control.
- To compare two versions, print each one's prompt for the same sample exchange. Run each several times with `claude -p --model sonnet --tools "" --system-prompt …`, and for text Codex reads, with `codex exec` and the Codex model. Count the outcomes.
- After a change to `systemText`, `buildPrompt`, `RESULTS_SYSTEM` or `resultsPrompt`, run `./scripts/eval.sh`. It runs both inbox model calls on the cases in `evals/cases.json`, on Sonnet and on Codex, and fails a case that passes in too few runs. It calls Sonnet as the mod does, at low effort, and applies each answer with `applyExchangeUpdate`, as the hosts do. Add a case for each behavior a change sets out to fix. `check.sh` leaves the evals out, since each run calls a model.
- Every eval run writes its results to `evals/results/`, which Git ignores, as each run lands. The file holds the commit, the uncommitted changes, the CLI versions, a hash of each text the models read and of the cases file, and each run's model, answer and verdict. Codex does not say which model answered, so its runs record the model asked for. Neither suite reads your own `CLAUDE.md` or `~/.codex/AGENTS.md`. Quote the results file when you report a run.
- A run exits 0 when every case passed and 1 when a case failed. It exits 2 when a case could not be graded because its calls kept failing: that case has no result, so rerun it. It exits 3 when it stopped, as when a session could reach more than the stand-in inbox.
- Do not rerun a failing case until it passes. Rerun it once at three times its runs with `--with <first results file>`, which judges both runs together and refuses a file that tested other text.
- `--set-baseline` saves the count of each selected case as its baseline, in `baselines.json` beside the cases. It needs a clean tree and 20 or more runs that could all be graded. A later run on the same model also fails a case whose count is under 1% likely under its baseline.

## Presses

Every action shows what it did as soon as it is pressed. When Discuss showed nothing, a person sent the same message four or five times.

- Each `Action` declares its `kind`, a `PressKind`.
- A Talk or Hand-off press leaves a ✓ and its label on the row, as in "✓ Discussed". A Talk press reads "Explaining…" or "Discussing…" until the agent's reply, and a handed-off row the reply left open reads "Still open". It stores its action id from `actionId()`, so the same action then reads "… again".
- A Local press, an open or a copy, shows "Opening x…" on its row, then its result: "✓ Opened x", or in red why it could not. It never reports through a toast.
- A Mark or View press shows itself, as closing a row or opening the text field does.
- Row and PR presses use `applyPress()` and `applyPrPress()`. The mod's `runPress()` and the Codex server run their effects through each host. A click and a key press record the same result.

## Tests and live checks

- In `tests/hooks.test.ts`, `world()` answers every engine event the mod uses, and the test harness takes one handler per event. A test changes an answer through the variables `world()` resets, such as `ledgerReply`, `stopBlock` and `ghAnswers`.
- The plugin store is keyed by the mod's name, so a session that loads a copy under your own config writes to your real inbox's state. Check the UI live in a session with its own `CLAUDE_CONFIG_DIR`. `mods/scripts/live.sh` in petekp/claude-code-setup starts one in tmux.
- To try a change with real model turns, run `claude -p` on a copy of the mod. Patch the copy to turn on, since the mod does nothing under `-p`, and to skip its `$.store` writes, since the run signs in with your own config and would save the trial's sessions to your real inbox.
- Check omp live in a session with a fresh `HOME` folder set on the single command, such as `env HOME=<folder> omp`. omp keeps its settings, plugins and the inbox's state under `HOME`, so a session on your real `HOME` loads your installed inbox and writes to your real inbox's state. Start omp in tmux to capture the band and panel, and kill only the tmux sessions you created, by name. Run `omp/tests` with `bun test --cwd omp tests`.
- To test whether the agent calls `record` or `close`, run `./scripts/eval.sh --suite agent` (see "Text a model reads"). Never let a test session reach an MCP server named `inbox`: the real mod answers the calls and saves them to your real inbox.

## Drawing in each look

- **Every look.** Check every state of what you change, and every move between states, not only the resting forms. Look at frames mid-move. A button must not shift while its press is out, content must not vanish before its space closes, and nothing may flicker. Then look in the real app. Say which states you did not see.
- **Every look.** A look draws the buttons its shared plan lists, in the plan's order. Row buttons come from `rowKeyPlan` in `hooks/view.ts`, and PR buttons from `threadActions`, `checkActions` and `prBlockActions` in `hooks/pr-tab.ts`. A look may style and wrap them. It never reorders, adds or drops one. If a look must differ, add the difference to "Differences on purpose" in `docs/looks.md` with its reason. The demo test in `tests/hooks.test.ts` checks the order in the terminal and desktop looks, and `omp/tests/panel.spec.ts` checks it in the omp panel.
- **Every look.** Sizes the desktop pane and the Codex tab share, such as row padding, live in `hooks/layout.ts`. Change them there so the looks do not drift apart.
- **omp panel.** `omp/src/panel.ts` draws from the shared view and plans, and imports no omp package. Only `omp/src/host.ts` imports omp, so a breaking omp release changes one file. The panel draws plain text lines with ANSI styles and takes keys only, so it needs no `Client`. A new move goes in `handleKey`, and its test in `omp/tests/panel.spec.ts`. Check the panel at a narrow width and in omp's light theme, and say which states you did not see. Rebuild `omp/dist/host.js` with `npm --prefix omp run build` after a change to anything it bundles. An install copies only `omp/`, so the extension cannot import `../hooks` at runtime.
- **Terminal.** The terminal and desktop looks share `hooks/register.tsx`, so a change there for the desktop app can change the terminal too. Check it there.
- **Desktop.** Before designing for the Claude app's pane, read "Drawing limits for desktop design" in `docs/reference/claude-desktop-app.md`. Build only on what it marks verified or stated, and probe anything it marks unknown. A Button there is always native and as small as its label, and its hotkey does nothing. A custom-drawn control that takes clicks over its whole shape needs a `Client`. The pane has no opacity, transform or CSS, so a row changes form in one draw. The pane redraws only on events, so confirm it shows the new build before trusting a capture.
- **Codex tab.** A row's form and animation come from the state machine in `codex/src/rows.ts`. Add a new move there, as `docs/plans/codex-row-states.md` describes, not as a special case in `codex/src/tab.tsx`. Measure each row's height and position frame by frame in a local page that hosts the built tab, in both themes and with reduced motion. Then check it in the Codex app. The server's handler reloads when its file changes, after a reinstall or while `npm --prefix codex run dev` runs, and an open tab then replaces its page with the new one. Only a change to the loader, `codex/src/server-main.ts`, needs Codex quit and reopened.
